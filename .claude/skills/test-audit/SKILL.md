# テストの監査

試作のテストを、少なく、壊れにくく、誤りを確実に捕まえるものに保つためのスキルである。小さな変更のたびにテストを足し続けると、テストが膨らみ、実装を変えるたびに壊れる。このスキルは、テストを足す前に価値を問い、価値の低いテストを定期的に整理する。

テストの設計の原則は、設計書の[テスト](../../../docs/design/07-quality/07-01-testing.md)で定める。このスキルは、その原則をテストを書く場面と見直す場面で適用する手順である。原則とこのスキルが食い違うときは、設計書を正とする。

使い方は二つある。

- **作成時の関門**: テストを加える・変えるたびに通す。
- **監査**: 既存のテストから、価値の低いものを探して整理する。一度に一つのまとまり（モジュール一つなど）を扱う。

## 作成時の関門

テストを加える前に、次の四つに答える。答えられないものがあれば、まだ加えない。

1. そのテストは、どの観察可能な振る舞い、不変条件、独立した契約を守るのか。
2. どんな現実的な退行（regression）があれば、そのテストは失敗するのか。
3. 既存のテストがその失敗を捕まえないのはなぜか。一つの契約には、最も適した境界（下の「持ち主の境界」）に主となるテストを一つ置く。別の層にテストを足すのは、その層に固有の危険（持ち主のテストでは届かない失敗）があるときに限る。似たテストを足す代わりに、表の形のテスト（パラメータを並べたテスト）に行を足すか、共有の準備の処理を使う。
4. 本番のコードが必要としない差し込み口（公開の範囲の拡大、フラグ、ラッパー、注入のための引数）を要するか。要するなら、テストを本当の境界へ移す。

次に、下の「価値の低いテストの型」のどれかに当たらないかを確かめる。当たるなら、「残す基準」が、そのテストが独立して守る契約を名指しできない限り、関門を通さない。振る舞いを変えない作り直し（リファクタリング）で壊れるテストは、振る舞いではなく実装を確かめている。持ち主の境界で書き直してから加える。

不具合を直したときの退行テストは、直す前のコードで、意図した理由で失敗し、直した後に通らなければならない。一度も失敗を確かめていない退行テストは、修正ではなくテストダブル（test double）の振る舞いを確かめているだけである。

## 持ち主の境界

試作では、次のものを持ち主の境界とする。この一覧は、設計書の[テスト](../../../docs/design/07-quality/07-01-testing.md)の「持ち主の境界」と同じ内容である。食い違ったときは設計書を正とし、この節を直す。

- 提供者の層（各提供者のアダプタ）の公開の関数。録った SSE のストリームを入力とし、共通の形のイベント列を出力として確かめる。
- 道具の実行器の公開の関数。道具の呼び出しの JSON を入力とし、道具の結果と、ファイルシステムの変化を確かめる。
- エージェントのループ。模擬の提供者（決まった応答を順に返す）を使い、道具の呼び出し・確認の要求・取り消し・文脈の圧縮の振る舞いを確かめる。
- 安全の性質（制限モードの道具の範囲、確認を飛ばせないこと、OS のサンドボックスが拒否すること）。本物の子プロセスと本物の OS のサンドボックスで確かめる。
- `benitoiteh exec` の入口から、イベントの出力（JSON Lines）・終了状態・セッションの記録までを確かめるゴールデンテスト。

LLM の提供者のネットワークと、端末だけを、テスト用の実装で置き換える。ハーネスの中の部品どうしは、置き換えずに本物をつないで確かめる。Benitoite の処理系（`benitoite`）は本物を使う。

## 価値の低いテストの型

作成時の関門と監査で共通に使う一覧である。

- 何も確かめない（アサーションのない）、網羅率を稼ぐためだけのテスト。
- 自分自身との比較や、入力をそのまま写す処理を確かめるテスト。
- 固定の準備データ、一覧、定義の一覧を写しただけのテスト（道具の定義の JSON を、同じ定義から作った JSON と比べる、など）。
- ソースや文字列を字面で探すだけのテスト。
- 本当の境界で確かめている内容を、非公開の判定や呼び出しの形で重ねて確かめるテスト。
- 同じ契約を、同じ呼び出しで繰り返すテスト。
- テストのためだけにある公開の範囲、大域の値、ラッパーを保つことだけが目的のテスト。
- テストからしか呼ばれない、本番では使わないコード。
- 期待値を、テストの対象の処理（または同じ仕組み）で作っているテスト。
- 確かめたい振る舞いをテストダブルの側で実装しているテスト（模擬の提供者が、エージェントのループのすべき判断を代わりに行う、など）。
- 宣言した性質を読み直すだけで、その性質が実際に働くことを確かめないテスト（サンドボックスの設定の文字列を確かめるだけで、拒否されることを確かめない、など）。
- 別の理由で通ってしまう否定のテスト（意図と別の検査に拒否された、など）。
- 名前や準備データが、実際に確かめていることより多くを約束しているテスト。

## 残す基準

次のいずれかを独立して守るテストは残す。

- 安全の性質（制限モードの道具の範囲、確認、OS のサンドボックス、秘密の除外）。
- 提供者の API との対応（要求の形、ストリームの解釈、誤りの扱い）。
- `benitoiteh exec` の出力の形、終了状態、セッションの記録の形。
- 現実的に起こりうる失敗を捕まえる退行テスト。

遅いことや、静的なことは、削除の理由にならない。

## 監査の手順

1. **読む**: 候補を判断する前に、テストの全体、対象の本番のコード、その入口・呼び出し元・呼び出し先、重なるテスト、変更の履歴を読む。先にリポジトリの AGENTS.md と、設計書のテストの章を読む。
2. **探すだけにする**: 見つける段階では書き換えず、証拠を先に報告する。
3. **証拠を記録する**: 候補ごとに、テストの名前と場所、テストが捕まえられる失敗、確かめている本番のコードのテスト以外の呼び出し元、残る持ち主の境界のテスト、消すことで一緒に消せる本番のコード、確かめるためのコマンドを記録する。一つでも欠けたら、その候補はまだ消さない。
4. **まとめて直す**: 持ち主の境界ごとに、一貫した一まとまりの変更にする。テストのためだけの公開の範囲やラッパーは、別名で残さずに消す。
5. **確かめる**: 対象のモジュールと周辺のテストを `cargo test` で実行し、lint を通す。

## 報告

作業の最後に、消したテストの種類と原因、本番のコードの簡素化、残した候補とその理由、実際に実行した検査とテスト、本番のコードとテストの行数の増減、次に行う作業を報告する。
