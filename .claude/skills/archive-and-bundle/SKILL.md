# ソースのアーカイブとブランチの bundle

ソースのアーカイブ、公開対象外の `private/` の zip、ブランチ・タグの控え（git bundle）を作る手順である。出力はすべて `work/`（git の追跡外）に置く。道具は同じディレクトリの `archive.sh` で、既にある出力のファイルは上書きせず、リモートには何も送らない。`archive` と `private` は `.partial` の名前で作り、照合が通ってから正式な名前へ移す。`.partial` も上書きせず、失敗したら今回作った `.partial` を消して止まる。リポジトリ内で呼び出す。macOS の bash 3.2 で動き、git、tar、zip、unzip を使う。`private` は照合に Python 3 の標準ライブラリも使う。

## ソースのアーカイブ

`.claude/skills/archive-and-bundle/archive.sh archive [<コミット>]`（既定は `HEAD`）で、tar.gz と zip を両方作る。

- ファイル名は `BenitoiteHarness-<タグ>-<ブランチ>-<短いコミット>.<拡張子>` とする（例: `BenitoiteHarness-v0.0.1-gamou-12345678.tar.gz`）。2026-10-21 に設計者が、処理系の命名規則に準じることを決めた。短いコミットは 8 文字に固定する。
- タグは、コミットに付いたタグを使う。付いていなければ直近のタグを使う。タグがなければタグの部分を省き、`BenitoiteHarness-gamou-<短いコミット>.{tar.gz,zip}` とする。
- ファイル名のブランチは、指定したコミットを `gamou` が含むなら `gamou`、次に現在のブランチ、それも含まなければコミットを含む手元のブランチの最初のものとする。ブランチ名とタグ名の `/` はファイル名では `-` に替える。
- 中の最上位のディレクトリは、タグの付いたコミットなら `BenitoiteHarness-<版>/`（タグの `v` を除く。例: `BenitoiteHarness-0.0.2/`）、ほかは `BenitoiteHarness-<短いコミット>/` とする。
- 道具は、中のファイルの数がコミットの木のファイルの数と一致することを確かめる。
- アーカイブに入るのは、コミットした追跡中のファイルだけである。`private/`、`reference/`、`work/`、`target/`、コミットしていない変更は入らない（追跡外であることが前提）。作る前に `git status` で、入れたい変更がコミットしてあるかを確かめる。

アーカイブを作るのは、設計者に頼まれたときである（リリースのタグを付けた後など）。作ったら、ファイル名と大きさを報告する。

## 公開対象外の zip

`.claude/skills/archive-and-bundle/archive.sh private` で、現在の作業ツリーの `private/` 全体を zip に保存する。設計者が公開対象外の控えを頼んだときに使う。

- ファイル名は `work/BenitoiteHarness-private-<ブランチ>-<短いコミット>-<日付>.zip` とする。ブランチは現在のブランチ、短いコミットは `HEAD` の先頭 8 文字、日付は実行環境の日付（`YYYY-MM-DD`）である。ブランチ名の `/` は `-` に替える。ブランチのない状態では止まる。
- zip 内の最上位は `private/` とする。隠しファイル、空のディレクトリ、コミットしていない変更も入る。シンボリックリンクは外部やディレクトリを指すものもリンクのまま入れ、参照先を辿らない。`.claude/skills/` と `.agents/skills/` にあるリンクは対象外であり、復元時は AGENTS.md の Agent Skills の運用に従って作り直す。
- 対象は gitignore で除いた `private/` に限る。リポジトリ直下の `work/`、`target/`、`reference/` は入れない。`private/` 自体がリンクなら止まる。
- `private/` の下で `.env`、`*.pem`、`settings.local.json` という名前を見つけたら、内容を読まずに止まる。ファイル、ディレクトリ、リンクのいずれも対象とし、リンクの参照先は辿らない。
- 作成後に zip の整合性と、元と zip 内のファイルの数・名前・リンクの種類が一致することを確かめる。数には通常のファイルとリンクを含め、ディレクトリの項目は含めない。照合に失敗した zip は完成品として扱わず、原因を確かめる。作成中は `private/` の書き換えを止める。

`private/` には API キーやトークンなどの秘密の値を置かないことを前提とする。非公開の運用情報を含むため、この zip は公開・push しない。作成の前後に次の確認を行う。

1. 作成前に `private/` のファイル一覧を調べ、設定、依頼文、報告、記録に秘密の値が保存されていないことを確かめる。キーの保管先や取得方法の記述と、キーの値を区別する。秘密を扱う道具は、キーチェーンなどから実行時に取得し、ファイルや出力に値を書かないことを確かめる。
2. 秘密の疑いがある箇所は、値を表示しない検査（たとえば `rg -l` で候補のファイル名だけを得る）で絞り、所有者がローカルで内容を確かめる。候補の値を LLM、端末の出力、報告へ写さない。疑いが解消できなければ作成を止める。
3. 作成後は zip 内の一覧を確かめ、同じ秘密の検査を一時の展開先でも行う。リンクは辿らず、確認後は一時の展開先を消す。作成から確認が終わるまで zip を共有しない。秘密の値が見つかった場合は保存物として扱わず、所有者に報告して対処する。件数の一致だけで「秘密がない」と判断しない。

作ったら、ファイル名、大きさ、元と zip 内のファイルの数、秘密の値の確認結果を、値そのものを含めずに報告する。

## ブランチとタグの bundle

ブランチを整理するときは、消す前に bundle に保存する。消すのは設計者の指示があるときだけで、push 済みの `gamou` とリモートのタグは扱わない。

1. 消す候補を示す。`git branch -vv`、`git tag`、`git worktree list` で、ブランチとタグ、作業ディレクトリが使っているブランチを確かめ、`gamou` に取り込み済みか（`git merge-base --is-ancestor`）を添えて設計者に示す。記録の文書（`docs/plan/results/`、`tools/skill-eval/results/` など）が引くコミットを持つブランチは、そのことも示す（保存先は `work/bundles.md` に記録する）。
2. 保存する。
   - 選んだ参照: `archive.sh bundle <名前> <ブランチやタグ>...`
   - `gamou` とリリースのタグ（`v<数字>…`）以外のすべて: `archive.sh bundle <名前> --all-except-main`（旗の名前は手本との互換のため維持する）
   出力は `work/BenitoiteHarness-<名前>-<日付>.bundle`（例: `BenitoiteHarness-branches-and-tags-before-cleanup-2026-10-11.bundle`）。道具は `git bundle verify` に加えて、保存した参照ごとに bundle の中の値が手元の値と一致することを確かめ、一つでも合わなければ何も消さずに止まる。
3. 消す。設計者の指示があれば、同じ呼び出しに `--delete` を付ける（保存と確かめの後に、保存した手元のブランチとタグを消す）。`gamou`、今のブランチ、リリースのタグ（`v<数字>…`）は消さない。作業ディレクトリが使っているブランチは git が拒むので残る（必要なら作業ディレクトリを先に片付ける）。
4. 記録する。bundle のファイル名、中の参照の数、記録の文書が引くコミットとそのブランチ、戻し方を、`work/bundles.md`（git の追跡外）に残す。手元に残す控えのブランチも同じ文書に記録する。bundle とこの記録は片付けで消さない。

戻し方: `git fetch work/<bundle> 'refs/heads/<名前>:refs/heads/<名前>'`（タグは `refs/tags/<名前>:refs/tags/<名前>`）。中の参照の一覧は `git bundle list-heads work/<bundle>`。

## 注意

- `work/` のアーカイブと bundle は git の追跡外で、このリポジトリの履歴には残らない。消すと戻せないので、片付けでも消さない。
- push と、リモートのブランチやタグの削除は、このスキルでは行わない。push は設計者の指示を得てから、スキル `git-workflow` に従って行う。
