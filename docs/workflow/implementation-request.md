# 実装作業の共通依頼文

作業ごとの依頼は、下の指定を埋めた自己完結の文にする。個人のパスと接続先は依頼文の中だけで渡し、公開の文書へ写さない。実装者の手順は [作業の進め方](../plan/00-common.md)、作業文書の構成は [雛形](change-plan-template.md)に従う。

## 依頼と取り込みの手順

1. Codex に作業の文書を書かせ、作るもの、触るファイル、依存、完了条件を明示する。
2. Claude Code が、作業の文書を設計書と既存のコードに照らして点検する。修正が要る場合は Codex に補足を書かせ、点検してから実装へ進む。
3. オーケストレータが作業ごとのブランチと git worktree を用意し、その worktree で `cargo fetch` を実行して依存を取得してから Codex へ依頼する。Codex 内の検査は取得済みの依存を使う。
4. Codex の報告を受け、オーケストレータがサンドボックスの外で `scripts/check.sh` の全体を走らせる。失敗は出力と終了状態を添えて同じ作業のセッションへ返す。
5. Claude Code が変更をレビューする。レビューに Codex を使わない。修正を依頼した場合は、その修正に応じて検査とレビューをやり直す。
6. 取り込む直前に、対象の変更に対する検査の出力と終了状態を読み、終了状態 0 を確かめる。失敗の記録を成功に書き換えない。コミットと `main` への `git merge --no-ff` は [git-workflow](../../.claude/skills/git-workflow/SKILL.md)に従う。
7. 確かめた結果を Codex に設計書と実装プランへ反映させ、Claude Code が点検して取り込む。依存を足した場合は、実行ファイルの大きさの変化を測り、`docs/plan/results/` に記録させる。
8. 取り込んだ内容で release の実行ファイルを作り直す（`cargo build --release -p benitoiteh`）。

## 作業の指定

| 欄 | 依頼時に埋める内容 |
|---|---|
| 作業 | 作業 ID、目的、作業文書と補足の場所 |
| 作業ツリー | 作業ディレクトリの絶対パスとブランチ |
| 変更の範囲 | 触ってよいファイル、新しく作るファイル、変えてはならないもの |
| 完了条件 | 作るもの、確かめる契約、必要な検査、報告に残すこと |
| 読み取り専用のリポジトリ | Benitoite の処理系の場所（既定は作業ツリーの隣の `../Benitoite`）。必要なら DeepSeek Harness の場所も指定する |
| テスト用の処理系 | 実行ファイルの絶対パス、対象の OS・CPU、下記の環境変数との対応 |
| 再開時の情報 | 修正する指摘、失敗した検査の出力、終了状態、実行環境 |

テスト用の処理系は macOS、aarch64 Linux、x86_64 Linux のどれに使うものかを示し、`BENITOITEH_TEST_BENITOITE`・`BENITOITEH_TEST_BENITOITE_AARCH64`・`BENITOITEH_TEST_BENITOITE_X86_64` と対応させる。主の作業ツリーの `work/` に置いた実行ファイルを、依頼先の `$PWD/work/` と取り違えさせない。git worktree に現れない設定や条件が必要なら、秘密の値を除いて依頼文に含める。

## 担当へ渡す指示

最初に `AGENTS.md` と指定した作業文書を読み、その範囲と完了条件に従って実装する。テストを作る・変える場合は [test-audit](../../.claude/skills/test-audit/SKILL.md)と [実装の規約の補足](../plan/00-common.md#実装の規約の補足)を読み、root のコンテナ、長い一時パス、シェルの有無などの環境差を考慮する。

本物の LLM を呼ばない。利用者の普段の設定・状態（`~/.config/benitoiteh`・`~/.local/state/benitoiteh` など）、キーチェーン、トークン、`~/.ssh` を読まない。テスト用の模擬の設定と状態を使う。

コミットしない。共通の検査は `scripts/check.sh --inside-codex` を使い、OS のサンドボックスとコンテナを要する検査はオーケストレータへ残す。保護を外した代替の検査をしない。最後の報告は [完了の報告](../plan/00-common.md#完了の報告)の形で日本語で書く。

## 起動と再開の条件

作業ごとに新しいセッションを、その作業の worktree で起こす。サンドボックスは `workspace-write` とし、`danger-full-access` で起動しない。同時に動かす実装担当の Codex は一つとする。失敗の修正は `codex exec resume` で同じ作業のセッションを再開し、失敗した検査の環境も渡す。

背景で動かす作業は、実行ツールが返した ID と終了の通知で追跡する。通知のない形で起動する場合は PID を記録し、終了後に報告と終了状態を別に確かめる。シェルの ID と PID を取り違えない。

## コマンドを制限した作業者への依頼

作業者の許可一覧に合わせて、許したコマンドの形を依頼文にも列挙する。作業ツリー外への `cd` や、許していないコマンドとの連結など、避ける形も書く。一つのコマンドが拒否されても、その道具全体の禁止を意味しないことを伝える。起動の許可一覧と依頼に載せる一覧は、同じスクリプトで管理して食い違いを防ぐ。

## 評価を依頼するとき

本物の LLM を呼ぶ評価は、`AGENTS.md` と [評価の手順](../design/07-quality/07-02-evaluation.md#評価の手順)に従い、提供者・モデル・回数・見込みの費用を設計者に示して了承を得る。時間を比べる走行中は Codex と全体の検査を同時に動かさない。評価のまとまりごとに release を写した同じ実行ファイルを使い、サンドボックスの方針を変えた後は release を作り直して写し直す。
