# P5-33 圧縮の 2 課題・資料の生成と否定の対照

## 目的

BH-014 の比較に使う `compact_json_summary`・`compact_dir_walk` を作る。3 段の依頼と資料、生成の道具、正しい解、全段の条件を調べる判定、初めの条件を欠いた否定の対照を担当する。P5-32 の後に行い、評価の道具とつないで確かめる。本物の LLM を呼ばず、長さの確定と BH-014 の決定は有料の試しの後に残す。

- 既存の `tools/skill-eval/tasks/json_summary/`・`dir_walk/`、`README.md`、`SOURCE.md`、取り込んだ v0.0.7 の Skill。テストの計画は `test-audit` の作成時の関門に従う

## 作るもの

- `tasks/compact_json_summary/`・`tasks/compact_dir_walk/` を新設する。`task.json` は `kind: staged`、`result_kind: run`、`script`、`attempt_limit`、`stages`（相対の Markdown のパス 3 個の配列）、`http: false` を持つ。最終の `reference.bnt`・`expected.stdout`・`expected.files/` は既存の実行の課題と同じ使い方にする。段のパスは課題の中の通常のファイルに限り、リンクと `..`、絶対パスは拒む。
- 元の `json_summary` などを読むが、11 課題の原本は変えない。新しい 2 課題の内容は次のとおりとする。

  | 課題 | 第 1 段で与える条件 | 第 2 段で加える条件 | 第 3 段で求める変更と最終判定 |
  |---|---|---|---|
  | `compact_json_summary` | 注文の JSON を地域ごとに集計する。取消済みを除き、金額の欠落は 0 とし、地域を名前順に出す | 地域ごとの件数と金額を JSON ファイルにも書く。未知の地域を `other` にまとめる | CLI の引数で入力を選べるようにする。取消済み、金額の欠落、未知の地域、空の入力を含む別の入力で、全段の条件を判定する |
  | `compact_dir_walk` | `.md` のファイルの相対パスを名前順に出す。隠れたディレクトリと `drafts/` 以下を除く | 拡張子の大文字も扱い、ディレクトリごとの件数を JSON に書く | CLI の引数で走査の根を選べるようにする。除外する場所、大文字の拡張子、空の根と入れ子の入力で、全段の条件を判定する |

- `task.md` は 3 段の進め方だけを書き、各段の条件はその段の依頼の本文だけで渡す。後の依頼やファイルに前の条件の全文を写さない。条件を応答で繰り返すことを求めない。条件の欠落は、各条件に対応する判定の名前で分類する。
- 各段に、入力仕様の例と期待する中間の集計、走査の対象外になる例など、課題に関係する資料を付ける。標準ライブラリだけの生成の道具で、同じ引数なら同じバイト列になるようにする。解のコード、無意味な反復、確認を促す指示を混ぜない。資料は workspace の `materials/` に置き、一つ 12 KiB 以下に分ける。段の依頼の本文は 4 KiB 以下にする。理由: 大きな依頼を一つの会話の項目にすると、残す量のどちらにも入らず、残す量の差を測れなくなる。
- 初めは資料の総量を 24・48・64 KiB の候補から選んで作り、生成の引数とハッシュを記録する。資料が足りなければ同じ 12 KiB 以下の単位で増やす。模擬の使用量と複数の実際の読み取りの結果で、次の依頼の前に圧縮し、直近の複数の項目が残ることを確かめる。有料の試しでは、設計書 07-02 の圧縮と残す量の条件を満たすかを確認する。本体の前に全条件で共通の長さと段を固定し、足りなければ追加の試しを設計者へ示す。課題ごとの固定値を `task.json` の `generation` に残す。
- 最終の成果物は原本の入力を置き直した判定用のディレクトリで検査する。`task.json` に `judge_cases`（`name`・`input`・`args`・`expected_stdout`・`expected_files` の配列）を加え、課題の中の `cases/<名前>/` に入力と期待する出力を置く。すべてのパスに段のパスと同じ検査を掛ける。ケースごとに新しい判定のディレクトリを作り、原本の入力とケースの入力を重ね、最終のスクリプトだけを写し、`benitoite run <script> <args>...` の形で検査する（取り込んだ [v0.0.7 の Skill](../../../assets/benitoite/v0.0.7/skill/SKILL.md) の実行の形に従う）。JSON の生成ファイルは値で比べる。初めの条件の欠落もケースの名前で理由に残す。最終の reference の宣言したエフェクトが、各段の解に要るエフェクトをすべて含むようにし、既存の `task_allow` の規則で全段に同じ `--allow` を渡す。

- 各課題の `task.json` に `self_test_failures: [{"script": "negative/<名前>.bnt", "case": "<judge_cases の名前>"}]` を置く。最初の条件を一つだけ外した解と、その条件を調べるケースを対応させる。
- 段の実行と上限・費用の合計、`--suite compaction` と `--interleave`、集計の仕組みは P5-32 を使う。必要な変更があれば、この 2 課題をつなぐ範囲に限る。
- `SOURCE.md` に元の課題と変えた点、生成の引数・ハッシュ、再開直後のバイト数による見積もりの注意を残す。`README.md` に LLM を呼ばない準備・検査と有料の走行の使い方を書く。試し 3 回、本体 18 回、停止額 $5 の条件は設計書 07-02 を参照する。

## テスト

- `--self-test --suite compaction` で、最終の解が全ケースを通り、最初の条件を一つ外した解が指定のケースで落ちることを両課題で確かめる。期待値を解から計算しない。
- `--dry-run --suite compaction` で、LLM とキーを使わず準備と判定を通す。資料を段の直前に置くことと、後の条件で前の条件を繰り返していないことも確かめる。
- 同じ生成の引数で同じバイト列になるよう、並び、改行、`json.dumps` の引数を固定する。量の候補とハッシュを記録する。
- 模擬の固定の使用量と複数の実際の読み取りの結果を使い、再開と圧縮、段の境で `kept_items > 0`、残す量の差、3 段の上限の合計を確かめる。実際の LLM の成績や比較の成立を模擬で証明したとは扱わない。

## 完了条件

- `scripts/check.sh --inside-codex` と 2 課題の self-test・dry-run が通る。模擬とサンドボックスを要する通しは、オーケストレータが外で確認する。
- 課題の生成の引数、ハッシュ、判定と否定の対照の例、比較が成立しない場合の行、走らせなかった検査を報告する。

## 補足（2026-10-20、始める前の点検）

本節は、上の各節に優先する。以下の推奨を、明記した修正を除いてこの作業の指示として採る。コードの行番号は、点検報告が参照した main の `d67e1af` のものである。

### 段ごとの資料と見積もり

1. **段ごとの資料の置き方がない**
   - 初めから全段の資料を置くと、第 1 段で後の段の資料を読めてしまう。
   - 推奨: 課題に `materials/1/`・`2/`・`3/` を置き、道具が段 N の起動の直前に workspace の `materials/N/` へ写す。`stages` の形は変えず、規約で対応させる。

2. **段の境の見積もりの元が変わる**
   - 再開した各段の最初の判定は、提供者の報告ではなく、全体のバイト数 ÷ 3 で見積もる（`agent/mod.rs:529`、`context/mod.rs:179`）。
   - 制限モードのシステムプロンプトと道具の定義だけで約 39 KB（31,390＋7,569 B）、見積もりで約 13,000 トークンを占める。
   - 資料の量の候補はこの見積もりで選ぶ。予備の比較の解釈の注意として `SOURCE.md` に書く。
   - 模擬の固定の `input_tokens` は、再開した最初の判定には効かない。

3. **DeepSeek の口で残す範囲ができる時点:** `anthropic-messages` では、道具が続く途中は残さない（`tool_sequence`）。`kept_items > 0` になるのは、末尾が新しい依頼である段の境だけである。設計書どおりだが、テストの表に明記する。

### 否定の対照とエフェクト

1. **否定の対照の置き場がない:** 推奨: `task.json` に `self_test_failures: [{"script": "negative/<名前>.bnt", "case": "<judge_cases の名前>"}]` を足し、名前を挙げたケースで落ちることを確かめる。

2. **エフェクト:** 最終の解は `Process.arguments()` を使うので `Process.Environment` を要する（`assets/benitoite/v0.0.7/skill/references/idioms.md:417`）。`task_allow` は最終の `reference.bnt` から決まるので、全段に同じ `--allow` が付く。

### 生成と判定の注意

- 課題の `materials/1/`・`2/`・`3/` は、その段の起動の直前にだけ写す。段のパスの配列 `stages` は変えない。
- Python 3.9 の標準ライブラリだけで生成する。生成の引数と出力のハッシュを `generation` に残す。
- `kept_estimate` は再構築前に選んだ範囲の見積もりである。推論を除いた後の送信量より多くなる場合がある。
- 課題は P5-32 の後に接続を確かめる。内容の下書きは P5-30 と並べて進められるが、完了には評価の道具による判定が要る。
