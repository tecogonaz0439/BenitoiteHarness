# P5-36 圧縮の課題の長さと段の区切りの調整

## 目的

P5-33 の後に、BH-014 の 2026-10-21 の試しの走行を調べ、二つの圧縮の課題の長さと段の区切りを共通の規則で調整する。本物の LLM を呼ばず、Rust の製品のコードと元の 11 課題を変えない。3 段では条件を満たせないと判断した場合は、資料の再生成を進めず、段数の変更を含む選択肢を設計者へ報告する。

## 読む設計書

## 作るもの

- 指定された生の記録の stdout とセッションから、番ごとの見積もり、資料の読み取り、圧縮の時点、段の境での増分を調べる。最後の応答・推論・次の依頼の量と、再開時の見積もりの計算法の切り替えを区別する。生の記録は写さず、数値の要約だけを本書に残す。
- 3 段、短い依頼、12 KiB 以下の資料という条件を守り、両課題に共通の資料量・分割の規則を選ぶ。全資料を読む場合と読まない場合を計算し、読み方と未確定の応答量に依存する範囲を明示する。3 段で満たせない場合は、根拠と選択肢を本書に残して止める。
- 調整を実施できる場合は、生成の引数と `task.json` に値を固定し、資料を決定的に生成し直す。システムプロンプトと道具を含めたバイト数を 3 で切り上げて割るオフライン検査を加える。
- 調整を実施できる場合は、設計書 07-02 と `SOURCE.md` を更新する。設計書の変更は【方針】（2026-10-21、試しの走行を受けたオーケストレータの決定）とし、試しの結果を 1〜2 文で添える。

## テスト

- 資料を全部読む場合と読まない場合について、段末と次の段の最初の番の見積もりを三条件の境（40,960・49,152・40,960）と比べる。資料の量や依頼が増え、段の途中で境を超える退行を検出する。既存の生成の再現性と模擬の検査だけでは、この量の契約を検証できない。
- 調整後は既存の生成の再現性の検査、圧縮の課題の模擬、self-test と dry-run を使う。OS のサンドボックスを要する通しは Codex 外へ残し、保護を外して実行しない。
- 指定の `BENITOITEH_TEST_BENITOITE` を使い、`scripts/check.sh --inside-codex` を走らせる。普段の設定と `~/.agents` を読まず、起動時の XDG と TMPDIR は作業用の一時ディレクトリにする。

## 完了条件

- 生の記録を調べ、オーケストレータの見立ての正否と段の境の数値を説明できる。
- 3 段で可能な場合は、共通の生成条件・見込みの見積もり・ハッシュを固定し、オフライン検査と `scripts/check.sh --inside-codex` が通る。模擬と dry-run のうち外での実行が必要なものを報告する。
- 3 段では満たせない場合は、実装を止め、根拠・選択肢・推奨案を報告する。この場合は本作業を「完了」にしない。
- LLM の API を呼ばず、コミットしない。Rust の製品のコード、追加の依存、元の 11 課題、作業ディレクトリ外のファイルを変えない。

## 確かめること

- 全部読む場合の量と圧縮の時点、資料の読み方による違い。
- 段の途中と再開直後で見積もりが異なる理由と、最終応答・推論・次の依頼による増分。
- 3 段で、予備の比較の時点の差と、残す量の比較の成立を両立できる条件。

### 全量を読む場合と読まない場合の計算

次の表は、現行資料について、固定部分 36,428 B と三つの依頼、全資料の行番号付きの読み取り結果を数えた下限である。最初の依頼には、生の記録で確認した環境と共通の依頼文の計 1,312 B を足した。後の依頼に環境の差分はなかった。走査の課題にも同じ長さの環境・共通の依頼文を仮定した。通常の read の行番号は `六桁の右寄せ番号 + タブ + 本文 + LF` として数えた。

資料を読まない列は依頼だけの量であり、課題を正常に終えられる会話の予測ではない。全量を読む列も、道具の引数・応答・実装のコード・言語の資料・実行結果を除いた下限である。途中の圧縮は計算に入れず、圧縮前の累積量を示す。圧縮後の量は要約と選ばれた範囲によって変わるので、この累積量を実際の送信量とは扱わない。

| JSON | 1 | 91,799 / 99,555 | 12,809 | 45,994 | 46,131 |
| JSON | 2 | 91,602 / 99,204 | 12,946 | 79,199 | 79,320 |
| JSON | 3 | 91,764 / 104,364 | 13,067 | 114,108 | — |
| 走査 | 1 | 91,600 / 99,006 | 12,813 | 45,815 | 45,965 |
| 走査 | 2 | 91,660 / 103,854 | 12,963 | 80,583 | 80,694 |
| 走査 | 3 | 91,620 / 108,000 | 13,074 | 116,694 | — |

各段は 9 ファイルで、JSON のファイルは 7,610〜10,557 B、走査は 7,056〜10,568 B である。両課題とも、全量を読む場合は第 1 段だけで低い境 40,960 を超える。予備を減らす条件の境 49,152 にも第 2 段の途中で達しうる。読まない場合は、資料をいくら増やしてもこの列の量は増えず、どの境にも届かない。これだけで、すべての読み方で圧縮が起きることを資料の量から保証できないと分かる。ただし、依頼の条件は「起きやすい」であり、未読の試行に圧縮がないことだけを停止の理由とはしない。

### 3 段のまま資料量を固定する案の限界

3 段の依頼には、正常に完了した依頼をまたぐ境が二つしかない。同じ読み方と出力量で、低い境と高い境の圧縮を異なる段の境へ分けるには、低い境を段 2 の入口、高い境を段 3 の入口で超える構成が必要になる。段 3 の資料を増やしても、その二つの入口の量は増えない。

今回の記録の資料以外の会話を保ち、行番号付きの資料の結果の量だけを置き換える、全バイト数による試算を行った。第 1 段の結果の量を X、第 2 段を Y とする。現行値の記録では、段 1 の最後の応答の直前の量は `81,654 + X` B、段 2 の入口は `83,368 + X` B になる。段 1 の途中で 40,960 を超えず、段 2 の入口で超える範囲は `39,513 ≤ X ≤ 41,226` B である。

一方、予備を減らす条件の記録では、段 2 の最後の応答の直前の量は `117,260 + X + Y` B になる。ここで高い境 49,152 を超えないためには `X + Y ≤ 30,196` B が必要であり、前の範囲と重ならない。この差には言語の資料の読み取り、コード、推論など、課題の資料量では直接固定できない内容が含まれる。

この試算は、資料を変えた後も LLM が同じ応答を返すという予測ではなく、既に観察した出力量を使った検査の候補である。これから「どのような 3 段の課題でも成立しない」とは結論しない。しかし、現行の依頼を保って資料だけを縮める案は、この二つの検査条件をともに満たせない。特定の条件の短い応答だけを前提に生成値を固定しても、今回問題になった読み方と出力量への依存を取り除いたとは言えない。

### 停止した範囲と選択肢

共通の資料量を固定できる根拠が得られないため、依頼の停止条件に従い、生成の引数・`task.json`・資料・設計書 07-02・`SOURCE.md` の変更へ進まず停止した。Rust の製品のコード、評価の実行器、元の 11 課題は変えていない。新しい検査を、根拠のない出力量の仮定で合格させることもしない。

設計者が選べる案は次の三つである。

| 案 | 変更と確かめ方 | 制約 |
|---|---|---|
| 3 段のまま、資料量を減らして再試行 | 段 1・2 の量を別に指定できる生成へ変え、全部読む場合の途中の超過と、未読・部分読みの場合の圧縮不足を併記する。有料の追加の試しで成立率を測る | 今回観察した出力量すべてには合わせられず、比較が成立しない試行を許容する方針と、追加の回数・費用の了承が要る |
| 段を増やし、資料の調査と実装の更新を分ける（推奨） | 例えば既存の三つの仕様の段を調査と実装の二つに分け、計 6 段を候補にする。各依頼と一度に読む資料を小さくし、圧縮できる依頼の境を増やす。新しい段の資料量と読み方をオフラインで計算してから固定する | 設計書の「3 段」の変更について設計者の了承が要る。6 段という数と量は候補であり、まだ成立を確かめていない。段数だけ増やしても、未読による圧縮不足をなくせるわけではない |
| 3 段を維持し、再開時に渡す文脈を評価の実行器で固定する | モデルの任意の読み取りと独立した、決定的な資料の追加を評価の道具へ設ける | 短い依頼と、自然な課題の会話で比較する現行の方法を変えるため、設計者の判断が要る。大きな一項目を足すだけでは残す量の比較を壊すので、追加方法の設計も必要である |

推奨の理由は、全量の一括読みの量を抑えながら、予備の比較を異なる依頼の境へ分ける機会を増やせることである。いずれの案でも、本物の LLM の API を呼ぶ前には回数と費用の了承を取り直す。BH-014 は閉じない。

### 実行した検査

指定された `BENITOITEH_TEST_BENITOITE` を使い、XDG と TMPDIR を作業用のディレクトリに向けて `scripts/check.sh --inside-codex` を実行した。fmt・clippy・ホストのテスト・既存資料の生成の照合・評価の道具・性能の道具・Linux 二対象のテスト用ビルド・ライセンス・リリースビルドの全段が通った。評価の道具は 103 件中 39 件を規定に従って除き、残りが通った。実行ファイルは macOS aarch64 が 5,706,560 B、Linux aarch64 が 6,232,880 B、Linux x86_64 が 7,498,224 B である。製品のコードを変えていないので、これらを本作業による性能の変化とは扱わない。

`tests/sandbox_*.rs`、Linux のテストの実行、評価の道具の `requires_sandbox` と `test_judge_sandbox.RuntimeTests`、self-test・dry-run、`benitoiteh-mock`・`benitoiteh-mock-completion-check`・`benitoiteh-mock-compact` の通しは Codex 内では走らせていない。保護を外した代替の実行はしていない。新しいテストの追加・削除と製品のコードの変更はともに 0 行である。作業文書の相対リンクと、上の不等式の境の整数計算も確かめた。
