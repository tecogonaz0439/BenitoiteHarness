# P0-03 HTTP と TLS の層、ストリームの打ち切りと名前の解決の差し替え（BH-010）

## 目的

提供者の層（P1）と `web_fetch`（P4）が使うモジュール `http` を作り、`ureq` で次のことができるかを確かめる（BH-010）。

- ストリーミングの応答の受け取りを、別のスレッドから打ち切れるか。
- データが届かない時間の上限を、`ureq` の外で見張って掛けられるか。
- 名前の解決を差し替えて、判定済みのアドレスにだけ接続できるか。

## 前提（オーケストレータが確かめたこと）

`ureq` 3.4.2 は、`Agent::with_parts(config, connector, resolver)` で、接続の処理（`unversioned::transport::Connector`）と名前の解決（`unversioned::resolver::Resolver`）を差し替えられる（`ureq-3.4.2/src/agent.rs`、`src/unversioned/`）。時間の上限は段階ごとの合計の時間（`timeout_connect`・`timeout_recv_response`・`timeout_recv_body`・`timeout_global` など）であり、読み取りごとの上限ではない（`src/config.rs`）。ソースは `~/.cargo/registry/src/index.crates.io-*/ureq-3.4.2/` にある。

## 作るもの

`crates/benitoiteh/src/http/`（`mod.rs`、`text.rs` ほか）と、そのテスト。

1. `HttpClient`: `ureq::Agent` を包み、TLS を `rustls`（暗号の実装は `rustls-graviola`）と OS の証明書の検証で設定する。Benitoite の処理系の設定の仕方（`git -C <Benitoiteのリポジトリ> show v0.0.6:crates/benitoite/src/builtins/funcs/http_client.rs` の 68〜74 行のあたりで `ureq` の `Agent` を作っている）に揃える。接続は使い回す。プロキシの環境変数を使わない設定にする（`web_fetch` の規則。提供者への要求でも使わない）。
2. ストリーミングの要求: `POST` で JSON の本文を送り、応答の状態とヘッダを返し、本文を別のスレッドで読む。読んだバイト列は `std::sync::mpsc::sync_channel` で渡す。呼び出した側は次のことができる。
   - 打ち切る（取り消しの印を立てる）。打ち切ったら、読み取りのスレッドがすぐに（目安 1 秒以内に）終わり、チャネルの受け取り側に打ち切りが分かる。
   - 最後にデータを受け取った時刻を見る。データが届かない時間が上限を超えたら、呼び出した側が打ち切る。
   - 打ち切りの方法は、確かめた結果で選ぶ。候補は、差し替えた接続の処理が下の TCP の接続の写し（`TcpStream::try_clone`）を持ち、打ち切りのときに `shutdown` する形である。使い回した接続は接続の処理（`Connector`）を通らないので、写しと要求を結び付けるには、接続を包む `Transport` に打ち切りの印を持たせる形か、ストリーミングの要求に使い回しをしない別の `Agent` を使う形が要る。どちらを採ったかと理由を報告に書く。打ち切れないと分かったときは、読み取りのスレッドを切り離して結果を捨てる形にし、その旨を報告する（設計書 02-01 の「HTTP の通信」の代わりの作り）。
3. 普通の要求（`GET`）: `web_fetch` のために、リダイレクトを自動で辿らず、受け取る本文の大きさの上限（呼び出す側が与える）で読むのをやめる。`Accept-Encoding` を送らない。
4. 名前の解決の差し替え: 呼び出す側が与えたアドレスの一覧だけに接続する `Resolver`。証明書は URL の元のホストの名前で照合されることを確かめる。
5. 時間の上限: 接続 10 秒、ヘッダまで 120 秒、データが届かない時間 300 秒、全体 30 分を既定とし、呼び出す側が変えられる。
6. 誤りの型 `HttpError`。接続の失敗、時間の上限、TLS の誤り、打ち切り、本文の上限、HTTP の状態を分ける。HTTP の状態の誤り（2xx 以外）は、状態の値、ヘッダの `Retry-After`、本文の先頭 64 KiB までを保つ。理由: P1 のアダプタが、本文の `error.type`・`error.code`・`message` で誤りを分類する（文脈の超過など）。
7. 要求のヘッダ（API キーのヘッダなど）は、呼び出す側が与える。`http` はヘッダの値を誤りの文と `Debug` の出力に含めない。

## 確かめること

1. 上の 2 の打ち切りが、TLS の接続（`https`）と平文の接続（`http`、手元の推論サーバのため）の両方で働くか。テストは手元の TCP のサーバ（テストの中で立てる。TLS は自己署名の証明書を使うなら、その証明書を信頼する設定をテストの中だけで作る。難しければ平文だけを確かめ、TLS は `shutdown` が下の TCP に届く理由をソースで示す）。
2. データが届かない時間の見張りが、ヘッダの後、本文の途中で止まったサーバで働くか。
3. 名前の解決の差し替えで、与えたアドレスだけに接続し、`Host` のヘッダと TLS の名前が元のホストのままであるか（ソースで示すか、テストで確かめる）。
4. TLS の設定とクレートを加えた後のリリースのビルドの実行ファイルの大きさ（P0-01 の後との差）。

Codex のサンドボックスはネットワークを許しているが、テストは外部のホストに接続しない。手元のループバックのサーバだけを使う。

## テスト

- 打ち切り: 本文を少しずつ送り続けるサーバに対して、打ち切りを立てると、読み取りのスレッドが終わり、呼び出した側が打ち切りの誤りを受け取る。
- データが届かない時間: 本文の途中で送るのを止めるサーバに対して、短くした上限で誤りになる。
- 本文の上限と、リダイレクトを辿らないこと。
- 名前の解決の差し替え: 名前をループバックのサーバのアドレスに解き、そのサーバに要求が届く。
