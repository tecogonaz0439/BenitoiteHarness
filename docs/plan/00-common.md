# 作業の進め方

本章は、実装プランの作業を実装する者（Codex）が、どの作業でも守る手順と規約を定める。

## 作業を始める前に読むもの

1. リポジトリの `AGENTS.md`（特に「実装の規約」「してはならないこと」）。
2. 本章と [10-interfaces.md](10-interfaces.md)。
3. 作業の文書（`docs/plan/tasks/<ID>-*.md`）と、その「読む設計書」に挙げた章と節。
4. 作業の文書の「触るファイル」に挙げた既存のファイルと、使う型を定めた既存のモジュール。
5. テストを書く・変えるときは、`.claude/skills/test-audit/SKILL.md`。

設計書の全部を読む必要はない。挙げていない章を読むのは、挙げた節が参照していて、判断に要るときだけとする。

## 作業の手順

1. 作業の文書の「作るもの」と「完了条件」を確かめる。
2. 実装し、テストを書く。テストは、作業の文書の「テスト」に挙げた契約を、[テスト](../design/07-quality/07-01-testing.md)の「持ち主の境界」の境界で確かめる。
3. `scripts/check.sh --inside-codex` を通す（後述の「検査」）。
4. 完了の報告を書く（後述の「完了の報告」）。

コミットしない。ブランチの作成、コミット、取り込みはオーケストレータが行う。

## 作業の範囲

- 作業ディレクトリ（オーケストレータが示した git の作業ツリー）の外のファイルを変えない。`../Benitoite` は読むだけとする。
- 作業の文書の「触るファイル」に挙げたもの、新しく作るファイル、そのテストだけを変える。ほかのファイルを変える必要が生じたら、小さな変更（`lib.rs` へのモジュールの宣言の追加、`Cargo.toml` への依存の追加など、作業の文書が予定しているもの）を除き、止まって報告する。
- 依存のクレートは、[10-interfaces.md](10-interfaces.md) の「依存のクレート」の表の版だけを使う。表にないクレートが要るときは、止まって報告する。
- 設計書と実装プランは変えない。食い違いや不足に気付いたら、後述の「止まるとき」に従う。

## 止まるとき

次のときは、実装を進めずに、完了の報告の形で、何が問題で、どの選択肢があり、どれを勧めるかを書いて終える。

- 設計書と実装プランが食い違うか、判断に要る記述がない。ただし、作業の文書が個別に明示した指示と、設計書の一般的な原則が食い違うだけで、安全の性質と、ほかの作業との型の約束に影響しないものは、作業の文書に従って進め、報告の「残したこと」に書く。
- [10-interfaces.md](10-interfaces.md) の型やシグネチャを変える必要がある。
- `unsafe` が要る（`AGENTS.md` の「実装の規約」）。
- 表にない依存のクレートが要る。

## 実装の規約の補足

`AGENTS.md` の「実装の規約」に加えて、次のことを守る。

- 誤りは、モジュールごとの誤りの型（`enum`）で表し、`Result` で返す。`anyhow` などの汎用の誤りのクレートは使わない。
- 利用者に示す英語の文言は、モジュールの `text` の子のモジュールに `pub const` で置く。値を埋める文言は、`text` の関数（`fn not_read(path: &str) -> String` など）にしてよい。
- LLM に見せる文（システムプロンプト、道具の説明、道具の結果の決まった文）は、設計書に英文で書いてあるものは字句を変えずに使う。
- `cfg(target_os = ...)` で OS ごとに分けるときは、その OS でない側でもビルドが通るようにする（`scripts/check.sh` が Linux 向けのクロスビルドも確かめる）。
- 子プロセスを起動するテストと、一時ファイルを作るテストは、テストごとに新しい一時ディレクトリを使い、終わったら消す。

## 検査

`scripts/check.sh` は、完了の前に通す検査（[テスト](../design/07-quality/07-01-testing.md)の「完了の前に通す検査」）をまとめて走らせる（P0-01 で作る）。

- Codex は `scripts/check.sh --inside-codex` を使う。Codex は macOS のサンドボックスの中で動くので、その中では `sandbox-exec` を重ねて掛けられず、Apple の `container` も使えない。`--inside-codex` は、OS のサンドボックスと Linux のコンテナを要するテスト（後述）を走らせず、走らせなかったことを最後に示す。
- オーケストレータは、取り込む前に、サンドボックスの外で `scripts/check.sh`（すべて）を走らせる。失敗すれば、記録を添えて直しを依頼する。

OS のサンドボックスを要するテストは、統合テストのファイルの名前を `tests/sandbox_*.rs` とし、ほかのテストと混ぜない。Linux のコンテナで走らせるテストは、`scripts/check.sh` の `linux` の段（P0-01 で作る）が、Linux 向けにビルドしたテストの実行ファイルを `container` の中で走らせる。

## 完了の報告

最後の応答は、日本語で、次の表と節の形で書く。

| 項目 | 内容 |
|---|---|
| 作業 | ID と題 |
| 結果 | 完了／止まった |
| 変えたファイル | パスの一覧（新しいものに「新」） |
| 検査 | `scripts/check.sh --inside-codex` の結果（通った／失敗した段） |
| 走らせなかったテスト | `--inside-codex` で除いたテストの名前 |

続けて次の節を書く。

- **確かめたこと**: 作業の文書の「確かめること」への答え。一次資料（クレートのソースのパスと版、OS の文書、試した結果）を添える。
- **決めたこと**: 作業の文書が任せた判断と、その理由。
- **残したこと**: 作業の文書の指示と設計書の原則の食い違い、後の作業に回したもの、気付いた問題。
