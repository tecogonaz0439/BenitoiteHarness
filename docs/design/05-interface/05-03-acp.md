# ACP（エディタとの連携）

- 状態: 草稿
- 未決事項: BH-054, BH-055, BH-056, BH-057

## 目的と範囲

本章は、ACP（Agent Client Protocol）に対応するエディタおよび統合画面（T3Code など）から `benitoiteh` を子プロセスとして起動し、標準入出力の上の JSON-RPC 2.0 で対話するためのサブコマンド `benitoiteh acp` の仕様を定める。対象は、信頼の境界、コマンドラインと通信の形、メソッドごとの振る舞い、エージェントのイベントから ACP の通知への変換、実行の前の確認の受け渡し、制限と扱わない機能である。

## 前提

- ACP（Agent Client Protocol）は、エディタやクライアント（Client）とコーディングエージェント（Agent）の間の通信を標準化するプロトコルであり、ローカルの子プロセスとは標準入出力の上の改行区切りの JSON-RPC 2.0（NDJSON）で通信する（<https://agentclientprotocol.com/>、Rust の定義は <https://github.com/agentclientprotocol/agent-client-protocol>）【要検証】（BH-055）。
- T3Code（<https://github.com/pingdotgg/t3code>）は、複数のコーディングエージェントを統合して扱うクライアントであり、ローカルの ACP のコマンド（`Local ACP command`）を子プロセスとして起動して標準入出力で駆動できる（`docs/user/providers-acp.md`、`packages/provider-acp/`）【要検証】（BH-055）。
- `benitoiteh` のエージェントのループ（[エージェントのループ](../01-agent/01-01-agent-loop.md)）は、画面（`ui`）に直接依存せず、チャネル（`SyncSender<AgentEvent>`）でイベントを送り、確認の受け手（`Approver`）を通して利用者の確認を受け、取り消しの印（`RunControl`）で中断を受ける（[クレートの構成](../06-impl/06-01-crate-structure.md)）。
- `benitoiteh` は、非同期の実行時（`tokio` など）を使わず、OS のスレッドと `std::sync::mpsc` のチャネルで組む（[クレートの構成](../06-impl/06-01-crate-structure.md)の「スレッドと非同期」）。公式の `agent-client-protocol` クレートは非同期の実行時を前提とするため使わず、`serde` と `serde_json` の上で ACP の JSON-RPC のメッセージを自前で読み書きする。

## 仕様

### 信頼の境界と安全の原則

【方針】ACP のクライアント（T3Code など）は、利用者が自分の権限で起動して操作するプログラムであり、[セキュリティモデル](../03-safety/03-01-security-model.md)の「利用者」および対話の画面と同じ信頼の側に置く。ただし、[目的と設計原則](../00-overview/00-01-goals.md)の設計原則 1（安全の性質を LLM の出力で崩せないようにする）を守るため、次の規則を掛ける。

- **道具と OS のサンドボックスは `benitoiteh` が実行する**: ACP には、エージェントからクライアントへファイルの読み書き（`fs/*`）や端末のコマンドの実行（`terminal/*`）を委ねる機能があるが、`benitoiteh` はこれらを使わない。すべての道具の実行は `benitoiteh` の主のプロセス（`safe_fs`、読まないファイル、`.bnt` の制限、ハードリンクの検査）と、`benitoiteh` が OS のサンドボックスを掛けて起動する子プロセスで行う。理由: クライアントの側に実行を委ねると、`benitoiteh` の道具のパスの規則、制限モードのエフェクトの照合（`--allow-effects`）、OS のサンドボックス（Seatbelt、bubblewrap と Landlock と seccomp）が掛からず、制限モードの保証 R1〜R5 と通常モードの保証 N1〜N3 が崩れる。
- **確認の事実は `benitoiteh` が組み立てる**: 道具の実行の前に確認が要るときは、`benitoiteh` がクライアントへ `session/request_permission` の要求を送る。要求に載せる操作の題と説明は、`benitoiteh` が確かめた事実（`ApprovalFacts`: 対象のパス、宣言・増加したエフェクトとその意味、OS のサンドボックスが許す書ける場所とネットワークの可否、許すプログラム、コマンドの全文、`.agents` への書き込みの警告）から組み立て、LLM が書いた説明（`justification`）と明確に分けて示す（[利用者の確認](../03-safety/03-03-approval.md)の「確認の共通の規則」）。
- **一回限りの確認をクライアントの応答で広げない**: その一回だけに効く確認（通常モードの `escalate`、`.agents` の下への書き込み、`read` の開かないファイルを取り込むスクリプトとテストの実行、`create_project`、書ける場所の外や守る場所への `write`・`edit`）では、`session/request_permission` の選択肢（`options`）にセッションの間の許可（`allow_always`）を含めない。クライアントが選択肢にない `optionId` や `allow_always` に当たる値を返しても、セッションの間の許可としては記憶せず、選択肢にない `optionId` は拒否（`Denied`）として扱う。
- **セッションの途中でモードを変えない**: クライアントからの設定の変更（`session/set_mode`・`session/set_config_option` など）で、制限モードと通常モードを切り替えることは許さない（[セキュリティモデル](../03-safety/03-01-security-model.md)の「モードを変える操作」）。モードは `benitoiteh acp` を起動するときのオプション（`--mode`）か利用者の設定ファイルの `default_mode` で決める。
- **外部の MCP サーバを取り込まない**: クライアントが `session/new` や `session/load` の `mcpServers` に MCP サーバの設定を渡しても、`benitoiteh` は接続せず、道具の一覧にも加えない。`mcpServers` が空でないときは、MCP を使わないことをクライアントへの通知（または標準エラー出力の診断）で示す。理由: 外部の MCP サーバの道具は Benitoite の型とエフェクトの検査を通らず、制限モードの性質を崩す（[目的と設計原則](../00-overview/00-01-goals.md)の「範囲」、BH-116）。

### コマンドラインと入出力

【方針】サブコマンドの形は次のとおりとする（[CLI と設定ファイル](05-01-cli.md)の「コマンドラインの形」）。

```text
benitoiteh acp [オプション]
```

- 受け付けるオプションは、`--mode`、`--project`、`--provider`、`--model`、`--effort`、`--sandbox`、`--approval`、`--allow`、`--trust-project`、`--allow-agents-write`、`--project-parent`、`--max-turns`、`--max-check-fix`、`--max-run-tokens`、`--ephemeral`、`--no-sandbox` とする。
- 標準入力と標準出力が端末であることは求めない（クライアントがパイプでつなぐため）。`--json`、`--output-last-message`、`--output-schema`、`--resume`、`--continue`、位置引数の `<依頼>` は、ACP のメッセージと役割が重なるため使い方の誤り（終了状態 2）とする。
- 標準出力には、ACP の JSON-RPC 2.0 のメッセージ（1 メッセージ 1 行の UTF-8 の JSON と `\n`）だけを書く。起動のときの診断や、JSON-RPC になる前の誤りは標準エラー出力に書く。標準エラー出力に書く文字列は、[対話の画面](05-02-tui.md)の「出力の示し方」と同じく、端末の制御の文字を目に見える形に変える。
- 標準入力が閉じられた（EOF）ときは、実行中の一連の処理があれば取り消し（[エージェントのループ](../01-agent/01-01-agent-loop.md)の「取り消し」と同じく子プロセスの後始末を行う）、セッションを閉じて終了状態 0 で終わる。

### スレッドの構成

【方針】`benitoiteh acp` は、非同期の実行時を使わず、次のスレッドで動く（[クレートの構成](../06-impl/06-01-crate-structure.md)の「スレッドと非同期」）。

| スレッド | 働き |
|---|---|
| 入力の読み取りのスレッド | 標準入力から 1 行ずつ JSON-RPC のメッセージを読み、クライアントからの要求・通知と、`session/request_permission` に対するクライアントの応答を振り分けてチャネルへ送る |
| 主のスレッド | セッションの準備、要求の振り分け、`session/cancel` による取り消しの印の設定、`AgentEvent` から `session/update` への変換を行う |
| エージェントのスレッド | `Agent::run_controlled`（および圧縮などの操作）を動かす。確認が要るときは `AcpApprover` を通してクライアントへ `session/request_permission` を送り、応答を待つ |

- 標準出力への書き込みは、一つの錠（`Mutex`）で排他し、1 行ごとに `flush` する。理由: 主のスレッドが送る `session/update` の通知と、エージェントのスレッド（`AcpApprover`）が送る `session/request_permission` の要求の行が混ざらないようにする。
- 【方針】一つの `benitoiteh acp` のプロセスが同時に持つアクティブなセッションは一つとし、同時に動かす `session/prompt`（一連の処理）も一つとする（BH-056）。新しい `session/new` または `session/load` を受けたときは、実行中の一連の処理がなければ前のセッションを閉じて新しいセッションに切り替え、実行中なら JSON-RPC の誤りを返す。理由: Linux の塞ぐ場所の錠、子プロセスの起動の錠、セッションごとの一時ディレクトリと状態の管理を、TUI の `/new` と同じ単純な形に保つ。

### メソッドの対応

【方針】ACP の版 1（`protocolVersion: 1`）を基本とし、T3Code が使うメソッドと欄に対応する【要検証】（BH-055）。知らないメソッドの要求には、JSON-RPC 2.0 の `Method not found`（`-32601`）を返す。

| メソッド | 向き | 種別 | 働き |
|---|---|---|---|
| `initialize` | Client → Agent | 要求 | プロトコルの版、エージェントの情報（`name: "benitoiteh"`、`version`）、機能（`loadSession: true`、画像の入力の可否など）を返す |
| `authenticate` | Client → Agent | 要求 | 選んだ提供者の認証の情報（環境変数の API キー、または `benitoiteh login chatgpt` で保存したトークン）が使えるかを確かめて返す |
| `session/new` | Client → Agent | 要求 | 指定された作業ディレクトリ（`cwd`。なければ `--project` またはプロセスの作業ディレクトリ）で起動の準備（`exec::prepare` に当たる検査）を行い、新しいセッションを作って `sessionId` と現在の設定の選択肢（モデルと推論の度合い）を返す |
| `session/load` | Client → Agent | 要求 | 指定された `sessionId` の記録を開いて再開の準備を行い、保存された会話を `session/update` で送ってから完了を返す |
| `session/prompt` | Client → Agent | 要求 | 利用者の依頼（文と添付の画像）を受け取り、一連の処理を走らせる。途中の経過は `session/update` で送り、終わったら `stopReason` を返す |
| `session/cancel` | Client → Agent | 通知（または要求） | 実行中の一連の処理を取り消す。`RunControl` の `cancel_step` と `cancel_run` を立て、確認を待っている `AcpApprover` があれば `Cancelled` で起こす |
| `session/set_config_option` | Client → Agent | 要求 | 同じ提供者の設定の中で、モデルまたは推論の度合い（`effort`）を替える（[対話の画面](05-02-tui.md)の `/model` と同じ規則）。モードの変更は拒む |
| `session/update` | Agent → Client | 通知 | エージェントのループのイベント（文と推論の差分、道具の呼び出しと結果、使ったトークンの量など）を送る |
| `session/request_permission` | Agent → Client | 要求 | 道具の実行の前の確認（および通常モードの通信の中継の確認）をクライアントに求め、選ばれた選択肢を受け取る |

### 起動とセッションの準備の確認

【方針】`session/new` と `session/load` でセッションを準備するときに、TUI では起動の確認の画面で尋ねる三つの項目（プロジェクトの信頼、制限モードでの処理系の実行ファイルの SHA-256 の変化、制限モードの記録を通常モードで再開するときの確認）は、既定では非対話（`exec`）と同じ規則で扱う【未決】（BH-054）。

- **プロジェクトの信頼**（[セキュリティモデル](../03-safety/03-01-security-model.md)の「プロジェクトの信頼」）: 保存された信頼の決定を使い、決定がないか信頼を要する置き場所が増えたときは、`--trust-project` を付けて起動したときだけ信頼し、そうでなければ信頼しない（プロジェクトの Skill・プラグイン・雛形・設定の `model` を読まず、その旨を診断として通知する）。
- **制限モードでの処理系の変化**（[セキュリティモデル](../03-safety/03-01-security-model.md)の「保証しないこと」、BH-099）: 前のセッションの記録から処理系の SHA-256 が変わっていたら、制限モードでは `session/new`・`session/load` を誤りとして拒む。通常モードでは警告を通知して続ける。
- **モードを変えての再開**（[セキュリティモデル](../03-safety/03-01-security-model.md)の「モードを変える操作」）: 制限モードで記録したセッションを通常モードの `benitoiteh acp` で `session/load` しようとしたときは、誤りとして拒む。

理由: ACP では `session/request_permission` が `session/prompt` の実行中（`toolCall` に紐付く確認）を前提としており、`session/new` や `session/load` の途中で確認のダイアログを出せないクライアントがある【要検証】（BH-054、BH-055）。最初の `session/prompt` の直前に `session/request_permission` で尋ねる代わりの案（案 B）は BH-054 で検討する。

### 依頼の受け取りと終わりの理由

【方針】`session/prompt` の `prompt` の配列からは、次の要素を受け取る【要検証】（BH-055）。

- 文の要素（`type: "text"`）と、クライアントが添えたファイルや選択範囲の要素（`type: "resource"` など）は、順序を保って一つの依頼の文字列にまとめる。クライアントが添えたパスの参照のうち、中身を含まないものはパスの文字として渡し、中身を読むときは LLM が `read` の道具で読む（読まないファイルの規則を通すため）。
- 画像の要素（`type: "image"`）または画像のパスが添えられたときは、[対話の画面](05-02-tui.md)の「入力の操作」の画像の添付と同じく、`read` の道具と同じ規則（範囲、読まないファイル、補助のプロセス `benitoiteh __image` による縮小、`objects/` への保存、送る画像の上限）を通す。一つでも読めなければ、提供者へ要求を送らずに誤りを返す。
- 一連の処理が終わったときの `Outcome` と `AgentError` は、ACP の `stopReason` に次のように対応させる【要検証】（BH-055）。
  - `Outcome::Completed`: `"end_turn"`
  - `Outcome::Cancelled`: `"cancelled"`
  - `AgentError::Limit`（番の数またはトークンの量の上限）: `"max_turn_requests"`（または `"max_tokens"`）
  - そのほかの `Outcome::Failed` と `AgentError`: JSON-RPC の誤りの応答（秘密と提供者の生の本文を含まない診断の文）を返す。

### イベントから `session/update` への変換

【方針】[エージェントのループ](../01-agent/01-01-agent-loop.md)の「イベント」（`AgentEvent`）を、次のとおり ACP の `session/update` の通知に変えて送る【要検証】（BH-055）。

| `AgentEvent` | ACP の `sessionUpdate` | 送る内容 |
|---|---|---|
| `SessionStart { notice, .. }` | エージェントの通知（または最初のメタデータ） | 送り先の提供者・モデル・ホストと、読んだ Skill・指示のファイルの診断 |
| `TextDelta { text, .. }` | `"agent_message_chunk"` | `{ "content": { "type": "text", "text": text } }` |
| `ReasoningDelta { text, .. }` | `"agent_thought_chunk"` | `{ "content": { "type": "text", "text": text } }` |
| `ToolCall { call_id, name, arguments, .. }` | `"tool_call"` | `toolCallId` に `call_id`、`title` に道具の呼び出しの一行の要約、`kind` に道具の分類（`read`・`glob`・`grep`・`benitoite_reference`・`benitoite_explain` は `"read"` または `"search"`、`write`・`edit`・`create_project` は `"edit"`、`benitoite_check`・`benitoite_run`・`benitoite_test`・`benitoite_scratch`・`bash` は `"execute"`、`web_fetch` は `"fetch"`）、`status` に `"in_progress"`、`rawInput` に `arguments` |
| `ToolResult { call_id, is_error, summary, screen, display, .. }` | `"tool_call_update"` | `toolCallId` に `call_id`、`status` に `is_error` が偽なら `"completed"`、真なら `"failed"`。内容には、`write`・`edit` の差分（`display`）または出力（`screen` と `summary`）を載せる |
| `TurnEnd { usage, .. }` | `"usage_update"`（対応する版） | 使ったトークンの量と文脈の見積もり |
| `Compaction { .. }` | 状態の通知 | 圧縮が行われたことと、要約した項目の数 |
| `Error { message, .. }` | 診断の通知 | 秘密を含まない誤りの文 |

### 実行の前の確認（`session/request_permission`）

【方針】ACP の起動では、承認の方針の既定を対話と同じ（制限モードは実行の前の確認を行い、通常モードは `--approval` または利用者の設定の `normal.approval`、既定 `on-request`）とし、`Approver` トレイトを実装する `AcpApprover` を使う。`--approval never`（または非対話の `--allow` だけの運用）を指定したときは、クライアントへ尋ねずに方針に従って判定する。

`AcpApprover::approve` は、確認の要求（`ApprovalRecord`）を受けたら、次の手順でクライアントへ `session/request_permission` を送る。

1. **事実の組み立て**: [対話の画面](05-02-tui.md)の「確認の画面」と同じく、`ApprovalRecord` の `facts` から、`benitoiteh` が確かめたすべての事実（対象のスクリプトのパス、増えたエフェクトに `+` を付けたエフェクトの一覧と同梱の Skill の説明、OS のサンドボックスの書ける場所とネットワークの可否、`Process.Run` のときの許すプログラムと注意、`Process.shell` の参照の有無、`.agents` への書き込みの注意、`read` の開かないファイルの取り込みの件数、通常モードのコマンドの全文と作業ディレクトリ、長い空白の `␠×N` の可視化、制御の文字の可視化）を組み立てる。LLM の `justification` があるときは、事実より前に行の数を限って（10 行まで）事実と区別する見出しを付けて置く。
2. **選択肢（`options`）の決定**: 確認の種類に応じて、クライアントに示す選択肢を決める。
   - **その一回だけ許す確認**: `ApprovalKind::Escalate`、`ApprovalKind::CreateProject`、`ApprovalKind::WriteScope`、`facts.agents_write` が真のとき、`facts.unread_imports > 0` のとき。選択肢は `allow_once`（今回だけ許可する）と `reject_once`（拒否する）の二つだけとする。
   - **セッションの間の許可を兼ねる、または選べる確認**:
     - 制限モードの `ApprovalKind::Effects` と `ApprovalKind::TestEffects`（`agents_write` が偽で `unread_imports == 0` のとき）は、[利用者の確認](../03-safety/03-03-approval.md)の「制限モードの確認」のとおり、許可するとその対象について確認したエフェクトの範囲をセッションの間覚える。選択肢の文言に「このセッションの間、この対象にこれらのエフェクトを許す」ことを明示する。
     - 通常モードの `untrusted` の `ApprovalKind::Command` と、`ApprovalKind::WebFetch`・`ApprovalKind::Network` は、`allow_once`（今回だけ許す）、`allow_always`（このセッションの間、同じコマンドまたは同じドメインを許す）、`reject_once`（拒否する）の三つとする。
3. **応答の判定**:
   - クライアントが提示した選択肢の中の `optionId` を返したら、対応する `ApprovalOutcome`（`Approved`、`ApprovedForSession`、`Denied`）を返す。
   - クライアントが提示していない `optionId` を返したとき、または形式が合わないときは、`ApprovalOutcome::Denied` とする。
   - クライアントが `cancelled` を返したとき、`session/cancel` が届いたとき、または標準入力が閉じたときは、`ApprovalOutcome::Cancelled` とする。
   - ACP の `session/request_permission` の応答には利用者が拒否の理由の文を添える欄がないため、`DeniedWithMessage` は使わず `Denied` とする。

### 通信の中継と秘密の入力の扱い

【方針】（BH-057）

- **通常モードの通信の中継**（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「通信の中継」）: `normal.network = "proxy"` で、許していないドメインへの接続がコマンドの実行の途中に起きたときは、TUI と同じチャネルを通して `AcpApprover` に `ApprovalKind::Network` の確認を送り、`session/request_permission` でクライアントに尋ねる。承認の方針が `never` のときは尋ねずに断る。
- **秘密の入力の仲介**（[秘密の入力](../03-safety/03-04-secrets.md)の「段 2: `benitoiteh` が秘密の入力を仲介する」）: `SSH_ASKPASS`・`GIT_ASKPASS`・`SUDO_ASKPASS` の仲介は、利用者が伏せ字でパスワードを入力する専用の欄を要し、秘密をログや通常のメッセージに載せない規則である。ACP の `session/request_permission` は選択肢の選択だけであり、秘密の文字列を安全に受け取る口を持たないため、`benitoiteh acp` では `askpass` の仲介を無効（非対話の `exec` と同じ扱い）とする。

### 巻き戻しとセッションの木

【方針】`benitoiteh acp` でも、セッションの記録（`session.jsonl`）、切り詰めた出力（`spill/`）、巻き戻しの記録（`objects/` と時点の一覧）は、TUI と同じく記録する（`--ephemeral` を付けたときを除く）。これにより、`benitoiteh acp` で行ったセッションを後で `benitoiteh --resume <ID>` で開いて `/rewind`・`/tree`・`/fork` を使うことも、TUI で行ったセッションを `benitoiteh acp` の `session/load` で再開することもできる。ACP の上に巻き戻しや枝の移動の独自のメソッドを足すかは、ACP の仕様の側の対応を見て決める【要検証】（BH-055）。
