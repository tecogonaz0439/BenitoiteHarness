# ACP（エディタとの連携）

- 状態: 草稿
- 未決事項: BH-054, BH-055, BH-056, BH-057

## 目的と範囲

本章は、ACP（Agent Client Protocol）に対応するエディタおよび統合画面（T3Code など）から `benitoiteh` を子プロセスとして起動し、標準入出力の上の JSON-RPC 2.0 で対話するためのサブコマンド `benitoiteh acp` の仕様を定める。対象は、信頼の境界と安全の原則、コマンドラインと通信の形、スレッドと終了の手順、ACP 版 1 のメソッドごとの契約、イベントと終了理由の変換、実行の前の確認の選択肢と表示の契約、通信の中継と秘密の入力の扱いである。

## 前提

- ACP（Agent Client Protocol）は、エディタや統合画面（Client）とコーディングエージェント（Agent）の間の通信を標準化するプロトコルであり、ローカルの子プロセスとは標準入出力の上の改行区切りの JSON-RPC 2.0（NDJSON）で通信する（<https://agentclientprotocol.com/>、仕様とスキーマは <https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`）。
- T3Code（<https://github.com/pingdotgg/t3code>、コミット `d5f8a7573a3817d8c20f7491e7672443355c4083`）は、複数のコーディングエージェントを統合して扱うクライアントであり、ローカルの ACP のコマンド（`Local ACP command`）を子プロセスとして起動して標準入出力で駆動できる（`docs/user/providers-acp.md`、`packages/provider-acp/`）。
- `benitoiteh` のエージェントのループ（[エージェントのループ](../01-agent/01-01-agent-loop.md)）は、画面（`ui`）に直接依存せず、チャネル（`SyncSender<AgentEvent>`）でイベントを送り、確認の受け手（`Approver`）を通して利用者の確認を受け、取り消しの印（`RunControl`）で中断を受ける（[クレートの構成](../06-impl/06-01-crate-structure.md)）。
- `benitoiteh` は、非同期の実行時や非同期の抽象（`tokio`・`futures` など）を使わず、OS のスレッドと `std::sync::mpsc` のチャネルによる同期 I/O で組む（[クレートの構成](../06-impl/06-01-crate-structure.md)の「スレッドと非同期」）。公式の Rust SDK `agent-client-protocol`（5.4.0。<https://github.com/agentclientprotocol/rust-sdk> のコミット `8ac65cf6b0b3371ae4d8231760cb91dad99e92ef` の `Cargo.toml`）は `futures` などの非同期の抽象を通常の依存に持つため使わず、`serde` と `serde_json` の上で ACP 版 1 の JSON-RPC メッセージを自前で読み書きする。自前の送受信の形は、固定した公式の版 1 のスキーマから作った通信例との照合で検証する（[テスト](../07-quality/07-01-testing.md)の「持ち主の境界」）。

## 仕様

### 信頼の境界と安全の原則

【方針】ACP のクライアント（T3Code など）は、利用者が自分の権限で起動して操作するプログラムであり、[セキュリティモデル](../03-safety/03-01-security-model.md)の「利用者」および対話の画面と同じ信頼の側に置く。ただし、[目的と設計原則](../00-overview/00-01-goals.md)の設計原則 1（安全の性質を LLM の出力で崩せないようにする）を守るため、次の規則を掛ける。

- **道具と OS のサンドボックスは `benitoiteh` が実行する**: ACP には、エージェントからクライアントへファイルの読み書き（`fs/*`）や端末のコマンドの実行（`terminal/*`）を委ねる機能があるが、`benitoiteh` はこれらを使わない。すべての道具の実行は `benitoiteh` の主のプロセス（`safe_fs`、読まないファイル、`.bnt` の制限、ハードリンクの検査）と、`benitoiteh` が OS のサンドボックスを掛けて起動する子プロセスで行う。理由: クライアントの側に実行を委ねると、`benitoiteh` の道具のパスの規則、制限モードのエフェクトの照合（`--allow-effects`）、OS のサンドボックス（Seatbelt、bubblewrap と Landlock と seccomp）が掛からず、制限モードの保証 R1〜R5 と通常モードの保証 N1〜N3 が崩れる。
- **MCP を利用しない ACP 版 1 の限定対応と、クライアントの MCP 資格情報の隔離**: ACP 版 1 の仕様はすべての Agent に stdio の MCP 接続への対応を求めている（<https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`）が、`benitoiteh` は外部の MCP サーバの道具が型とエフェクトの検査を通らないため MCP を使わない（[目的と設計原則](../00-overview/00-01-goals.md)の「範囲」、BH-116）。T3Code は `session/new`・`session/load` の `mcpServers` に自前の MCP bridge を渡す（`packages/provider-acp/` の `AcpSessionRuntime.ts`）ため、非空の `mcpServers` を要求の誤りとしては拒まず、接続も道具の追加も行わずに無視したことを一度だけ診断として示す。このとき、次の二つの隔離を必ず掛ける。
  1. **子プロセスの環境からの強制除外**: T3Code は ACP エージェントの起動環境に、T3Code 本体の MCP HTTP サーバ（worktree の作成と setup script の起動などの権限を持つ）へ接続するための資格情報と設定（`T3_ACP_MCP_ENDPOINT`、`T3_ACP_MCP_AUTHORIZATION`、`T3_ACP_MCP_NODE`、`T3_ACP_MCP_ENTRYPOINT`、`T3CODE_THREAD_ID` などの `T3_ACP_MCP_*` および `T3CODE_*`。<https://github.com/pingdotgg/t3code> のコミット `d5f8a7573a3817d8c20f7491e7672443355c4083` の `packages/provider-acp/`）を渡す。`benitoiteh` は、これらの変数（`T3_ACP_MCP_*` と `T3CODE_*`）を、提供者のキーと同じく、[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「規則の後に必ず当てる変更」で子プロセスの環境から必ず除き、環境の規則の `set` や `*` を含まない `allow` で指定することも拒む。理由: 制限モードで `Process.Environment` と `Http.Connect` を確認したスクリプトや、通常モードの子プロセスがこれらの資格情報を読んで T3Code の MCP 接続先を直接呼び、`benitoiteh` の `safe_fs` とサンドボックスを通らない操作を T3Code 本体に行わせる道を塞ぐ。
  2. **記録と診断からの秘匿**: `session/new`・`session/load` で受け取った `mcpServers` の中身（`env`、HTTP ヘッダ、コマンド、引数、URL）と起動環境の `T3_ACP_MCP_*`・`T3CODE_*` の値は、診断の通知、標準エラー出力、セッションの記録（`session.jsonl`）のどれにも書かず、無視した `mcpServers` の件数だけを示す。
- **確認の事実の表示とクライアントの自動承認の扱い**:
  - 道具の実行の前に確認が要るときは、`benitoiteh` がクライアントへ `session/request_permission` の要求を送る。要求には `benitoiteh` が確かめたすべての事実（`ApprovalFacts`）を、クライアントの承認画面で省略されずに表示される欄に載せる（後述の「実行の前の確認（`session/request_permission`）」）。
  - ACP の `session/request_permission` の応答（`outcome: "selected"`）には、人間がその都度画面を見て押したことと、クライアントが自身の方針で自動承認したことを区別する欄がない。T3Code はスレッドの承認方針（`packages/provider-acp/src/server/clientPolicy.ts` と `adapter.ts`）に応じて、`auto-accept-edits` や `Full access` のときに一部の確認要求へ確認画面を出さずに `allow_once`（なければ `allow_always`）を自動で返す。したがって、制限モードの R3（実行の前の確認）、通常モードの N2（範囲の外の操作の確認）、`.agents` への書き込みの毎回の確認を、人間による確認として成り立たせるには、**クライアントの側で自動承認を行わない設定（T3Code の Supervised 相当）で使うこと**を対応の前提条件とする（[利用者の確認](../03-safety/03-03-approval.md)の「確認の共通の規則」）。
- **一回限りの確認をクライアントの応答で広げない**: その一回だけに効く確認（通常モードの `escalate`、`.agents` の下への書き込み、`read` の開かないファイルを取り込むスクリプトとテストの実行、`create_project`、書ける場所の外や守る場所への `write`・`edit`）では、`session/request_permission` の選択肢（`options`）にセッションの間の許可（`allow_always`）を含めない。クライアントが選択肢にない `optionId`、重複した応答、または終わった呼び出しへの遅れた応答を返したときは、どの許可も広げず、選択肢にない `optionId` は拒否（`Denied`）として扱う。
- **セッションの途中でモードを変えない**: クライアントには制限モードと通常モードを切り替える `modes` を広告せず、`session/set_mode` は未対応（`-32601`）とし、`session/set_config_option` でもモードの変更は受け付けない（[セキュリティモデル](../03-safety/03-01-security-model.md)の「モードを変える操作」）。モードは `benitoiteh acp` を起動するときのオプション（`--mode`）か利用者の設定ファイルの `default_mode` で決める。

### コマンドラインと入出力

【方針】サブコマンドの形は次のとおりとする（[CLI と設定ファイル](05-01-cli.md)の「コマンドラインの形」）。

```text
benitoiteh acp [オプション]
```

- 受け付けるオプションは、`--mode`、`--project`、`--provider`、`--model`、`--effort`、`--sandbox`、`--approval`、`--allow`、`--trust-project`、`--allow-agents-write`、`--project-parent`、`--max-turns`、`--max-check-fix`、`--max-run-tokens`、`--ephemeral`、`--no-sandbox` とする。
- 標準入力と標準出力が端末であることは求めない（クライアントがパイプでつなぐため）。`--json`、`--output-last-message`、`--output-schema`、`--resume`、`--continue`、位置引数の `<依頼>` は、ACP のメッセージと役割が重なるため使い方の誤り（終了状態 2）とする。
- 標準出力には、ACP の JSON-RPC 2.0 のメッセージ（1 メッセージ 1 行の UTF-8 の JSON と `\n`）だけを書く。起動のときの診断や、JSON-RPC になる前の誤りは標準エラー出力に書く。標準エラー出力に書く文字列は、[対話の画面](05-02-tui.md)の「出力の示し方」と同じく、端末の制御の文字を目に見える形に変える。

### スレッドの構成と終了の手順

【方針】`benitoiteh acp` は、次のスレッドで動く（[クレートの構成](../06-impl/06-01-crate-structure.md)の「スレッドと非同期」）。

| スレッド | 働き |
|---|---|
| 入力の読み取りのスレッド | 標準入力から 1 行ずつ（1 行の上限は 16 MiB）JSON-RPC のメッセージを読み、クライアントからの要求・通知と、`session/request_permission` に対するクライアントの応答を振り分けて主のスレッドのチャネルへ送る |
| 出力の書き込みのスレッド | 主のスレッドから渡された JSON-RPC の応答・通知・確認の要求を標準出力へ 1 行ずつ書き、1 行ごとに `flush` する。書き込みまたは `flush` が失敗したら、出力の障害の印を立てて主のスレッドへ知らせ、以降の出力を捨てる |
| 主のスレッド | セッションの準備、要求の振り分け、確認の要求の台帳の管理、`session/cancel` と切断の処理、`AgentEvent` から `session/update` への変換を行う |
| エージェントのスレッド | `Agent::run_controlled` を動かす。確認が要るときは `AcpApprover`（および `NetworkGate`）から主のスレッドへ確認を依頼し、返事のチャネルで待つ |

【方針】取り消し（`session/cancel`）、標準入力の終了（EOF）、標準出力の書き込みの障害が起きたときは、デッドロックと子プロセスの残りを防ぐため、次の状態遷移の順で処理する。

1. **新しい受付の停止**: 取り消しまたは切断（EOF・出力の障害）を確定したら、その一連の処理（切断のときはプロセス全体）について新しい仕事と新しい確認の要求の受付を止める。
2. **取り消しの設定と保留中の確認の解除**: 実行中の `RunControl` の `cancel_step` と `cancel_run` を `true` にする。主のスレッドが持つ保留中の確認の台帳（通常の道具の確認と通信の中継の確認の両方）をすべて `ApprovalOutcome::Cancelled` で即時に完了させ、返事を待っている `AcpApprover` と `ProxyRun::decide` のスレッドを起こす。出力のスレッドにまだ書かれていない確認の要求があっても、主のスレッドが台帳から外して待ち手を起こすので、出力の滞留で確認の解除は止まらない。
3. **終了を待つ間のイベントの回収**: 子プロセス（`SIGINT`/`SIGTERM` から 10 秒後の `SIGKILL` まで）とエージェントのスレッドが終わるのを待つ間も、主のスレッドは `AgentEvent` の上限付きチャネル（長さ 64）からイベントを受け取り続ける。理由: イベントの受け取りを先に止めてスレッドの `join` を待つと、`Agent::emit` が満杯のチャネルへの送信で止まり、終了できなくなる。接続が生きている `session/cancel` では受け取ったイベントを `session/update` として出力へ送り、EOF または出力の障害の後は受け取ったイベントを読み捨てる。
4. **完了の回収と応答**: エージェントのスレッドの完了を受け取り、チャネルに残ったすべてのイベントを抜き終えてから（TUI の `Worker::drain` と `Worker::close` と同じ順序）、一連の処理を終える。接続が生きている `session/cancel` では、最後の `session/update` を送り終えた後に、元の `session/prompt` の要求に対して一度だけ `result: { "stopReason": "cancelled" }` を返す（ACP 版 1 の取消の仕様に従い、取消の後に下位の処理が誤りを返したときも `"cancelled"` とする）。
5. **プロセスの終了**: 標準入力の EOF または標準出力の障害でプロセスを終えるときは、3 と 4 の後始末（子プロセスの停止とセッションの記録の書き出し）を終えた後に終了する。出力の障害で標準入力がまだ開いているときは、`stdin` の読み取りのスレッドがブロッキングの読み取りで止まっているため、無期限に `join` を待たずにプロセスを終える。

### セッションの多重度

【方針】一つの `benitoiteh acp` のプロセスが同時に持つアクティブなセッションは一つとし、同時に動かす `session/prompt`（一連の処理）も一つとする（BH-056 の案 A）。

- `session/prompt` の実行中に新しい `session/prompt`、`session/new`、`session/load` を受けたときは、JSON-RPC の誤りを返す。
- 一連の処理が動いていないときに新しい `session/new` または `session/load` を受けたときは、前のセッションの記録と一時ディレクトリを閉じて（記録は残すので後から `session/load` で再開できる）、新しいセッションをアクティブにする。切り替えのときに、前のセッションの確認の台帳や許可の記憶を新しいセッションへ引き継がない。
- アクティブなセッションの `sessionId` と一致しない `sessionId` を指定した `session/prompt`・`session/cancel`・`session/set_config_option` は、JSON-RPC の `Invalid params`（`-32602`）で拒む。

理由: T3Code の一般の ACP の経路（`packages/provider-acp/` の `AcpSessionRuntime.ts` の `startTurnUnlocked`）は、同じ実行器に進行中の番があれば新しい番を拒み、別のセッションが要るときはセッションを切り替え直す作りである。1 プロセスで同時に 1 セッションをアクティブにする形なら、Linux の塞ぐ場所の錠、子プロセスの起動の錠、作業ディレクトリと設定の管理を TUI の `/new` と同じ単純な形に保てる。複数スレッドでの切り替えの動作は統合試験で確かめる【要検証】（BH-055）。

### ACP 版 1 のメソッドと通信の契約

【方針】初版が対応する通信の形式は **ACP 版 1（`protocolVersion: 1`）** に固定する（BH-055）。

- クライアントが `initialize` で `protocolVersion: 2`（および版 2 用の追加の欄）を送ってきたときも、未知の欄があることでは拒まず、`result.protocolVersion` に `1` を返して版 1 として交渉する。以後は版 1 のメソッドとデータの形だけを使う。版 2 への対応は別の作業とする。理由: ACP の移行の仕様と T3Code のクライアント実装（`effect-acp/src/client.ts`）は、版 2 を要求したクライアントがエージェントから `protocolVersion: 1` の応答を受けて版 1 として通信を続ける交渉を認めている（<https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`、<https://github.com/pingdotgg/t3code> のコミット `d5f8a7573a3817d8c20f7491e7672443355c4083`）。
- JSON-RPC 2.0 の規則に従い、要求の `id`（数値または文字列）は型と値をそのまま応答に保ち、知らないメソッドの**要求**（`id` があるもの）には `Method not found`（`-32601`）を返し、知らないメソッドの**通知**（`id` がないもの）には応答を返さない。

各メソッドの要求の `params` と応答の `result` は、ACP 版 1 のスキーマに従い次のとおりとする。

| メソッド | 向き | 種別 | 要求の主な `params` | 正常時の `result` |
|---|---|---|---|---|
| `initialize` | Client → Agent | 要求 | `protocolVersion`（必須）。`clientCapabilities`・`clientInfo`（任意） | `protocolVersion: 1`、`agentInfo: { "name": "benitoiteh", "version": "<版>" }`、`agentCapabilities: { "loadSession": true, "promptCapabilities": { "image": <image_input>, "embeddedContext": true } }`、`authMethods` |
| `authenticate` | Client → Agent | 要求 | `methodId`（広告した認証の方法の ID） | `{}`（選んだ提供者の API キーまたは保存済みの ChatGPT のトークンが使えることを確かめる。使えなければ誤りを返す） |
| `session/new` | Client → Agent | 要求 | `cwd`（必須。絶対パス）、`mcpServers`（必須。配列） | `{ "sessionId": "<ID>", "configOptions": [...] }`。`cwd` が欠けているか相対パスのときは `Invalid params`（`-32602`）とする |
| `session/load` | Client → Agent | 要求 | `sessionId`（必須）、`cwd`（必須。絶対パス）、`mcpServers`（必須。配列） | 保存された会話を `session/update` で順に送り終えた後に、`{ "configOptions": [...] }` を返す。記録のプロジェクトの実のパスと `cwd` の実のパスが一致しないときは誤りとする |
| `session/prompt` | Client → Agent | 要求 | `sessionId`（必須）、`prompt`（必須。`ContentBlock` の配列） | 一連の処理が終わり、すべての `session/update` を送り終えた後に、`{ "stopReason": "<理由>" }` を返す |
| `session/cancel` | Client → Agent | 通知 | `sessionId`（必須）。JSON-RPC の `id` を持たない通知（もし `id` 付きの要求として届いたときは、取り消しを発動したうえで `{}` を返す） | 通知には応答を返さない。実行中の `session/prompt` の側が `"stopReason": "cancelled"` で終わる |
| `session/set_config_option` | Client → Agent | 要求 | `sessionId`、`configId`（`"model"` または `"effort"`）、`value` | 同じ提供者の設定の中でモデルまたは推論の度合い（`effort`）を切り替え（[対話の画面](05-02-tui.md)の `/model` と同じ規則）、変更後の全 `configOptions`（`{ "configOptions": [...] }`）を返す |
| `session/update` | Agent → Client | 通知 | `sessionId`、`update`（`sessionUpdate` をタグとするオブジェクト） | 通知なので応答なし |
| `session/request_permission` | Agent → Client | 要求 | `sessionId`、`toolCall`（`ToolCallUpdate` の形）、`options`（`PermissionOption` の配列） | `{ "outcome": { "outcome": "selected", "optionId": "<ID>" } }` または `{ "outcome": { "outcome": "cancelled" } }` |

- **`configOptions` の形**: `session/new`・`session/load`・`session/set_config_option` が返す `configOptions` には、`type: "select"` の項目として、現在のモデル（`id: "model"`、`category: "model"`）と推論の度合い（`id: "effort"`、`category: "thought_level"`。提供者が持つときだけ）を載せる。制限モードと通常モードを選ぶ `modes` は返さず、`session/set_mode` は `-32601`（`Method not found`）とする。
- **`session/load` の履歴の再送**: 保存されたセッションの今の枝の会話を、利用者の発言（`user_message_chunk`）、推論の文（`agent_thought_chunk`）、応答の文（`agent_message_chunk`）、道具の呼び出しと結果（`tool_call` と `tool_call_update`）として順に `session/update` で送ってから、`session/load` の応答を返す。過去の記録にある承認の記録からは、今のセッションの許可（確認したエフェクト、コマンド、ドメイン）を復元しない（[セッション](../01-agent/01-05-sessions.md)の「再開」と同じ規則）。

### 起動とセッションの準備の方針の分離

【方針】これまで `ExecArgs.interactive` の一つの真偽値でまとめて切り替えていた準備の方針（`crates/benitoiteh/src/cli/exec.rs` と `src/agent/mod.rs`）を、次の五つの独立した項目に分ける。`tui`・`exec`・`acp` の各入口が選ぶ組み合わせは次の表のとおりとする（BH-054 の案 A、BH-057）。

| 方針の項目 | `tui`（対話の画面） | `exec`（非対話） | `acp`（ACP エージェント） |
|---|---|---|---|
| 1. 起動・再開時の確認（プロジェクトの信頼、制限モードでの処理系の SHA-256 の変化、制限モードから通常モードへの再開） | 画面で確認を受ける | 保存済みの信頼か `--trust-project` に従う。制限モードの処理系の変化とモード変更の再開は拒む | `exec` と同じ（保存済みの信頼か `--trust-project` に従い、制限モードの処理系の変化とモード変更の再開は拒む） |
| 2. 実行時の承認の方針の既定と受け手 | 制限モードは確認あり、通常モードは設定値（既定 `on-request`）。`InteractiveApprover` | 制限モードは `--allow`、通常モードは `never`。`NonInteractiveApprover` | 制限モードは確認あり、通常モードは `--approval` または設定値（既定 `on-request`）。`AcpApprover`（`--approval never` または `--allow` 指定時は事前許可の範囲だけで判定） |
| 3. `--allow`・`--allow-agents-write`・`--project-parent` | 使い方の誤り | 受け付ける | 受け付ける。`--allow` を指定した制限モードでは、その範囲に収まる実行を確認なしに許し、超える分は `--approval never` でなければ `AcpApprover` で尋ねる |
| 4. 通常モードの通信の中継（`network = "proxy"`）の未許可ドメインの確認 | 承認の方針が `never` でなければ画面で尋ねる | 尋ねずに断る | 承認の方針が `never` でなければ `AcpApprover` と同じ確認の台帳を通して `session/request_permission` で尋ねる |
| 5. 秘密の入力の仲介（`secrets.askpass`） | 設定が真なら有効 | 無効 | 無効 |

理由（1 を `exec` と同じにする理由）: ACP 版 1 には、`session/new`・`session/load` の途中でプロジェクトの信頼や処理系の変更を尋ねるための独立した要求の形がなく、T3Code の一般の ACP の経路にも、進行中の `session/prompt`（active turn）がない間は入力の要求を扱えない制約がある（`packages/provider-acp/` の `activeContext`）。最初の `session/prompt` の中へ確認を遅らせる案（BH-054 の案 B）は、信頼が決まる前に文脈と指示のファイルの準備を完了できないため採らない。

### 依頼の受け取りと終わりの理由

【方針】`session/prompt` の `params.prompt`（ACP 版 1 の `ContentBlock` の配列）からは、要素の `type` ごとに次の規則で受け取る。知らない `type`、音声（`audio`）、非対応のバイナリの `blob` が含まれるときは、黙って捨てたり文字列化したりせず、要求全体を `Invalid params`（`-32602`）で拒み、提供者へ要求を送らない。1 回の `session/prompt` のメッセージ全体の大きさは 16 MiB を上限とする。

| `ContentBlock` の `type` | 受け取り方と規則 |
|---|---|
| `"text"` | `text` の文字列を、利用者の依頼の文として順序どおりに繋ぐ |
| `"resource_link"` | 内容を持たない参照（`uri`、`name` など）。ファイルを主のプロセスで勝手に開かず、参照の `uri` と `name` を文字として依頼の文に添える。中身を読むときは LLM が `read` の道具で読む（読まないファイルと範囲の規則を通すため） |
| `"resource"` | クライアントが埋め込んだ内容（`resource.uri` と `resource.text`、`mimeType`）。`resource.text` があるものだけを受け付け、`resource.blob`（バイナリ）は `-32602` で拒む。`text` は `<resource uri="...">...</resource>` の形で依頼の文に添える。これはクライアントが渡した信頼しない内容として扱い、`read` の道具がそのローカルのファイルを読んだ版（`write`・`edit` の前提）としては記録せず、許可やモードを変える効果も持たせない |
| `"image"` | base64 の画像（`data` と `mimeType` が必須、`uri` は任意）。提供者の `image_input` が偽のとき、`mimeType` が対応する 4 種類（`image/png`・`image/jpeg`・`image/gif`・`image/webp`）でないとき、1 枚の復号後の大きさが上限（縮小前の入力上限 64 MiB）を超えるとき、1 回の依頼の画像の数が 20 枚を超えるときは `-32602` で拒む。クライアントがすでにバイト列を送っているためパスの規則は当てず、復号したバイト列を[道具](../01-agent/01-03-tools.md)の「画像のファイルの読み取り」と同じ補助のプロセス（`benitoiteh __image`、OS のサンドボックスと時間・メモリの上限付き）に通して検証・縮小し、セッションの `objects/` に保存して添付とする。一つでも検証・縮小に通らなければ、提供者へ要求を送らずに誤りを返す |

【方針】一連の処理の終わりの理由は、`Agent::run_controlled` が返す `RunReport` に、英語の診断の文を解析せずに判別できる終了の分類（完了、取り消し、番の数の上限、トークンの量の上限、そのほかの失敗）を型として持たせ、ACP 版 1 の `stopReason` に次のとおり対応させる。

| 終了の分類 | `session/prompt` の応答 |
|---|---|
| 正常に完了（`Outcome::Completed`） | `result: { "stopReason": "end_turn" }` |
| 取り消し（`Outcome::Cancelled`、または `session/cancel` を受けた後） | `result: { "stopReason": "cancelled" }` |
| 一連の処理の番の数の上限（`max_turns`）に達した | `result: { "stopReason": "max_turn_requests" }` |
| 一連の処理のトークンの量の上限（`max_run_tokens`）に達した | `result: { "stopReason": "max_tokens" }` |
| そのほかの失敗（提供者の誤り、提供者の拒否、検査と修正の回数の上限、子孫のプロセスの残りなど） | JSON-RPC の `error`（秘密と提供者の生の応答本文を含まない診断の文） |

### イベントから `session/update` への変換

【方針】[エージェントのループ](../01-agent/01-01-agent-loop.md)の「イベント」（`AgentEvent`）は、ACP 版 1 のスキーマ（<https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`）で定義された次の `sessionUpdate` に変えて送る。クライアントの optional な capability（`session.notices` など）に依存する未標準の通知には安全上必要な情報を載せず、どの版 1 クライアントでも表示される標準の更新型を使う。

| `AgentEvent`（または履歴の再生） | ACP 版 1 の `sessionUpdate` | 送る `update` の形と規則 |
|---|---|---|
| 履歴の再生の利用者の発言 | `"user_message_chunk"` | `{ "sessionUpdate": "user_message_chunk", "content": { "type": "text", "text": "<文>" } }` |
| `TextDelta { text, .. }` | `"agent_message_chunk"` | `{ "sessionUpdate": "agent_message_chunk", "content": { "type": "text", "text": text } }` |
| `ReasoningDelta { text, .. }` | `"agent_thought_chunk"` | `{ "sessionUpdate": "agent_thought_chunk", "content": { "type": "text", "text": text } }` |
| `ToolCall { call_id, name, arguments, .. }` | `"tool_call"` | `{ "sessionUpdate": "tool_call", "toolCallId": call_id, "title": "<一行の要約>", "kind": "<分類>", "status": "pending", "rawInput": arguments }`。`kind` は、`read`・`benitoite_reference`・`benitoite_explain` が `"read"`、`glob`・`grep` が `"search"`、`write`・`edit`・`create_project` が `"edit"`、`benitoite_check`・`benitoite_run`・`benitoite_test`・`benitoite_scratch`・`bash` が `"execute"`、`web_fetch` が `"fetch"`、`update_plan` が `"think"` とする。初期の `status` は `"pending"` とし、確認が不要と決まって実行に入った時点（または確認が許可された時点）で `"in_progress"` の `"tool_call_update"` を送る |
| `ToolResult { call_id, is_error, summary, screen, display, .. }` | `"tool_call_update"` | `{ "sessionUpdate": "tool_call_update", "toolCallId": call_id, "status": "completed" \| "failed", "content": [...] }`。`is_error` が偽なら `"completed"`、真なら `"failed"`。`content` には、`display`（`write`・`edit` の差分）または `screen` と `summary` を `{ "type": "content", "content": { "type": "text", "text": "..." } }` の形で載せる |
| `TurnEnd { .. }`、`Compaction { .. }`（および `session/new`・`session/load` の直後） | `"usage_update"` | 提供者の設定に `context_window`（上限）があるときだけ、`{ "sessionUpdate": "usage_update", "used": <現在の文脈の見積もりのトークン数>, "size": <context_window> }` を送る。`used` には累積の消費量ではなく、現在の文脈の大きさの見積もり（`Agent::context_estimate`）を入れる |
| `SessionStart` の起動診断、`Compaction` の要約通知、`Error` の診断 | 標準エラー出力（および `Error` は `session/prompt` の JSON-RPC `error` 応答） | 起動時の診断や圧縮の経過は標準エラー出力にも書く。確認の事実などの安全に関わる情報は、表示が保証されない通知には移さない |

### 実行の前の確認（`session/request_permission`）

【方針】`AcpApprover` は、確認の要求（`ApprovalRecord`）を受けたら、ACP 版 1 の `session/request_permission` をクライアントへ送り、利用者の決定を受ける。

#### 1. 要求の JSON の形と、T3Code の承認画面にすべての事実を表示させる規則

ACP 版 1 の `session/request_permission` の要求と応答は次の形をとる（<https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`）。

```json
{
  "jsonrpc": "2.0",
  "id": "bh-perm-1",
  "method": "session/request_permission",
  "params": {
    "sessionId": "<セッションの ID>",
    "toolCall": {
      "toolCallId": "<呼び出しの ID>",
      "title": "<確認の題>",
      "kind": "execute",
      "status": "pending",
      "rawInput": {
        "command": "<benitoiteh が組み立てた確認の事実の全文>"
      },
      "content": [
        {
          "type": "content",
          "content": {
            "type": "text",
            "text": "<benitoiteh が組み立てた確認の事実の全文>"
          }
        }
      ]
    },
    "options": [
      {
        "optionId": "allow-once",
        "name": "<選択肢の説明>",
        "kind": "allow_once"
      },
      {
        "optionId": "reject-once",
        "name": "Decline",
        "kind": "reject_once"
      }
    ]
  }
}
```

【方針】T3Code の一般の ACP の経路（`packages/provider-acp/` の `parsePermissionRequest` と `packages/shared/src/toolActivity.ts` の `deriveToolActivityPresentation`）は、`toolCall.content` の全体をそのまま承認カードに出すのではなく、①コマンド（`rawInput.command` など）、②題（`deriveToolActivityPresentation` で `Ran command` や `Changed files` に要約される）、③詳細、の優先順で一つの説明（`parsed.detail`）を選んで承認カードの `prompt` に渡す。そのため、`rawInput.command` に生のコマンド文字列だけを入れ、サンドボックスの範囲や `.agents` の警告を `content` だけに入れると、承認カードにはコマンドしか表示されない。これを防ぐため、次の規則を掛ける。

- **`benitoiteh` が確かめた事実の全文を一つの文にまとめる**: [対話の画面](05-02-tui.md)の「確認の画面」と同じく、`ApprovalRecord` の `facts` から、`benitoiteh` が確かめたすべての事実を欠かさずに複数行のテキストとして組み立てる。含める事実は次のとおりである。
  - 確認の題（例: `Run Benitoite script?`、`Run command outside the sandbox?`、`Write under .agents/?`、`Allow network access?`）。
  - 対象のパス（`Targets`、`Path`）、作業ディレクトリ（`Directory`）、URL とドメイン（`URL`、`Domain`）。パスの改行とタブは `\x0a`・`\x09` に変え、一つのパスを一行にする。
  - 制限モードのエフェクトの一覧（前に確認したエフェクトから増えたものに `+` を付け、同梱の Skill の説明を添える）、`read` の開かないファイルの取り込みの件数（`unread_imports`）、`Process.shell` の参照の有無。
  - OS のサンドボックスの範囲（書ける場所、ネットワークの可否、`Process.Run` のときの許すプログラムの一覧と注意、通常モードの `escalate` でサンドボックスの外で動くこと）。
  - `.agents` への書き込み（`agents_write`）のときの `This call may write agent skills and settings under .agents/. This approval covers this call only.` の警告。
  - 通常モードのコマンドの全文（8 文字以上の空白の連なりは `␠×N` に変え、制御の文字と文字の向きを変える文字は `\x1b`・`\u{202e}` の形に変える）。
- **T3Code が承認カードに選ぶ欄へ事実の全文を入れる**: `session/request_permission` の `toolCall` では、元の生の引数（LLM が渡した `arguments`）をそのまま `rawInput` に置かず、組み立てた事実の全文を `rawInput.command`（および `content` のテキストブロック）に入れる。これにより、T3Code の `parsePermissionRequest` が `command` を優先して選んでも、確認に要るすべての事実が承認カードに表示される。実機の T3Code の承認カードで、すべての種類の確認について事実が欠けずに表示されることを統合試験で確かめる【要検証】（BH-055）。
- **LLM の `justification` の扱い**: クライアントの承認カードでは、TUI のように「答えのキーのすぐ上に事実を固定し、`justification` を薄い色と別の字下げで分ける」描画の制御を `benitoiteh` の側から強制できない。LLM が長い `justification` の末尾に偽の事実を書いて承認カードの表示を埋めたり偽装したりすることを防ぐため、`session/request_permission` の承認表示には LLM の `justification` を含めず、`benitoiteh` が確かめた事実だけを示す。

#### 2. 確認の種類ごとの選択肢と記憶の範囲の対応表

【方針】T3Code の Web UI の承認カードは、`options[].name` をそのままボタンのラベルにするのではなく、固定のボタン（`Approve` は `kind: "allow_once"` のみを探し、`Always allow this session` は `kind: "allow_always"`、なければ `"allow_once"` を探し、`Decline` は `kind: "reject_once"` を探す。該当がなければ `cancelled` を返す）を使う（`packages/provider-acp/`）。また、`benitoiteh` の既存の `approval/mod.rs` では、エフェクトの確認は `ApprovalOutcome::Approved` でセッションに記憶し、`Command` と `WebFetch` は `ApprovedForSession` でセッションに記憶していた。

T3Code のボタンの意味（「今回だけ許可」と「このセッションの間許可」）と、`benitoiteh` の内部の記憶の範囲を一致させるため、確認の種類と条件ごとに、出す `options`、対応する内部の結果、記憶する範囲を次の表のとおり定める。

| `ApprovalKind` | `facts` の条件 | 出す `options`（`optionId` / `kind`） | 選ばれたときの内部の扱い | セッションに記憶する範囲と有効期間 |
|---|---|---|---|---|
| `Effects`・`TestEffects` | `agents_write == false` かつ `unread_imports == 0` | 1. `allow-once` / `allow_once`<br>2. `allow-session` / `allow_always`<br>3. `reject-once` / `reject_once` | 1. 今回だけ実行を許す（`confirmed_effects` を更新しない）<br>2. `ApprovalOutcome::Approved`（`remember_effects` で `confirmed_effects` を更新する）<br>3. `ApprovalOutcome::Denied` | `allow-once` はこの 1 回の実行だけ。`allow-session` はこのセッションの間、その対象（スクリプトまたはテストの組）について確認したエフェクトの集合を記憶する |
| `Effects`・`TestEffects` | `agents_write == true` または `unread_imports > 0` | 1. `allow-once` / `allow_once`<br>2. `reject-once` / `reject_once` | 1. 今回だけ実行を許す（`.agents` 書き込みと読まないファイルの取り込みは覚えない。エフェクトの集合も `allow-once` では記憶しない）<br>2. `ApprovalOutcome::Denied` | 記憶しない（この 1 回の呼び出しだけ） |
| `Command`（通常モード `untrusted`） | — | 1. `allow-once` / `allow_once`<br>2. `allow-session` / `allow_always`<br>3. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`<br>2. `ApprovalOutcome::ApprovedForSession`（`remember_command`）<br>3. `ApprovalOutcome::Denied` | `allow-once` はこの 1 回だけ。`allow-session` はこのセッションの間、完全一致するコマンド文字列を記憶する |
| `WebFetch` | — | 1. `allow-once` / `allow_once`<br>2. `allow-session` / `allow_always`<br>3. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`<br>2. `ApprovalOutcome::ApprovedForSession`（`remember_domain`）<br>3. `ApprovalOutcome::Denied` | `allow-once` はこの 1 回だけ。`allow-session` はこのセッションの間、そのドメインを記憶する |
| `Network`（通常モード `network = "proxy"`） | 元のコマンドが実行中 | 1. `allow-once` / `allow_once`<br>2. `allow-session` / `allow_always`<br>3. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`（そのコマンドの間だけ許す）<br>2. `ApprovalOutcome::ApprovedForSession`（セッションの間そのドメインを許す）<br>3. `ApprovalOutcome::Denied` | `allow-once` は元の `bash` コマンドが動いている間だけ、そのドメインのすべてのポートを許す。`allow-session` はこのセッションの間、そのドメインのすべてのポートを許す |
| `Escalate`（通常モード） | — | 1. `allow-once` / `allow_once`<br>2. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`<br>2. `ApprovalOutcome::Denied` | 記憶しない（この 1 回の呼び出しだけ） |
| `WriteScope`（範囲外・守る場所・`.agents` への書く道具） | — | 1. `allow-once` / `allow_once`<br>2. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`<br>2. `ApprovalOutcome::Denied` | 記憶しない（この 1 回の呼び出しだけ） |
| `CreateProject`（制限モード） | — | 1. `allow-once` / `allow_once`<br>2. `reject-once` / `reject_once` | 1. `ApprovalOutcome::Approved`<br>2. `ApprovalOutcome::Denied` | 記憶しない（この 1 回の呼び出しだけ） |

- 一回限りの確認（`allow-once` と `reject-once` のみを出した要求）に対して、クライアントの UI が「Always allow this session」のボタンを表示し、フォールバックとして `allow-once` を選んで返してきた場合も、`benitoiteh` は提示した `allow-once` の意味どおり**その 1 回だけの許可**として扱い、セッションには記憶しない。
- クライアントがその要求で提示していない `optionId`（一回限りの要求に対する `"allow-session"` など）を返したとき、すでに終わった要求の `id` に重複して応答したとき、または形式が合わないときは、すべて `ApprovalOutcome::Denied` として扱い、どの許可も記憶しない。
- クライアントが `{ "outcome": { "outcome": "cancelled" } }` を返したときは、`ApprovalOutcome::Cancelled` とする。

### 通信の中継と秘密の入力の扱い

【方針】（BH-057）

- **通常モードの通信の中継と終了競合の防止**（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「通信の中継」）:
  - `normal.network = "proxy"` で、許していないドメインへの接続がコマンドの実行の途中に起きたときは、`ProxyRun::decide` から `AcpApprover` と同じ確認の台帳を通して `ApprovalKind::Network` の `session/request_permission` をクライアントへ送る。確認の事実には、ドメインとポート、元のコマンド、作業ディレクトリ、「今回だけ許可（`allow_once`）」はそのコマンドの間に効き、許可はそのドメインのすべてのポートに効くことを示す。
  - **コマンド終了と遅れた応答の直列化**: 既存の `ProxyRun`（`crates/benitoiteh/src/sandbox/proxy.rs`）では、`ProxyRun::finish` が `finished = true` を立てるだけで、`decide` の `recv_timeout` が `Ok(answer)` を返したときに終了状態を再確認せずに `gate.session` へドメインを加えていたため、コマンド終了と相前後して届いた遅れた応答でセッションの許可が増えうる競合があった。これを改め、コマンドの生存状態（`finished`）と、確認の応答の採用・許可（`allowed`・`gate.session`・`declined`）の更新を同じ錠（`Mutex`）のもとで直列化する。コマンドの終了（`finish`）が確定するときに、そのコマンドに紐付く保留中の通信確認をすべて無効化して待ち手を起こし、終了・取り消しが先に確定したコマンドの確認に対する遅れた応答からは、コマンドの許可もセッションのドメイン許可も一切更新しない（TUI と ACP の両方に効く共通の修正とする）。
- **秘密の入力の仲介の無効化**（[秘密の入力](../03-safety/03-04-secrets.md)の「段 2: `benitoiteh` が秘密の入力を仲介する」）:
  - `SSH_ASKPASS`・`GIT_ASKPASS`・`SUDO_ASKPASS` の仲介は、利用者が伏せ字で秘密を入力する専用の欄を要し、秘密をログや通常のメッセージに載せない規則である。
  - ACP には構造化された入力を求める `elicitation/create` があるが、その仕様（form mode）はパスワード、API キー、トークンなどの秘密の情報の収集に使うことを明示的に禁じている（<https://github.com/agentclientprotocol/agent-client-protocol> のコミット `5ce539f03d2750e7f58a3ffdfab6919c2d04445c`）。そのため、通常のメッセージやフォームへ秘密の入力を落とすことはせず、`benitoiteh acp` では `askpass` の仲介を無効（非対話の `exec` と同じ扱い）とする。

### 巻き戻しとセッションの木

【方針】`benitoiteh acp` でも、セッションの記録（`session.jsonl`）、切り詰めた出力（`spill/`）、巻き戻しの記録（`objects/` と時点の一覧）は、TUI と同じく記録する（`--ephemeral` を付けたときを除く）。これにより、`benitoiteh acp` で行ったセッションを後で `benitoiteh --resume <ID>` で開いて `/rewind`・`/tree`・`/fork` を使うことも、TUI で行ったセッションを `benitoiteh acp` の `session/load` で再開することもできる。
