# Benitoite の処理系との連携

- 状態: 草稿
- 未決事項: なし

## 目的と範囲

本章は、`benitoiteh` が Benitoite の処理系（`benitoite`）を使う方法を定める。対象は、処理系の見つけ方と機能の確かめ、Skill の文書の得方、処理系の起動の仕方、診断の受け渡し、実行の前の検査の報告の読み方、参照の文書の引き方である。処理系を起動する道具（`check`・`run` など）の LLM から見た形は[道具](../01-agent/01-03-tools.md)で、起動した処理系に掛ける OS のサンドボックスは[OS のサンドボックス](../03-safety/03-02-sandbox.md)で、実行の前の確認は[利用者の確認](../03-safety/03-03-approval.md)で定める。

## 前提

- 対象とする処理系は、Benitoite の最新のリリース `v0.0.7`（コミット `63de89a2`）である。`v0.0.7` もソースコードだけのリリースであり、実行ファイルは配っていない（[Benitoite の CHANGELOG](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/CHANGELOG.md) の 0.0.7）。利用者は処理系をソースからビルドして用意する。
- 処理系の CLI は `check`・`run`・`test`・`fmt`・`skill`・`package` のサブコマンドを持ち、`--diagnostics=json` で診断を一行一件の JSON で標準エラー出力に書く（[CLI](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/06-tooling/06-01-cli.md)、[診断エンジン](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/02-impl/02-10-diagnostics.md)の「JSON の形式」）。`test` は、`--diagnostics=json` のとき、テストごとの結果と集計を一行一件の JSON で標準出力に書く（[Benitoite のリファレンス](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/reference/benitoite.md)の「16. Tests」）。
- `v0.0.7` は、`benitoiteh` の依頼（後述の「処理系への要望」）に応えて、次の機能を加えた（CHANGELOG の 0.0.7 の「Harness interfaces」、同梱の Skill の [Inspecting before execution](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/crates/benitoite/skill/references/inspection.md)）。
  - `check --report=json`: `main` を実行せずに検査し、宣言したエフェクトの上限、読み込んだソースとその SHA-256、診断、`Process.shell` の参照の有無を、一つの JSON で標準出力に書く。
  - `test --check [--report=json]`: `test` と同じ選び方の対象を、テストを実行せずに検査する。
  - `run` と `test` の `--allow-effects=<名前,...>`: 実行の直前に検査した宣言の上限が、渡した集合に収まらなければ、`E0512` と終了状態 2 で実行を断る。
  - `--version=json`: 版、ビルドの情報、対応する出力の形式の版（`formats`）を返す。
  - `Process.Command` の `environment` で、`DYLD_`・`LD_` で始まる名前を設定させない。
  - `skill list` と `skill show`: 同梱の Skill の文書を、インストールせずに標準出力に書く。
- `v0.0.7` は、`language "0.0.6"` 以前の宣言を `E0908` にする。ローダの環境変数の拒否を互換性の変更として登録したためである。`language` の宣言を省いたファイルは、今の版の規則で検査する（CHANGELOG の 0.0.7）。
- 処理系の静的な検査とエフェクトの上限の照合は、宣言した契約を比べるだけであり、実行時の権限制御と OS のサンドボックスを持たない。隔離は処理系を起動する側に委ねる（[Benitoite の SECURITY.md](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/SECURITY.md)、Inspecting before execution の末尾）。
- 処理系の実行ファイルは Wasmtime と Cranelift を含み、aarch64 の macOS のリリースのビルドで約 30 MB である（2026-10-18 に、`v0.0.7` のタグのソースからビルドしたもので 30,097,536 バイトを確かめた）。

## 仕様

### 処理系をライブラリとして組み込まない理由

【決定】`benitoiteh` は処理系のクレートをライブラリとして組み込まず、処理系の実行ファイルを子プロセスとして起動する。理由: 処理系を組み込むと Wasmtime と Cranelift が入り、`benitoiteh` の実行ファイルが処理系と同じ 30 MB 前後になって、小さい実行ファイルという目標（[目的と設計原則](../00-overview/00-01-goals.md)の「性能の目標」）を満たせない。また、子プロセスにすれば、処理系にだけ OS のサンドボックスを掛けられる。

子プロセスにする代償は、起動のたびにプロセスの生成と処理系の初期化の時間がかかることである。2026-10-18 に、手元の macOS（Apple Silicon）で `v0.0.7` の処理系の一回の起動を測ると、`check --report=json` が約 22 ミリ秒（標準のモジュールを含めて 44 のソースを読む小さなスクリプト）、`--version=json` と `skill show` が約 5 ミリ秒であった。LLM の応答の時間（秒の単位）と比べて小さいので、子プロセスにする形を保つ（BH-020 を閉じた）。

### 処理系の見つけ方と版の確かめ

【方針】`benitoiteh` は、起動のときに一度だけ処理系を探し、以後はその絶対パスを使う。

1. 利用者の設定ファイルの `benitoite.path` に書いたパス（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「設定ファイル」）。
2. なければ、`PATH` の中の `benitoite`。ただし、`PATH` の要素のうち、相対のパスと、プロジェクトのディレクトリとその下を指すものは飛ばす。理由: プロジェクトに置かれた `bin/benitoite` などを処理系として選ばないためである。

見つけたパスは、シンボリックリンクを解いた実のパスにして保持する。理由: セッションの途中で `PATH` やリンクの先が変わっても、確かめた実行ファイルだけを起動するためである。OS のサンドボックスで実行を許すファイルも、この実のパスで指定する（[OS のサンドボックス](../03-safety/03-02-sandbox.md)）。

【方針】処理系の実のパスは、OS の実行ファイルの形式のファイルであり、`#!` で始まるスクリプトでなく、サンドボックスの書ける場所の外にあることを要する。Linux では静的リンクであることも要する。満たさなければ、制限モードでは起動を止める。規則と理由は、制限モードで実行を許すプログラムと同じである（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「制限モードで実行を許すプログラム」）。処理系を包むシェルのスクリプト（Benitoite の Skill の評価の道具の `bin/benitoite` など）は、制限モードの処理系として使えない。

【方針】起動のときに `benitoite --version=json` を実行し、標準出力の JSON を読む。次のすべてを満たすときだけ、処理系を使えるとする。

- 終了状態が 0 で、標準出力の全体が一つの完全な JSON のオブジェクトとして読め、`schemaVersion` が 1、`kind` が `"version"` である。
- `formats` の次のキーの配列が、どれも 1 を含む: `diagnostics`、`testResults`、`checkReport`、`testCheckReport`、`effectLimit`、`skillList`、`skillDocument`。

理由: 処理系の側は、使える機能を版の数の大小でなく、`formats` に `benitoiteh` の理解する版が含まれるかで判定するよう定めている（Inspecting before execution）。ソースからビルドした処理系は、版の数が同じでも、ビルドしたコミットによって機能が違いうる。`--version=json` を持たない `v0.0.6` 以前の処理系は、この問い合わせを使い方の誤りとして終わるので、使えないと判定される。

満たさないとき（処理系が見つからないときを含む）は、制限モードでは起動を止め、通常モードでは Benitoite の道具を外して続ける。どちらも、理由を画面に示す。理由: 制限モードの確認とサンドボックスは、後述の「実行の前の検査の報告」と、処理系の `--allow-effects` の照合に頼る。これらを持たない処理系では、確認したエフェクトを処理系に確かめさせられない。

【方針】`version`（版の数）と `build`（ビルドのコミットなど）は、セッションの記録のヘッダと `doctor` に示す。`version` が、`benitoiteh` のシステムプロンプトの対応の説明を確かめた版（`0.0.7`。後述の「取り込む文書と版」）と違えば、画面とセッションの記録に警告を出して続ける。理由: Skill の手順が変わると、システムプロンプトに書いた、Skill の手順と `benitoiteh` の道具の対応が合わなくなりうる。止めずに続けるのは、要る機能の有無は `formats` で確かめてあり、対応の食い違いは LLM の手数を増やしうるだけで、確認とサンドボックスを弱めないからである。`build` は実行ファイルの自己申告であり、同じ実行ファイルであることの証明には使わない（`dirty` の `null` は「変更なし」でなく「不明」を表す。Inspecting before execution）。

【方針】起動のときに、処理系の実のパスのファイルの SHA-256 を求め、セッションの記録のヘッダに書く。同じプロジェクトのディレクトリの直前のセッションの記録と値が違えば、処理系の実行ファイルが変わったことを、前と今の版とともに画面に示して続ける。理由: 処理系の実行ファイルの中身は、制限モードの保証の前提である（[セキュリティモデル](../03-safety/03-01-security-model.md)の「保証しないこと」）。`build` の自己申告と違い、ハッシュは中身が変わったことを確かめられる。利用者が意図して処理系を更新したときも示すので、止めずに続ける。

### 取り込む文書と版

【方針】LLM に見せる Skill の文書（`SKILL.md` と `references/` の下の文書）は、起動した処理系から `benitoite skill show --format=json <名前>` で得て、`benitoiteh` の実行ファイルには埋め込まない（BH-024 を閉じた）。

- 名前は、`benitoite skill list --format=json` が返す一覧のうち、`SKILL.md` と、`references/` で始まるものに限る。ライセンスの文書は LLM に見せない。一覧は、初めて要るときに一度だけ得る。
- 得た本文は、セッションの間、主のプロセスのメモリに保ち、同じ名前を再び問い合わせない。`SKILL.md` は、どちらのモードでも起動のとき（システムプロンプトを作るとき）に得る（制限モードでは全文を、通常モードでは名前と説明を、システムプロンプトに入れる。[文脈の管理](../01-agent/01-04-context.md)の「Benitoite の Skill の置き方」）。ほかの文書は、`benitoite_reference` と `benitoite_explain` で初めて求められたときに得る。
- 次のどれかに当たる問い合わせの結果は使わない。終了状態が 0 でない。標準出力が一つの完全な JSON のオブジェクトとして読めない。`schemaVersion` が 1 でないか、`kind` が `"skillDocument"` でない。`name` が求めた名前と違う。`byteLength` と `contentHash`（SHA-256）が `text` の UTF-8 のバイト列と合わない。起動のときの `SKILL.md` で当たれば、制限モードでは起動を止め、通常モードでは Benitoite の道具と `<benitoite>` の節を外して続ける。道具の呼び出しで当たれば、その道具の誤りとして返す。
- `SKILL.md` の `contentHash` を、セッションの記録のヘッダに書く。システムプロンプトのハッシュ（同じヘッダ）も、得た `SKILL.md` によって変わる（[セッション](../01-agent/01-05-sessions.md)の「セッションの記録」）。
- `SKILL.md` の `{{benitoite-version}}` は、処理系が `skill show` で返すときに、自分の版に置き換えてある。`benitoiteh` は置き換えない。
- `SKILL.md` の先頭の HTML の注釈は、LLM に見せるときに除く（[文脈の管理](../01-agent/01-04-context.md)の「Benitoite の Skill の置き方」）。`SKILL.md` の手順は `benitoite` のコマンドを打つ前提で書いてあるので、`benitoiteh` の道具との対応は、システムプロンプトの側に書く（[文脈の管理](../01-agent/01-04-context.md)の「システムプロンプトの構成」）。

理由: 起動した処理系と同じ版の文書を LLM に見せられる。版の違う写しを埋め込むと、LLM が古い書き方で書き、検査で誤りになりうる（`v0.0.6` で `language "0.0.5"` が、`v0.0.7` で `language "0.0.6"` が `E0908` になった）。取り込み直しの手間と、実行ファイルの約 330 KB（`v0.0.7` の文書の大きさ）もなくなるので、文書を圧縮して埋め込むかの検討は要らなくなった（BH-021 を閉じた）。処理系は制限モードの起動に要り、通常モードで処理系がないときは Benitoite の道具を外すので、処理系なしに文書だけが要る場面は生じない。問い合わせの時間は前述のとおり小さい。

【方針】処理系の Skill の写しを、`v0.0.7` のタグから `assets/benitoite/v0.0.7/skill/` に置く。同じディレクトリの `SOURCE.md` に、元のタグ、コミット（`63de89a2`）、写した日、写したパスを書く。写した文書は、60 のファイル、合わせて 328,650 バイトである。この写しは実行ファイルに埋め込まず、システムプロンプトの対応の説明を書いたときに読んだ版の記録として置く。写した文書を手で直さない。処理系の新しいリリースが出ても自動では取り込み直さず、設計者の指示で取り込み直し、そのときに対応の説明を見直す。2026-10-18 に、手元でビルドした `v0.0.7` の `skill show SKILL.md` の本文が、この写しの `{{benitoite-version}}` を `0.0.7` に置き換えたものとバイト列で一致することを確かめた。

### 処理系の起動

【方針】`benitoiteh` は、処理系を次の形で起動する。オプションはスクリプトのパスより前に置く。`run` のスクリプトのパスより後の引数はスクリプトに渡る（Inspecting before execution）。

| 用途 | コマンドライン |
|---|---|
| 版と機能の確かめ | `benitoite --version=json` |
| Skill の文書 | `benitoite skill list --format=json`、`benitoite skill show --format=json <名前>` |
| 検査 | `benitoite check --diagnostics=json <スクリプトのパス>` |
| テストの検査 | `benitoite test --check --diagnostics=json <パス>...` |
| 実行の前の検査 | `benitoite check --report=json <スクリプトのパス>` |
| テストの実行の前の検査 | `benitoite test --check --report=json <パス>...` |
| 実行 | `benitoite run --diagnostics=json --allow-effects=<名前,...> <スクリプトのパス> [スクリプトの引数...]` |
| テスト | `benitoite test --diagnostics=json --allow-effects=<名前,...> <パス>...` |

- `run` と `test` には、いつも `--allow-effects` を付ける。エフェクトがないときは `--allow-effects=` とする（空の集合）。理由: 省くと、処理系は上限を掛けない。渡す集合は後述の「実行の前の検査の報告」で定める。
- ほかのサブコマンド（`fmt`・`package`・`skill install`）は起動しない。
- 作業ディレクトリはプロジェクトのディレクトリとする。
- 環境変数は、`benitoiteh` の環境から LLM の提供者のキーの変数（`OPENAI_API_KEY`・`ANTHROPIC_API_KEY`・`GEMINI_API_KEY`・`DEEPSEEK_API_KEY` と、設定ファイルで提供者のキーとして参照した変数）を除いて渡す。理由: LLM が書いたスクリプトが `Process.Environment` でキーを読み、出力に含めて LLM の提供者へ送ることを防ぐ。Benitoite の事前検討でも同じ対策が挙がっている（Benitoite の docs/todo の TODO-132）。
- 標準入力は、利用者の端末につながない。道具の引数（`stdin`）で文字列が渡されたときは、それを書いてから閉じ、渡されないときは空（`/dev/null`）にする。理由: 子プロセスが利用者の端末の入力を奪うと、取り消しの操作ができなくなる（[道具](../01-agent/01-03-tools.md)の「benitoite_run（制限モード）」）。
- 標準出力と標準エラー出力は、子プロセスが終わるまで読み続ける（上限を超えても読むのをやめない）。受け取った出力の扱い（LLM に返す末尾、`spill/` に残す量、捨てた量の表示）は、[道具](../01-agent/01-03-tools.md)の「出力の切り詰め」で定める。理由: 読むのをやめると、子プロセスがパイプの書き込みで止まる。末尾を返す道具では、途中で受け取りをやめると、本当の末尾（失敗の理由や集計）が失われる。ただし、検査の報告と問い合わせの結果は、標準出力の全体を一つの JSON として読む必要があるので、16 MiB を上限とし、超えたら読むのをやめて子プロセスを止め、報告が読めないものとして `The inspection report from benitoite exceeded 16 MiB and was not read. Pass fewer or narrower paths.` を道具の誤りとして返す。理由: 報告の `sources` は、対象（入口）ごとに、読み込んだ標準のモジュールを含むソースの記録を繰り返し持つ。2026-10-18 に `v0.0.7` で測ると、対象一つにつき約 9 KB であり、約 1,900 の入口を持つディレクトリを `benitoite_test` に渡すと上限に届く。上限を設けないと、大きな報告や壊れた処理系の出力で主のプロセスのメモリを使い尽くしうる。
- 時間の上限（`run` と `test` の既定 120 秒、検査と実行の前の検査の既定 30 秒、問い合わせの既定 10 秒）を過ぎたら、`SIGINT` を送る。処理系は `run` と `test` では `SIGINT` を受けるとリソースを解放して終了状態 130 で終わる（[CLI](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/06-tooling/06-01-cli.md)の「終了状態」）。送ってから 10 秒で終わらなければ `SIGKILL` を送る。利用者の取り消しも同じ手順で止める（[エージェントのループ](../01-agent/01-01-agent-loop.md)の「取り消し」）。
- スクリプトとテストの対象のパスは、範囲の判定（[道具](../01-agent/01-03-tools.md)の「道具の定義の共通の規則」）に使った、シンボリックリンクを解いた絶対の実のパスで処理系に渡す。理由: 判定したものと処理系が読むものを揃える。LLM が渡した相対のパスをそのまま渡すと、`-` で始まるパスが処理系のオプションとして読まれうる。
- 子プロセスは新しいプロセスグループで起動し、止めるときはグループに送る。理由: 通常モードでスクリプトが起動した外部コマンドも、あわせて止めるためである。終わった後に残ったプロセスの片付けと、グループを抜けたプロセスの扱いは、[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「子プロセスの後始末」で定める。
- 検査、実行の前の検査、問い合わせは、利用者のスクリプトを実行しない（報告の `executed` は偽に決まっている）が、書ける場所を一時ディレクトリだけ、ネットワークを使えない方針の OS のサンドボックスの中で起動する（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「制限モードの方針」）。理由: 検査でも、定数の評価と外部の関数の宣言の照合のために WASM の部品をコンパイルする（Inspecting before execution）。処理系の欠陥で検査の途中に予期しない操作が起きても、範囲を狭めておく。通常モードでも、サンドボックスの方針（`danger-full-access` を含む）によらず、この方針で起動する。ただし、通常モードで OS のサンドボックスを使わない指定（`--no-sandbox`）のときは、サンドボックスを掛けずに、ほかの道具の子と同じく端末から切り離して起動する（2026-10-18 に決めた【方針】）。理由: 利用者がサンドボックスを外すと決めたときは、`bash` も `benitoite_run` もサンドボックスの外で動くので、問い合わせだけを止めても範囲は狭まらない。

### 終了状態と診断の受け渡し

【方針】`check` と `run` の終了状態は、処理系の定め（0 成功、1 スクリプトの実行の失敗、2 検査の誤り・エフェクトの上限を超えたこと・使い方の誤り、3 処理系の不具合、130 中断）のとおりに解釈する。`run` は `Process.exit(code)` で任意の値で終わりうるので、標準エラー出力に処理系の形式の JSON の報告があるかで、処理系の失敗とスクリプトの終了を区別する（処理系の定めた方法である）。`try e or die` の失敗は、終了状態 1 と `kind` が `"die"` の報告で示されるので、スクリプトの実行の失敗として扱う（[CLI](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/06-tooling/06-01-cli.md)の「終了状態」）。

【方針】`run` と `test` が終了状態 2 で終わり、`code` が `"E0512"` の診断があるときは、診断に加えて `The script changed after the effects were confirmed and now declares more effects. Call the tool again to inspect it and ask the user.` を返す。理由: `benitoiteh` は直前の報告の集合を `--allow-effects` に渡すので、`E0512` は、報告の後にスクリプトか、それが取り込むモジュールが変えられたときに起きる。`benitoite_test` にディレクトリを渡したときは、報告の後にディレクトリの下に入口のファイルが加えられたときにも起きる。この診断は標準エラー出力から読むのでスクリプトが偽れるが、LLM への説明にだけ使い、確認とサンドボックスの判定には使わないので、偽っても新しい操作は許されない。

【方針】標準エラー出力の各行のうち、JSON のオブジェクトとして読めて `kind` を持つ行を診断とし、ほかの行をスクリプトの出力とする。実行の前の検査の報告では、報告の `diagnostics` の配列の各要素を診断とする（報告の診断は、標準エラー出力の診断と同じ欄を持つ）。診断は、LLM に返すときに次の文章の形に変える。

```text
error[E0405] src/report.bnt:12:5: <message>
  12 |     bind total <- List.sum(items)
     |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  note: <notes の各要素>
  help: <helps の message>
    replace 12:20-12:25 with "xs"
```

- `code` が `null` の報告（`kind` が `"die"` の失敗終了と、報告の中の使い方の誤り）は、角括弧のコードを省き、`error src/main.bnt:8:3: explicit failure exit` の形で始める。位置（`primary`）が `null` のときは、位置を省く。注記（`message: ...`・`cause: ...`）は、ほかの診断と同じく `note:` の行で示す。
- 位置の行のソースは、`benitoiteh` がファイルから読んで添える。理由: JSON は位置だけを持ち、ソースの行を含まない。LLM はソースの行が添えてあると、直す箇所を `read` で読み直さずに済む。
- 添える行を読むときは、そのモードの `read` の道具と同じ規則（読める範囲、読まないファイル、パスの解き方。[道具](../01-agent/01-03-tools.md)の「道具の定義の共通の規則」）を当て、通常のファイルの一行（2,000 文字まで）だけを読む。規則に当たるか、位置がファイルの中にないときは、行を添えずにパスと位置だけを示す。理由: 標準エラー出力の診断は、スクリプトが偽れる（`Console.Write` だけで、診断の形の行を書ける）。偽の診断の位置を親が無条件に読むと、子プロセスにも LLM の道具にも許していないファイルを、親が代わりに読んで LLM に送ることになる。`read` と同じ規則を当てれば、添える行は LLM が `read` で読めるものに限られ、新しく読めるものは増えない。報告の診断はスクリプトの実行の出力でないが、報告にはスクリプトが選んだファイルの名前が含まれ、表示用のパスは OS のパスに戻せるとは限らない（Inspecting before execution）ので、同じ規則を当てる。
- 修正案（`helps` の `edits`）は、置き換えの範囲と文字列のまま示す。`benitoiteh` は置き換えを当てない。理由: Benitoite の処理系も置き換えを当てず、当てるのは利用者か LLM であると定めている（Benitoite の設計書 02-10「修正案」）。
- 誤りが多いときは、`error` を先に、出た順に最大 20 件を示し、残りの件数を一行で示す。

【方針】`test` の結果は、標準出力の各行のうち、JSON のオブジェクトとして読めて `kind` が `"test"` か `"testSummary"` の行から作る。失敗したテストは、名前と `failure` の `reason`・`message` を示す。`reason` が `"exit"` で `die` の欄があるときは、その報告を上の診断と同じ形に変えて示す。失敗したテストが書いた出力（`stdout`・`stderr` の欄）は、末尾を添える（量は[道具](../01-agent/01-03-tools.md)の「出力の切り詰め」）。JSON として読めない行は、出力としてそのまま示す。

【方針】テストが通ったと示すのは、集計の行（`testSummary`）があり、終了状態が 0 で、`filesNotRun` が 0、`interrupted` が偽のときだけとする。`passed` と `failed` がともに 0 でも、この条件を満たさなければ通ったと示さない。集計の行がないときは、集計がないことを示す。`filesNotRun` が 0 でないときは、実行しなかった入口の数を示す。理由: 処理系の側は、エフェクトの上限で全体を断ったときにも、`passed` と `failed` が 0 で `filesNotRun` が入口の数の集計を書き、この条件で成功を見分けるよう定めている（Inspecting before execution）。集計の行がないのは、処理系が途中で終わったことを示しうる。この結果は、LLM と利用者に示すためだけに使い、確認とサンドボックスの判定には使わない（[セキュリティモデル](../03-safety/03-01-security-model.md)の「信頼の境界」）。

### 実行の前の検査の報告

実行の前の確認（[利用者の確認](../03-safety/03-03-approval.md)）には、実行するプログラムのエフェクトが要る。

【方針】`benitoite_run` は確認の直前に `check --report=json` を、`benitoite_test` は `test --check --report=json` を一度実行し、その報告から、確認とサンドボックスに使うエフェクトを得る。`benitoiteh` はスクリプトのソースからエフェクトを読まない。理由: `v0.0.6` までは、`benitoiteh` が字句の単位で `main` のシグネチャを読んでいた。この読み取りは処理系の構文を `benitoiteh` の側でもう一度実装するものであり、構文が変わると、誤って少ない集合を読みうる。報告は、処理系が型の検査を終えたプログラムから作る。

報告は処理系の言明として、処理系の実行ファイルを信頼する範囲で信頼する（[セキュリティモデル](../03-safety/03-01-security-model.md)の「信頼の境界」）。理由: 報告を作る検査は利用者の関数を実行せず、検査の前に値を求める `const` は、リテラル、定数、構築子、演算子などの純粋な式に限られ（[Benitoite のリファレンス](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/reference/benitoite.md)の「8. Constants and type aliases」）、外部の WASM の部品はコンパイルしても実体化も呼び出しもしない（同リファレンスの「2. The command line」）。このため、スクリプトは報告の中身を自分の出力で書けない。ただし、報告の診断の文には、スクリプトが選んだ名前（識別子、ファイルの名前、文字列）が含まれうるので、LLM に渡す内容としては信頼しない（[セキュリティモデル](../03-safety/03-01-security-model.md)の「関係する者と信頼」の、LLM が読む内容）。

【方針】報告を確定した結果として使うのは、次のすべてを満たすときだけとする。条件は、処理系の側が確定した集合として使ってよいとする条件（Inspecting before execution）に、`benitoiteh` の側の確かめを加えたものである。

- 終了状態が 0 である。
- 標準出力の全体が一つの完全な JSON のオブジェクトとして読める。欄は名前で読み、欄の並びと空白に頼らない（処理系の側は、欄の順序を契約に含めない）。
- `schemaVersion` が 1、`kind` が `"checkReport"`（テストでは `"testCheckReport"`）、`status` が `"ok"`、`complete` が真、`executed` が偽である。
- `aggregateEffects` が `null` でなく、`basis` が `"declaredUpperBound"` で、`expanded` の名前がすべて、後述の知る名前である。

満たさないときは実行しない。`status` が `"checkError"` なら、報告の `diagnostics` を前述の診断の形に変えて返す。ほかのとき（使い方の誤り、処理系の不具合、中断、読めない報告、知らない名前）は、処理系の誤りとして理由を一行で返す。理由: 処理系の側は、不完全な報告、`null`、知らない状態と名前を、空の集合として読まないよう求めている。`v0.0.6` までの字句の読み取りは、読めないときに最大の集合とみなして確認を求めた。報告では、読めないことは処理系の誤りか検査の誤りを示し、`--allow-effects` には集合を名前で渡すので、知らない名前を含む集合を処理系に渡せない。

知るエフェクトの名前は、`--allow-effects` が受け付ける次の 13 とする（Inspecting before execution）: `State`、`Console.Read`、`Console.Write`、`File.Read`、`File.Write`、`Process.Run`、`Process.Exit`、`Process.Environment`、`Clock.Time`、`Random.Generate`、`Http.Connect`、`Http.Listen`、`Assert.Check`。報告の `expanded` は `IO.All` を開いた原子の名前で書かれる。

【方針】確認とサンドボックスの方針に使うエフェクトは、報告の `aggregateEffects.expanded` とする（`main` では `main` の宣言の上限、テストでは選んだテストの関数の宣言の上限の和）。処理系に渡す `--allow-effects` も同じ集合とし、前に確認した範囲（[利用者の確認](../03-safety/03-03-approval.md)の「制限モードの確認」）がこれより広くても、広い範囲を渡さない。理由: 渡す集合を今回の報告の集合に限れば、報告の後にスクリプトが変えられてエフェクトが増えたとき、処理系が実行の直前の検査で `E0512` を返して実行を断る。サンドボックスの方針と処理系の照合も、同じ集合で揃う。

【方針】`Assert.Check` は、確認の画面に示さず、確認が要るかの判定（前に確認した範囲より増えたか）にも数えない。ただし、`--allow-effects` に渡す集合からは除かない。理由: `Assert.Check` はテストの関数の契約の一部であり（`main` には書けない。`E0415`）、表明が外れたときにそのテストを失敗にするだけで、プログラムの外に作用しない。処理系の側は、確認の画面で省くときも許す集合から落とさないよう求めている。落とすと、`Assert.Check` を宣言したテストが `E0512` で断られる。

【方針】報告の `processShellReference`（`main` の契約、テストでは各対象の値）が `"present"` で、エフェクトに `Process.Run` を含むときは、確認の画面に、スクリプトが標準のシェルの関数（`Process.shell`）を参照していることと、制限モードではシェルの起動を OS のサンドボックスが拒むことを示す（[利用者の確認](../03-safety/03-03-approval.md)の「制限モードの確認」）。`"absent"` を、シェルや別の言語の処理系が起動されないことの証明として扱わない。理由: この値は到達性の解析でなく、検査したプログラム全体での式の参照を数えたものであり、`"present"` も呼び出しが起きることを示さない（Inspecting before execution）。制限モードの保証は、OS のサンドボックスの実行の制限に置く（[セキュリティモデル](../03-safety/03-01-security-model.md)の「保証しないこと」）。

【方針】確認の結果をセッションの記録に書くときは、報告の `sources` のうち `kind` が `"user"` のものの表示用のパスと `contentHash` を添える。理由: 後で記録を調べるときに、どの内容のスクリプトについて確認したかを辿れる。ただし、このハッシュは後の実行が同じ内容を読むことを保証しない（処理系の側の限界。[セキュリティモデル](../03-safety/03-01-security-model.md)の「保証しないこと」）。

【方針】`benitoite_test` の対象には、`.bnt` のファイルのほか、ディレクトリも受け付ける（BH-023 を閉じた）。同じパスを重ねて指定したときは一つにまとめてから渡す。理由: 対象の選び方（下のディレクトリの辿り方、下位のパッケージを除く規則など）は、`test --check` と `test` が同じ処理で行う（[CLI](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/06-tooling/06-01-cli.md)の「テストの非実行の検査報告」）。`v0.0.6` までは、`benitoiteh` が選び方を作り直すとエフェクトを読んだファイルの組と処理系が実行するファイルの組がずれうるので、ファイルだけに限っていた。報告と実行の間にディレクトリにファイルが加えられても、加わったファイルのテストのエフェクトも `--allow-effects` で照合される。

### 参照の文書と診断の説明

【方針】`benitoite_reference` の道具（[道具](../01-agent/01-03-tools.md)の「benitoite_explain と benitoite_reference」）は、処理系から得た Skill の `references/` の文書（前述の「取り込む文書と版」）を名前で返す。名前は、`references/` と拡張子 `.md` を除いたもの（`idioms`・`grammar`・`inspection`・`stdlib/IO.File` など）とし、`references/<名前>.md` が一覧にあるものだけを受け付ける。`stdlib/index` はモジュールの一覧である。名前を省いたときと、一覧にない名前を指定したときは、一覧から作った引ける名前（と `SKILL`）を返す。道具の定義は、一覧に依らない固定の文とする（[道具](../01-agent/01-03-tools.md)の「benitoite_explain と benitoite_reference」）。

【方針】`benitoite_explain` の道具は、診断のコード（`E0405` など）を受け取り、`references/diagnostics.md` の、そのコードの見出し（`## E0405`）から次の見出しの前までを返す。理由: `diagnostics.md` は約 94 KB あり、全体を文脈に入れるとトークンを浪費する。コードごとの節だけを返せば足りる。

### 処理系への要望

試作で見つけた、処理系に欲しい機能は、Benitoite の作業ツリーを変えずに、本節と未決事項に書く。Benitoite の docs/todo に項目を足すかは、設計者が決める。

【決定】2026-10-16 に、次の機能を、Benitoite の `v0.0.7` で処理系に加える候補として設計者に示した。同日の外部のレビューを受けて、優先の順と内容を改め、6 を加え、設計者が承認した。2026-10-17 に、`v0.0.6` の変更を踏まえて依頼の文面を改め、設計者が処理系の側に依頼した。処理系の側は Benitoite の docs/todo の TODO-254 で扱い、同日に公開した `v0.0.7` で 1〜6 をすべて加えた（CHANGELOG の 0.0.7 の「Harness interfaces」）。番号は依頼のときの優先の順である。

| 番号 | 依頼した機能 | `v0.0.7` で加わった形 | 未決事項 |
|---|---|---|---|
| 1 | 実行せずに `main` を検査し、`IO.All` を開いたエフェクトの集合と `Process.shell` の参照の有無を機械で読める形で出力する | `check --report=json`（`checkReport`）。エフェクトは宣言の上限。シェルの参照は検査したプログラム全体での式の参照で、到達性を見ない | BH-022（閉じた） |
| 2 | テストの対象を、テストを実行せずに検査し、テストの関数とそのエフェクトを出力する。対象の選び方は `test` の実行と同じ処理を使う | `test --check --report=json`（`testCheckReport`） | BH-023（閉じた） |
| 3 | `run` と `test` に許すエフェクトの集合を渡し、検査したエフェクトが収まらなければ実行せずに終わる | `--allow-effects`。収まらなければ `E0512`、終了状態 2。照合した同じ検査済みのプログラムを実行する。`test` は全対象の準備が済むまでテストを始めない | BH-027（閉じた） |

| 5 | `Process.Command` の `environment` で、ローダに働く環境変数を設定させない | `DYLD_`・`LD_` で始まる名前を、大文字と小文字を区別せずに拒む。親から受け継いだ環境変数は変えない | BH-026（閉じた） |

1 と 2 の報告は、依頼のときに共通に求めた欄（出力の形式の版、結果の分類と完全さ、検査の対象、読み込んだソースの一覧と内容のハッシュ、既存の形の診断）をすべて持つ。

各機能の補足は次のとおりである。

- 3 は、実行時の権限制御ではない。処理系が実行の前に行う静的な検査の結果と、渡された集合を比べるだけである。同じ `File.Write` のまま書く先が変わること、同じ `Process.Run` のまま起動するコマンドが変わることは拒まない（Inspecting before execution）。3 があっても、OS のサンドボックスは外さない。
- 5 は、`Command.environment` に明示した名前だけを拒む。親から受け継いだ環境変数と、`Process.Run` で許したコマンド（`env` など）が子に設定する変数は対象の外である（CHANGELOG の 0.0.7）。書ける場所のライブラリを読み込ませる道は、引き続き OS のサンドボックス（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「制限モードの方針」）が塞ぐ。5 は、外部コマンドに渡す環境変数の扱いを検討する項目（Benitoite の docs/todo の TODO-058）と関係する。
- 4 の `build` は実行ファイルの自己申告であり、同じ実行ファイルであることの証明にならない。
- 次のものは、`v0.0.6` の時点で処理系がすでに満たしていたので、依頼に含めなかった。Linux 向けのリリースの実行ファイルが静的にリンクされていること（[導入の手順](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.6/docs/reference/install.md)）、`--diagnostics=json`、`SIGINT` で資源を解放して終わること。
