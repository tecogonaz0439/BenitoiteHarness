- 状態: 草稿

## 目的と範囲

本章は、設計から試作の完了までの段階、各段階の完了条件、作業の分担、試作の後の判断の基準を定める。

## 前提

- 設計書と実装プランは Claude Code が書き、試作の実装は Codex CLI（GPT-6.1-Sol、推論の度合い high）が行う（2026-10-17 の設計者の指示。`AGENTS.md`）。
- Benitoite の処理系は、設計書と実装プランを Claude Code が作り、実装を LLM のサブエージェントが実装プランに従って行い、Claude Code がオーケストレータとしてすべての作業を確かめる形で作られた（Benitoite の AGENTS.md の「プロジェクトの概要」）。

## 仕様

### 進め方

【方針】

1. 設計書（本書）を作り、外部のレビュー（ChatGPT Pro）を受けて直す。
2. 段階ごとに、実装プラン（`docs/plan/`）を作る。実装プランは、設計書と実装プランだけを読めば実装できる粒度で書く。
3. Claude Code がオーケストレータとして、実装の作業を Codex に配る。作業ごとに git のブランチと作業ツリー（git worktree）を分け、オーケストレータが確かめてから `main` に取り込む。
4. 段階の完了条件を確かめたら、設計書の【方針】を、確かめた内容に合わせて【決定】に改めるか、直す。

### 段階

【方針】

2026-10-17 に、設計者の指示で、段階の順を一部入れ替えた。Benitoite の `v0.0.7` の公開を待つ間に、`v0.0.7` に依らない作業（P2 のうちサンドボックスの項目、P3、P4 のうち `create_project` と `doctor` の処理系の版の確かめを除くもの）を、P2 の処理系との連携の作業より先に進める。理由: 処理系との連携は、`v0.0.7` で処理系に加わる機能（エフェクトの報告など。[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系への要望」）を使って作るので、公開を待たずに作ると作り直しになる。ほかの作業は模擬の提供者で確かめられ、待つ間に進められる。段階の完了条件は変えない。

Benitoite の評価の道具の取り込みは、P0 から P5 に移した（2026-10-17）。理由: 評価の道具は P5 まで使わず、取り込んだ後に処理系の新しい版が出れば、取り込み直すことになる。

後回しにするもの（Gemini の専用のアダプタ、OS のキーストア、git の道具、計画を書く道具）は、P5 の評価の結果を見て、P6 の前に加えるかを決める。【決定】Sign in with ChatGPT は、評価の結果によらず加える（2026-10-18 に設計者が決めた）。理由: API キーでは ChatGPT の購読を使えず、購読なしでは、設計者だけでなくほかの利用者にとっても使い続けにくい。加える時期と作り方は、実装プランで決める。 【決定】利用者の Agent Skill の読み込み（[文脈の管理](../01-agent/01-04-context.md)の「利用者の Agent Skill」）も、評価の結果によらず、P6 の前に加える（2026-10-19 に設計者が決めた）。理由: Benitoite で書いた道具を Skill として配り、LLM に使わせられることは、試作の後の判断の材料になる。 【決定】セッションの木（会話を枝分かれさせて保ち、前の時点から別の枝を始めること）と、画像のファイルを読むこと（[道具](../01-agent/01-03-tools.md)の「read」。今は誤りを返す）も加える（2026-10-19 に設計者が決めた）。加える時期は別に決める。

### 作業の分担

【方針】

- 設計書、実装プラン、作業の確かめ、取り込み、設計書の更新は、オーケストレータ（Claude Code）が行う。
- 実装は、実装プランの作業ごとに Codex CLI（GPT-6.1-Sol、推論の度合い high）が行う。作業ごとに新しい Codex のセッションを起こし、作業ツリーの中だけを書ける形（`workspace-write`）で動かす。同時に動かすのは一つとする（2026-10-17 の設計者の指示）。
- Codex を起動する前に、作業の文書を設計書と既存のコードと突き合わせる点検を、Claude のサブエージェントで行う。理由: 文書の食い違いで Codex が止まると、使用量が無駄になる（Benitoite の処理系の改造で得た運用）。
- 本物の LLM の API を呼ぶ確かめと評価は、設計者の了承を得てから行う。

### 試作の後の判断

試作を終えたら、Benitoite の処理系にマージするか、独立したままとするかを設計者が決める（BH-080）。判断の材料として、次の点を P6 で報告する。

- **安全の性質**: 制限モードの保証（[セキュリティモデル](../03-safety/03-01-security-model.md)の R1〜R5）が、macOS と Linux で確かめられたか。確かめられなかった点は何か。
- **性能**: 実行ファイルの大きさと速さの目標を満たしたか。Benitoite の課題での成功率と回数が、同じモデルの Claude Code と比べてどうか。
- **事前検討との差**: サーバモードの代わりに OS のサンドボックスを掛けた作りで、事前検討がサーバモードに求めた性質（エージェント用のプロファイル、承認の画面での認証、監査の記録）のうち、何が欠けているか。
- **マージの形の候補と代償**:
  - (a) 処理系の `agent` のサブコマンドとして取り込む。利用者に配る実行ファイルが一つになる。代償は、処理系の実行ファイルに提供者の層と画面の依存が加わること（処理系は約 30 MB なので、大きさの比は小さい）、事前検討の ADR 0342 の決定 3 を改めるか、サーバモードを先に作る必要があること。
  - (b) 同じリポジトリの別のクレートと別の実行ファイルにする。処理系と同じ版で配れ、実行ファイルは小さいまま保てる。
  - (c) 独立したリポジトリのままとする。処理系の版との対応を、取り込んだ文書の版で管理し続ける。
- **処理系への要望**: 試作で見つけた、処理系に欲しい機能（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系への要望」）。

### サーバモードの実装の後の見直し

【決定】Benitoite にサーバモードと、エフェクトに基づく実行時の権限制御が実装された後に、その実装を確かめて、試作のハーネスの作りを見直す（2026-10-16 の設計者の方針）。見直す点は、[目的と設計原則](00-01-goals.md)の「事前検討との関係」の表の点、特に次のものである。この見直しは試作の後の判断（前節）とは別に、サーバモードの実装の時期に合わせて行う（BH-081）。

- 処理系の CLI を子プロセスとして起動する作りを、デーモンの通信口に直接つなぐ作り（ADR 0346）に改めるか。
- `benitoiteh` が掛ける OS のサンドボックスと、サーバモードのエージェント用のプロファイル（ADR 0192）の分担。
- 実行の前の確認と、サーバモードの承認の画面の関係（ADR 0345 の決定 2）。
- 処理系の実行の前の検査の報告（`check --report=json`）と `--allow-effects` による照合を、サーバモードの実行前の判定の結果に置き換えるか。
