# 目的と設計原則

- 状態: 草稿
- 未決事項: BH-001, BH-080

## 目的と範囲

本章は、試作のハーネス `benitoiteh` の目的、Benitoite の事前検討との関係、範囲と範囲の外、性能の目標の要約、設計原則を定める。

## 前提

- Benitoite は、利用者が言語を学ばずに、LLM によるスクリプトの作成と修正を通じて作業を自動化できることを目指す、静的型付きの関数型スクリプト言語である。利用者は作業と許可する操作を決め、処理系は型とエフェクトの規則への適合を検査し、LLM はコードの作成・修正と診断の説明を担う（[Benitoite の設計書 00-01「目的と設計原則」](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/design/00-overview/00-01-goals.md)）。
- Benitoite の事前検討は、処理系が自前のエージェントハーネスを持つことを、初回リリース版の後の機能として検討した。目的は、操作の範囲を型とエフェクトで限り、実行の前の確認を処理系が強制できる入口を作ることと、LLM を使ったテスト（構文の測定と Skill の評価）を処理系と一体で制御することである（[06-08「エージェントハーネス」](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/archive/2026-10-09-design-first-release/06-tooling/06-08-agent-harness.md)、Benitoite の docs/todo の TODO-124）。
- 事前検討は、エージェントハーネスをサーバモード（実行時の権限制御と OS のサンドボックスを持つデーモン）の後に作り、サーバモードのない版で動かす経路を作らないと定めた（[ADR 0342](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/archive/2026-10-09-design-first-release/decisions/0342-agent-harness-after-server-mode.md) の決定 3）。サーバモードは、最新のリリース `v0.0.7` の時点で実装されていない（[Benitoite の CHANGELOG](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/CHANGELOG.md) の 0.0.7）。

## 仕様

### 目的

【決定】試作の目的は次の四つである。

1. **事前検討の設計を動くもので確かめる**。制限した道具、エフェクトによる実行の前の確認、Benitoite の Skill を文脈に置く形が、LLM のスクリプトの作成の成功率と、利用者の安全をどこまで両立させるかを確かめる。
2. **二つのモードを持つハーネスを作る**。Benitoite 以外のスクリプト言語を使わせない制限モードと、一般的なハーネスと同じく振る舞う通常モードを持つ（[モード](../01-agent/01-02-modes.md)）。
3. **小さく速く、性能の高いハーネスを作る**。実行ファイルが小さく、実行が速く、エージェントとしての性能が主なハーネスに劣らないことを、測って示す（後述の「性能の目標」）。
4. **試作の後の判断の材料を得る**。Benitoite の処理系にマージするか、独立したままとするかを、試作の結果で決める（[ロードマップ](00-03-roadmap.md)の「試作の後の判断」）。

### 事前検討との関係

【決定】事前検討の決定は、試作の条件に合わない点を除いて引き継ぐ。引き継がない点と、その理由は次のとおりである（2026-10-16 に設計者が承認した）。サーバモードと実行時の権限制御が Benitoite に実装された後に、その実装を確かめて、この表の点（特にサーバモードを通さない作り）を見直す（[ロードマップ](00-03-roadmap.md)の「サーバモードの実装の後の見直し」）。決定ごとの対応の全体は[事前検討との対応](../08-appendix/08-02-pre-study-mapping.md)にまとめる。

| 事前検討の決定 | 試作 | 理由 |
|---|---|---|
| サーバモードのない版でエージェントハーネスを動かす経路を作らない（ADR 0342 の決定 3） | サーバモードなしで動く。処理系の子プロセスに、`benitoiteh` が OS のサンドボックスを掛ける | サーバモードが実装されていない。試作は処理系の配布物ではなく、事前検討がサーバモードに求めた隔離を、試作の中で OS のサンドボックスで代える |
| デーモンの通信口に直接つなぐ（ADR 0346） | 処理系の CLI を子プロセスとして起動する | 同上 |
| 処理系のサブコマンド `benitoite agent` とする（ADR 0209 の予約、ADR 0343 の例） | 別の実行ファイル `benitoiteh` とする | 利用者の要件。マージするかは試作の後に決める |
| シェルを道具として持たせない（ADR 0344 の決定 5） | 制限モードだけで守る。通常モードはシェルを持つ | 利用者の要件（通常モード） |
| 圧縮と会話の再開は初めは設けない（Benitoite の docs/todo の TODO-134 の見立て） | 設ける | エージェントとしての性能の目標に、長い作業を続けられることを含める |
| LLM の API のクライアントに既存の OSS を使う（ADR 0194 の決定 4） | HTTP と TLS の OSS の上に、提供者のアダプタを自前で作る | 試作は非同期の実行時を使わずにスレッドで組む（06-01）。三つの通信の形の要求と応答の変換は、HTTP の層の上で自前で書ける量である。事前検討も、互換の口の違いを吸収する層は自分で持つ方が扱いやすい可能性を挙げていた（Benitoite の docs/todo の TODO-128） |
| 四つの提供者（ADR 0340） | 三つのアダプタを先に作り、Gemini の専用のアダプタと Sign in with ChatGPT は後に加える | 評価に要る提供者を先に揃える |

### 範囲

試作が作るものは、二つのモード、三つの提供者のアダプタ、制限モードと通常モードの道具、OS のサンドボックス（macOS と Linux）、利用者の確認、対話の画面と非対話の実行、セッションの記録と再開と巻き戻し、圧縮、利用者の Agent Skill の読み込み（2026-10-19 に加えた。[文脈の管理](../01-agent/01-04-context.md)の「利用者の Agent Skill」）、評価の道具である。

【方針】次のものは試作の範囲に含めない。理由は各章に書く。

- Windows への対応（[OS のサンドボックス](../03-safety/03-02-sandbox.md)）。
- MCP のクライアントとサーバ。外部の MCP サーバの道具は型とエフェクトの検査を通らないので、制限モードの性質を崩す（ADR 0344 の決定 5）。通常モードに加えるかも、試作の後に決める。
- 下位のエージェント（sub-agents）と計画のモード。小さく保つ原則（後述）による。Pi の作者も、下位のエージェントを「ブラックボックスの中のブラックボックス」として核に入れていない。計画を書く道具は評価で決める（BH-008）。
- git の道具（BH-007）。
- 役割ごとにモデルを分けること（ADR 0343）。
- 手元の重みでの推論、クラウドの基盤の認証、Apple の Foundation Models（ADR 0340）。
- IDE との連携、拡張の仕組み（プラグイン）。

### 性能の目標

【方針】性能は、次の二つで示す。値と測り方は各章で定める。

- **実行の性能**: 実行ファイルの大きさ、起動の時間、メモリの使用量（[性能](../06-impl/06-02-performance.md)）。
- **エージェントとしての性能**: Benitoite の Skill の評価の課題での成功率、検査と修正の回数、トークンの量を、同じモデルで動く主なハーネス（DeepSeek Harness、Claude Code、Antigravity の CLI）と比べる（[評価](../07-quality/07-02-evaluation.md)）。

### 設計原則

【方針】判断に迷ったときは、次の原則で選ぶ。衝突したら番号の小さい方を優先する。

1. **安全の性質を LLM の出力で崩せないようにする**。確認と OS のサンドボックスを、LLM が飛ばせない場所に置く。安全の性質を、性能や使い勝手のために弱めない。
2. **測って決める**。性能に関わる選択（道具の形、文脈の作り、依存のクレート）は、測った結果で決める。測っていない改善を主張しない。
3. **小さく保つ**。道具の数、システムプロンプトの長さ、依存のクレートを、要るものだけにする。DeepSeek Harness は評価に道具一つと一文のシステムプロンプトの最小の構成を用意し、Pi は四つの道具と約 400 トークンのシステムプロンプトを核にしている（[先行事例](../08-appendix/08-01-prior-art.md)）。
4. **LLM が見慣れた形に揃える**。道具の名前と引数と結果の書き方は、主な LLM が学習で見慣れた形にする。
5. **キャッシュを壊さない**。LLM に送る内容は追記だけで伸ばし、先頭を変えない（[文脈の管理](../01-agent/01-04-context.md)）。
6. **マージを妨げない**。Benitoite の処理系の規約（lint、依存のクレート、文書の書き方）に揃え、試作の後にどちらの判断もとれるようにする。

### 名前

実行ファイルの名前 `benitoiteh` と、モードの名前（制限モード、通常モード）は仮のものである。見直しは BH-001 で、試作の後の判断とあわせて BH-080 で扱う。
