関数型スクリプト言語 Benitoite 専用のエージェントハーネスの試作（実行ファイル名は仮に `benitoiteh`）の設計書を作りました。実装を始める前に、設計書のレビューをお願いします。

- 対象のコミット: `09dde24f92ec4768f9288e1b0448ced0f921ec08`
  （ブラウズするときは https://github.com/tecogonaz0439/BenitoiteHarness/tree/09dde24f92ec4768f9288e1b0448ced0f921ec08 を使ってください）

最初に `docs/design/00-overview/00-01-goals.md`（目的と設計原則）を読み、その後で各章を読んでください。設計書は日本語で書かれています。

### 背景

- Benitoite は Rust で実装した静的型付きの関数型スクリプト言語です。関数の型にエフェクト（`uses File.Read, Process.Run` など）を書き、処理系は実行の前に型とエフェクトを検査します。処理系のリポジトリは https://github.com/tecogonaz0439/Benitoite です。最新のリリースは `v0.0.5` で、設計書のリンクもこのタグを指しています。
- エージェントハーネスは、Benitoite のプロジェクトで事前に検討していました（v0.0.5 の `docs/archive/2026-10-09-design-first-release/` の 06-08 章と ADR 0340〜0348）。試作は、その決定を基本的に引き継ぎます。ただし、処理系のサーバモード（実行時の権限制御を持つデーモン）がまだないので、一部を変えています。変えた点は 00-01 の「事前検討との関係」と付録 08-02 にあり、設計者が承認済みです。
- 設計書が「Benitoite の docs/todo の TODO-nnn」として引いている項目は、非公開のリポジトリにあり、読めません。要点は設計書の本文に書いてあります。
- 試作の要件は次のとおりです。
  - sh や Python など、Benitoite 以外のスクリプト言語を使わせない**制限モード**と、一般的なハーネスと同じく振る舞う**通常モード**を持つ。
  - Rust で書く。
  - 実行ファイルが小さく、実行が速く、エージェントとしての性能が高い。
  - 設計から実装までを Claude Code で行い、Codex は使わない。
- 参考にしたハーネス（Codex CLI、Pi Coding Agent、DeepSeek Harness）は、それぞれ特定のコミットのソースで調べ、付録 08-01 にまとめました。

### 特に見てほしい点

優先度の高い順に挙げます。

1. **制限モードの安全の性質**（03-01・03-02・03-03・01-03）
   - LLM の出力だけで次のことができる道筋が残っていないか、具体的な手順で探してください。
     - 確認を飛ばす。
     - サンドボックスの外に出る。
     - `.bnt` 以外のファイルや、許した範囲の外のファイルに書く。
     - Benitoite 以外の言語の処理系（sh、python など）を動かす。
   - 考えられる道筋の例: シンボリックリンク、ハードリンク、環境変数、Unix ソケット、Mach のサービス、`io_uring`、許したプログラムの機能、Benitoite の処理系のサブコマンド、一時ディレクトリ、切り詰めた出力の置き場所、`web_fetch`、書いた後の検査、補助のプロセス `benitoiteh __sandbox`。
   - 設計書は、確認・道具の層・OS のサンドボックスの三層で守る形をとっています。各層の想定が妥当かも見てください。
2. **OS のサンドボックスの作り**（03-02）
   - macOS は `sandbox-exec`（Seatbelt）、Linux は Landlock と seccomp を使い、bubblewrap は使わない、という判断が妥当かを見てください。
   - Linux で「読ませない場所」と「書ける場所の中の守る場所（`.git`）」を実現する方法（BH-049）、Landlock の実行の権利と動的リンクのローダの扱い（BH-043）について、一次資料（カーネルの文書など）に基づいて意見をください。
3. **エージェントとしての性能に効く設計**（01-01・01-03・01-04）
   - 道具の形（`read`・`edit` の `old_string`/`new_string`・`bash`）、書いた後の検査、出力の切り詰めの値、文脈の構成とプロンプトのキャッシュ、圧縮の作り方が妥当かを見てください。
   - より良い代わりの案があれば、根拠とあわせて示してください。
4. **提供者の層**（02-01）
   - Anthropic の Messages API、OpenAI の Responses API、OpenAI の Chat Completions API の扱いに、事実の誤りや抜けがないかを見てください。
   - 【要検証】の事項（BH-030 の Responses API の欄、BH-031 の DeepSeek の推論の文の扱い）について、公式の文書で確かめられることがあれば、出典つきで教えてください。
5. **処理系への要望**（04-01 の「処理系への要望」、BH-022〜BH-026）
   - Benitoite の `v0.0.7` で処理系に加える候補として 5 件を挙げています。レビューの後に内容を固めて、処理系の側に実装を依頼する予定です。
   - 過不足、優先度、出力の形の案について意見をください。
6. **章どうしの整合と、実装プランを作れる十分さ**
   - 同じ規則が章によって違って書かれていないか、見てください。
   - 実装者がこの記述だけでは判断できない箇所がないかも見てください。
7. **性能の目標と段階の計画**（06-01・06-02・00-03）
   - 実行ファイル 8 MiB 以下などの目標と、依存のクレートの選び方が現実的かを見てください。

### 報告の形

- 日本語でお願いします。
- 指摘は、重いものから順に番号を付けて並べてください。各指摘には次のことを書いてください。
  - 場所（ファイルのパスと見出し）
  - 問題点
  - 重さ（実装の前に直すべき／実装の中で直せばよい／好みの範囲）
  - 修正案
- 外部の事実（API の仕様、OS のサンドボックスの機能、クレートの機能など）を挙げるときは、出典の URL を添えてください。確かめられなかった事実は、そう明記してください。
- 未決事項（`BH-nnn`）について意見があれば、番号を添えてください。
- 最後に、全体の所見（実装に進めるか、先に直すべき点は何か）を短くまとめてください。
- 設計書の文章の好み（言い回しなど）は、意味の誤解を招く場合に限って指摘してください。
