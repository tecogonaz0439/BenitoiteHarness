# 実装の契約、段階のゲート、性能・評価、BHへの意見

この文書は、[指摘一覧](01-findings.md)を実装プランへ反映するための補足です。別の未採番の重大指摘を増やすものではありません。設計上の問題は33件の指摘番号へ対応させ、以下は具体化の案として示します。

## 1. 先に固定する設計判断

大枠を作り直す必要はありません。しかし、次の判断を実装者ごとの解釈に任せると、章ごとに違う安全境界や履歴形式ができてしまいます。

| 判断 | 先に決める内容 | 指摘 |
|---|---|---|
| Linuxの完全な制限モード | BH-049の方式、必要ABI、使えない環境での起動拒否 | 02〜04、16 |
| 親の代理操作 | 診断、道具、snapshot、復元、spillを通す共通のファイル操作 | 01、05、11、17 |
| 実行の単位 | 検査した入力の固定、処理系の同一性、子孫の終了条件 | 08、09、12 |
| 承認の単位 | 現在のポリシー世代、一回の要求、通常モードの外部実行の再確認 | 06、10、11 |
| 保存の単位 | 元の提供者項目と順序、wire ID、確定前／実行中／完了の記録 | 13、15、19 |
| 圧縮の単位 | 提供者別のthinking保持、独立した復旧要求、完結した道具交換 | 14、18 |
| 出力の予算 | 上限前のprefix、実際のtail、打ち切り表示、spill総量 | 21、22、26 |
| 検証の単位 | 機能×OS能力ごとの合格条件と証跡 | 28 |

ここで求めるのは、実装の細部をすべて先に書くことではありません。誰が何を保証するか、失敗をどの状態として返すかを決めることです。

## 2. Claude Codeの実装プランへ渡す契約案

型名は仮です。複数のcrateへ分割すること自体を要求するものでもありません。既存のライブラリと実行ファイルの構成の中で、責務を分離できれば十分です。

### 2.1 PolicySnapshot

一回の道具または実行が参照する、不変の権限のまとまりです。

```text
PolicySnapshot
  epoch
  mode
  project_root_identity
  readable_roots
  writable_roots
  protected_objects_and_names
  allowed_executable_identities
  ip_network_policy
  external_ipc_policy
  approval_scope
  state_root_identity
  scratch_root_identity
```

文字列をcanonicalizeした結果だけで全体を表現せず、実際のディレクトリや実行ファイルとの結び付きを持たせます。`create_project`、許可設定の変更、ルートの変更ではepochを進め、旧epochの承認や書き込み用handleを新しい範囲へ持ち込まないようにします。

modeによって意味の違う項目を、同じ空配列やfalseに押し込めない方がよいでしょう。例えば「ネットワーク無効」と「OSでまだ実現できていない」は別の状態です。

### 2.2 SafeFs / ReadBroker / WriteBroker

親の道具による操作、診断の抜粋、巻き戻しを一つの規則に従わせます。操作の入口ごとにcanonicalizeと検査を独立に書く方式は避けます。

```text
ReadResult
  authorized_source_id
  content_version
  complete_or_truncated
  range_returned
  continuation

WriteResult
  destination_identity
  previous_content_version
  new_content_version
  post_check_status
```

書き込みには、読んだ版を期待値として渡し、検証と実際の操作を可能な限り同じhandleに結び付けます。LinuxのFD相対操作とmacOSの実装方法は別でも、外から見える成功条件は揃えます。

ハーネス自身が設定や履歴を読むことは、LLMの `read` が同じ場所を読めることを意味しません。「内部専用の読み書き」と「LLMの代理操作」を型やAPIで分け、内部用途にだけ必要な権限が道具へ漏れないようにします。

### 2.3 CheckedExecution

承認前に確定する検査結果と、承認後に動かす入力を結び付けます。

```text
CheckedExecution
  interpreter_identity
  input_manifest
  target_set
  expanded_effects
  check_completion
  policy_epoch
  immutable_execution_input
```

承認のキーをすべて内容ハッシュに変える必要はありません。現在の「エフェクトの種類についてセッション中に承認する」意味は維持できます。ただし、一回のrunで検査したものと違う入力を使うこと、testの対象集合が変わることを許さない契約は必要です。

### 2.4 ApprovalDecision

LLMから返された文字列を、そのまま承認として認めない構造にします。

```text
ApprovalDecision
  request_id
  policy_epoch
  displayed_scope_digest
  source: trusted_interactive_input | explicit_cli_policy
  decision
  validity: one_shot | explicitly_defined_session_scope
```

このdigestは表示内容の同一性を確かめる内部の識別子であり、暗号署名を導入しなければならないという意味ではありません。承認待ちに入る前のキューに残った入力、古い画面での選択、子の出力に紛れた応答は、現在のrequestに対応する判断として使わないようにします。

### 2.5 ProviderTurnとCompactionPlan

提供者の元の項目、共通の表示用データ、実行可能な道具引数を別に持ちます。具体案は [提供者の補足](03-api-and-interpreter.md) に示しました。

圧縮には、単に文字列の要約を返す関数ではなく、次の状態が必要です。

```text
CompactionPlan
  source_history_revision
  retained_complete_turns
  reasoning_replay_policy
  summary_input_budget
  summary_output_budget
  resulting_prefix_identity
  disposition: replace_after_success | keep_original_on_failure
```

要約の失敗や取消で、元の履歴を途中まで消さないようにします。DeepSeek用の新規会話への移行、Anthropic用のprefix変更などを、同じデータ削除処理へ無条件に流さないことが重要です。

### 2.6 JournalとSnapshot

ユーザー向けイベントを公開する形式の安定性と、内部の再開形式の正しさは別です。BH-012がP5のままでも、内部形式はP1のうちに版と状態遷移を決めてください。

```text
ToolLifecycle
  planned -> approved -> starting -> running -> completed
                                     |            |
                                     +-> uncertain+
```

`uncertain` は、クラッシュなどで副作用の有無を確定できない状態です。「完了イベントがないから未実行」として自動再実行しないようにします。

snapshotの各pathは、少なくとも `present(blob)`、`absent`、`not_captured(reason)`、`outside_scope` を区別します。容量超過や読み取り失敗をabsenceへ変換しないこと、現在のポリシーで復元できないものを強行しないことが必要です。

### 2.7 BoundedOutput

出力上限は各道具に散らさず、共通の収集器に持たせます。

```text
BoundedOutput
  bytes_observed
  bytes_retained
  prefix
  tail_ring
  spill_reference
  loss: none | middle_dropped | collection_stopped | disk_limit
  source: stdout | stderr | tool
```

「保存した最後の部分」が「実際の出力の最後」と一致するかを明示できます。stdoutとstderrの総順序を作れない場合は、作れないことを型に残し、都合のよい一つの時系列へ見せかけない方がよいでしょう。

## 4. 段階計画への提案

[00-03 ロードマップ](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/00-overview/00-03-roadmap.md) のP0〜P6は、大筋で維持してよい構成です。変更するのは、完了条件の具体性と、後の機能追加で再実施する検査です。

| 段階 | 維持する内容 | 追加する完了条件 |
|---|---|---|
| **P0 準備** | Rustの雛形、依存とサイズ、BH-010/043/049 | ダミーの子を実際に隔離する縦の試験。必要ABI・名前空間・FD・env・exec・IPCの結果を残し、機能不足では起動拒否する。unsafe方針をここで確定 |
| **P1 核** | 二つのアダプタ、基本道具、exec、履歴 | 元の提供者項目の損失のない保存、strict変換、途中切断、実行状態journal、親のSafeFsを通すこと |
| **P2 制限モード** | Benitoite連携、承認、OS隔離、自動check | 偽診断、子孫、hardlink、test対象、ローダ、Unix/Machを含む試験表に合格。成功しないOS構成では制限モードを公開しない |
| **P3 通常モード** | bash、Responses、プロジェクト指示 | サンドボックス外実行を一回の判断に結び付ける。可変スクリプトの承認キャッシュ試験。送信先とプロジェクト設定の扱いを明示 |
| **P4 対話・長い作業** | TUI、圧縮、再開、巻き戻し、project、web | 端末の無害化、提供者別の圧縮、復元、ルート変更、SSRF、spillの試験を再実施。P2で一度通ったことを安全の証拠に使い回さない |
| **P5 評価** | 課題比較、各選択肢、性能 | 比較の固定条件、失敗分類、繰返し、キャッシュ・費用の内訳、失敗時の証跡を残す |
| **P6 判断** | マージ・独立・配布 | 実証した保証と未対応条件を分けて説明する。サーバモード実装後のBH-081は独立して維持 |

P0の検証は、ハーネス全体を先に実装するという意味ではありません。制約を読み込み、ダミーの静的子プロセスを起動し、許可／拒否を観測する最小の補助プロセスで十分です。ここに本物のLLMは不要です。

Git worktreeを分けて並行作業する方針は維持できます。ただし、SafeFs・PolicySnapshot・ProviderTurn・Journalの契約はオーケストレータが先に一つに固定し、別々のサブエージェントが似た名前の異なる型を作ることを避けてください。

## 5. 道具の形とエージェント性能

### 5.1 維持を勧める初期設計

小さな道具集合、exactな `old_string/new_string`、一回ごとのshell、書いた後の検査、安定したsystem/tools、全文ではなく必要な範囲を読む方式は、いずれも試作の出発点として妥当です。実測なしに、より複雑な道具へ置き換える根拠はありません。

ただし、各方式の「失敗したときに次の一手へ進める」性質を評価する必要があります。

| 道具・機能 | 初期案への評価 | 優先する改善 | 比較は後でよいもの |
|---|---|---|---|
| `read` | 行範囲と上限を持つのはよい | 長い一行の続き、返却範囲、完全性の表示 | 行番号の有無・表現 |
| `edit` | exact一致は予測しやすい | 曖昧一致を拒否し、読んだ版との一致を検査 | 複数変更の一括適用、patchとの比較 |
| `write` | 全置換の意味が明快 | 未読・読取世代・サイズ超過の扱い | 小変更を常にeditへ強制するか |
| `bash` | 一回ごとのshellは状態が少ない | 子孫の回収、真正なtail、承認の一回性 | 常駐shellの便益と状態漏れ |
| 自動check | 修正の往復を減らせる可能性 | 「検査できた対象」を返す | 毎回／書込群の後／無効の比較 |
| 読み取りの先行実行 | 待ち時間を減らせる可能性 | 完成した引数、順序、取消・世代の整合 | 並列数の最適値 |
| scratch | Benitoiteへ計算を任せる道具としてよい | 実行と読取の範囲を明示 | プロジェクトimportを可能にする別モード |
| `web_fetch` | 再解決・リダイレクトを考慮している | IP固定とTLSホスト名、復号後上限、総量 | 抽出・要約の自動化 |

scratchからプロジェクトのモジュールをimportできないことは、安全境界を明確にする設計上の選択です。それをバグとは数えません。ただし、計算用scratchと、既存コードの検証用runの使い分けを道具の説明と模擬課題で確認するとよいでしょう。

### 5.2 exact editの代案

最初からfuzzyな置換を入れるより、exact一致を維持したまま、複数の置換を一回で渡す案を比較対象にすることを勧めます。適用の前に全件を検証し、一件でも合わなければ全件を適用しない形です。

ただし、複数ファイルの完全な原子更新は別の問題です。最初は単一ファイル内の一括編集に限定する、または複数ファイルでは「全件を検証してから順に適用、失敗時の結果を明示」とするなど、実際に保証できる単位を選んでください。単に「transaction」と名付けてクラッシュ時まで原子的だと見せることは避けます。

この案は好み・評価の範囲です。安全境界の穴を直すための必須機能ではありません。

### 5.3 自動checkの返却形式

改善のためには、成功／失敗だけでなく、次のような結果があると役立ちます。

```text
post_check
  status: passed | failed | skipped | partial
  checked_entries
  edited_sources_covered
  edited_sources_not_covered
  diagnostics
  elapsed
```

Benitoiteのentryと依存の関係上、あるmainのcheckが通っても、編集したすべての独立したファイルを検査したことにはなりません。逆に、自動checkが構文エラーを返しても、LLMに修正を継続させる材料であり、成功したwriteまで失敗扱いにして同じ書込を再試行させるべきではありません。

「書込が成功した」「その後の検査が失敗した」を別々に返すと、道具の意味が安定します。

### 5.4 圧縮の内容

要約には、実際の証拠に結び付く項目を残すことを勧めます。

```text
作業の目的 / 制約
現在のプロジェクトとポリシー世代
変更したファイルと現在の内容の識別子
実行した検査・テストと、その結果
未完了の作業 / 既知の失敗
次に必要な判断
参照すべき保存済み出力
```

承認の文章を要約へ書いても、承認状態の正本にはしません。要約に「すでに承認済み」とあっても、現在のPolicySnapshotと承認台帳にない権限を増やさないことが必要です。

文脈長の見積もりは、通常の予防線と、既に超過したときの復旧を分けます。後者は同じ大きな履歴に要約依頼を足すのでなく、上限内へ選別した別の要約入力を作ります。要約の品質と、提供者別のthinking再送規則の両方を試験してください。

## 6. 8MiB・起動・メモリの目標

参照: [06-01 クレートの構成](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/06-impl/06-01-crate-structure.md)、[06-02 性能](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/06-impl/06-02-performance.md)。以下は測定計画の提案であり、実測値ではありません。

### 6.1 目標の現実性

**8MiBを試作の目標として維持することに反対しません。ただし、依存を測っていない現時点で、達成可能と保証できる根拠はありません。** 逆に、同期HTTPやRustで書くことだけから不可能と断定する根拠もありません。

まず最終配布と同じ機能を有効にした最小の縦の構成で、TLS、証明書検証、JSON、TOML、regex/走査、端末、OS隔離、埋め込み文書を段階的に足して測るのがよいでしょう。空の実行ファイルだけが小さいことは、8MiBの実現性の証拠になりません。

| 候補 | 選択への意見 | P0で観測するもの |
|---|---|---|
| `ureq` と同期スレッド | 小さな制御構造という狙いは合理的 | ストリーム取消、DNS・接続・受信の各上限、実際の依存サイズ |
| rustlsと暗号実装・証明書検証 | 暗号化の正しさを削ってサイズを合わせない | crypto providerの重複、platform verifier、対象OSのビルド、追加依存 |
| regex・ファイル走査 | `grep/glob` に適した出発点 | 不要な機能、重複した走査、巨大行、除外規則のコスト |
| JSON/TOML | 独自パーサへ置換して縮める優先度は低い | 保持するDOMと文字列のコピー、履歴の累積RAM |
| 端末層 | 自前の軽い描画は試作として成立 | Unicode、制御文字、再描画、長い出力での正しさ |
| rustix等のOS層 | 必要APIを正しく使えることを優先 | 対象ごとのAPI、unsafe方針、OS機能の導入試験 |
| Skillの埋め込み | オフライン・固定版という利点がある | 非圧縮と圧縮の差、展開時のRAM、処理系版との差 |

ureqのbody timeoutは、必要な「データが止まった時間」の上限と同義ではありません。BH-010はサイズと独立した実現性試験として残す必要があります。[S-R03]

### 6.2 測定する単位

| 指標 | 固定する条件・追加する記録 |
|---|---|
| 実行ファイル | target、Rust toolchain、lockfile、features、release設定、strip、圧縮前のbyte数。処理系・外部補助ファイルのサイズは別欄 |
| `--version` | warm/coldを区別し、起動直後の終了まで。遅延初期化で不要なTLS・Skillを読み込まないことも観測 |
| 対話起動 | 画面描画完了と入力受付可能の時点。処理系versionを含む区間を明示 |
| 最初の要求送信 | HTTP要求を作るまで／送信開始／最初のbyte受信を分ける。設計の30msの区間を固定 |
| idleメモリ | 初期化後の静止点で現在のRSSを測る。最大RSSとは別 |
| 200ターン | ターン数だけでなく、総本文量、推論量、tool結果、JSONLサイズを固定 |
| 描画16ms | 受信、整形、UIキュー、描画を分けて時刻を取る。大量deltaでもキューが伸び続けない |
| grep 1万ファイル | 総byte数、行長、拡張子、除外数、一致数、filesystem cacheの状態を固定 |
| 子の起動・check | ハーネス起因の時間と処理系起因を分け、エージェント全体の壁時計も併記 |

最大RSSを測る道具を使うこと自体はよいのですが、それをidle RSSの測定結果と同じ欄に入れないでください。性能目標の対象が違います。

### 6.3 予算超過の扱い

8MiBに届かない場合は、まず重複依存、不要feature、埋め込み内容、生成物を調べるべきです。安全機能やTLS検証を無効にして達成した8MiBは、同じ製品の達成値ではありません。

常駐20MiBや長いセッション100MiBは、並列数・出力上限・snapshotの方式と同じ予算表で検討します。個々の道具が上限以下でも、四つ同時に返し、native履歴とUI文字列に複製し、要約用に連結すれば、総量は別に増えます。

セッションやspillの保持期間を定めるだけでなく、byte総量と一回の入力量の上限、回収失敗時の動作を追加するのがよいでしょう。空き容量不足で安全な実行ログを保存できないときは、黙って実行を続けるかどうかも決める必要があります。

## 7. 評価の設計

参照: [07-02 評価](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/07-quality/07-02-evaluation.md)。同じモデルで比べる方針、模擬提供者でハーネス自体の性能を測る方針は維持を勧めます。

### 7.1 三つの評価を分ける

| 評価 | 目的 | 主な条件 |
|---|---|---|
| 安全性の適合試験 | 禁止操作が通らないことを確認 | 固定fixture、全件の合否、OS/ABIごとの証跡 |
| ハーネスの実行性能 | 実装自体の遅延・資源消費を比較 | 模擬SSE、固定道具出力、ネットワークの揺れを除く |
| エージェントの課題達成 | 道具と文脈の設計の効果を比較 | 同じ課題・モデル条件、複数試行、費用と時間 |

安全性は、平均成功率に埋め込むべきではありません。例えば一回でも許可外へ書ける構成は、課題達成率が高くても、その安全要件については不合格です。

### 7.2 課題ごとに固定するもの

```text
task_id / task_revision / initial_tree_hash
expected_outcome / expected_restriction
runtime_version / runtime_hash
provider / endpoint / model / effort / capability_profile
system_and_tool_schema_hash
mode / permissions / approval_policy
context_limit / output_limit / time_limit / cost_limit
cache_policy / warm_or_cold
attempt_number
```

課題の初期木は試行ごとに戻します。前回の成功結果やsnapshotを次の試行へ混ぜないようにします。キャッシュを許す比較と、初回の比較も分けます。

旧記録を引く場合は、モデル・system・道具・処理系・上限が揃っているかを確認します。揃わない記録は背景情報として使い、新実装との差の因果的な証拠とはしないことを勧めます。

### 7.3 失敗の分類

単なるsuccess/failだけでなく、少なくとも次を区別すると、改良先が分かりやすくなります。

| 分類 | 例 |
|---|---|
| 課題の誤解・実装の誤り | 間違ったアルゴリズム、要求の取り違え |
| 道具の利用失敗 | exact edit不一致、未読の書込、長い行の残りが取得できない |
| 検査の不足 | 自動checkは成功したが編集した独立ファイルを検査していない |
| 権限による意図した停止 | 制限モードでのshや許可外の操作を正しく拒否 |
| ハーネスの不具合 | API履歴不整合、取消不能、復元誤り、失われたtool結果 |
| 外部要因 | 提供者の一時エラー、モデルの利用不能、環境の障害 |
| 予算による終了 | 時間、トークン、費用、メモリ、ディスクの上限 |

v0.0.5の課題を使う場合は、制限モードで当然拒否する操作が含まれる課題を、事前に期待結果として分類してください。実行後に都合よく「これは対象外」と付け替えると、比較が不透明になります。

### 7.4 回数と比較

各条件3回は、明白な失敗を見つける探索としては使えます。しかし、僅かな成功率の差から優劣を確定するには弱い設計です。最初に全課題を少数回で回し、差の出た課題と代表課題を追加反復する二段階にすると、費用を抑えながら不確かさを見られます。

報告には成功数／試行数、中央値と分布、個別失敗を残します。同じeffort名でも実際の計算量が完全に同じになると仮定せず、提供者が返した使用量と壁時計を記録します。

行番号、自動check、計画の道具、圧縮量、edit形式を同時に変えると、どの変更が効いたか分からなくなります。初期比較では一つずつ変更し、最終候補の組合せを追加で確認するのがよいでしょう。

## 9. 全体の所見

実装の雛形とP0の検証には進めます。設計の大枠を止めるより、**Linuxの完全な隔離、親の代理操作、承認と子孫の寿命、損失のない提供者履歴**を短い設計判断として先に固定することを勧めます。

その後、P1/P2を小さく縦に実装し、偽診断・Unix IPC・hardlink・ローダ・取消の試験を、機能を足すたびに回してください。性能目標と道具の好みは、同じ安全性を満たす候補どうしで測って決めるのがよいでしょう。
