# 制限モードの安全性 — 攻撃経路、OS方式、検証ゲート

この文書は [指摘一覧](01-findings.md) の安全性の根拠を補います。設計の内容を実行済みの実装と取り違えないよう、各経路に前提と判定を付けます。

## 1. 結論と保証の読み方

三層に分ける方向はよいものです。ただし、三つとも同じ操作を重複して禁止するわけではありません。確認は「利用者が認めた範囲」を確定し、道具層は「親が代理で何をするか」を限定し、OSは「既に走り始めた子と子孫」を制約します。子の出力を親が解釈する入口では、OSの制約は親の代理操作に移りません。

| 境界 | 信頼してよい入力 | 信頼してはいけない入力 | 必須の性質 |
|---|---|---|---|
| 利用者の確認 | 本物のUI/CLIが受けた、対象要求に対応する選択 | LLMの説明、出力に含まれる「承認済み」、古いキー入力 | 表示した範囲と実行ポリシーが一致する |
| 道具の呼び出し | 検証済みの型、現在のポリシー | path、JSON、URL、コマンド、診断に書かれた位置 | 入力が親の権限へ直接昇格しない |
| 子の実行 | 固定した処理系、適用に成功したOSポリシー | スクリプト、環境の追加値、子孫の要求、実行結果 | 実行後も範囲を越えず、完了後に権限が残らない |
| 状態の保存と復元 | ハーネスが所有する有効な記録 | リポジトリ中のファイル、途中のJSONL、偽のsnapshot名 | 記録がないことを未実行・不存在と誤認しない |

R1〜R5は、次のように限定して読む必要があります。

- R1は主として **execを許すファイル** の保証です。許可したネイティブプログラムが内部に任意の言語を実装していないことまで、ファイル名やELFヘッダだけで証明するものではありません。
- R2の `.bnt` 限定は **親の道具による編集** の保証です。承認した `File.Write` の実行が範囲内へデータや設定を書くことは、既に許容されています。
- R3の承認は **エフェクトの種類** を単位にしています。同じエフェクトで内容が変わった実行を毎回再確認する設計へ戻すことは求めません。ただし、一回のcheck・抽出・runの対応は必要です。
- R4のネットワーク許可は、親のweb_fetchとは別の能力です。またIP通信を許しても、外のUnix/Machサービスへ代理実行を依頼できるようにしてはいけません。
- R5は情報の持ち出しを完全に防ぐ保証ではありません。既定の秘密パターン以外の平文や、利用者が明示的に認めた読み取りからの出力は残ります。ここで問題にするのは、禁止したはずのものを親が代わりに読む経路です。

これらの区別は、[03-01](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/03-safety/03-01-security-model.md) と [03-03](https://github.com/tecogonaz0439/BenitoiteHarness/blob/09dde24f92ec4768f9288e1b0448ced0f921ec08/docs/design/03-safety/03-03-approval.md) の承認済みの例外に沿うものです。

## 3. 具体的な手順

### A-01: 診断JSONからの代理読み取り

**安全な試験用の前準備**として、試験担当者がプロジェクト外の専用ディレクトリに、秘密に見える名前のダミーファイルを作ります。実際の鍵や認証情報は使いません。例えば `/tmp/bh-review-fixtures/outside/.ssh/id_ed25519` に `DUMMY_DO_NOT_SEND` と一行だけ書きます。

LLMが行う操作は、Console.Writeだけを使うscratchを要求することです。そのスクリプトから `Console.writeErrorLine` で、次のようなJSONを一行出します。以下は診断のペイロード例であり、実行した結果ではありません。

```json
{"kind":"check","severity":"error","code":"E0401","message":"fixture","primary":{"file":"/tmp/bh-review-fixtures/outside/.ssh/id_ed25519","start":{"line":1,"column":1,"offset":0},"end":{"line":1,"column":17,"offset":16},"label":"fixture"},"secondary":[],"notes":[],"helps":[]}
```

1. scratchの静的効果はConsole.Writeだけなので、既定の確認不要範囲に収まります。
2. 子は実際の対象ファイルを読みません。対象パスは単なる出力文字列です。
3. 04-01の具体処理だけを素直に実装した親が、このJSONの位置の行を追加取得すると、子の権限より広い読み取りを行います。
4. 診断に添えられたダミーの内容がLLMの要求へ入ると、読み取り禁止の回避になります。

00-02の総則を実装で強制していれば、3で拒否されるべきです。したがって、この試験は総則が具体処理に確実に接続されていることを確かめる試験です。`kind` や `code` を本物の一覧に制限しても、出力は偽造できます。単に専用FDへ変える場合も、実行するスクリプトや許可コマンドがそのFDへ書けるなら出所の認証にはなりません。[S-B01] [S-B02]

**推奨する結果**: パスはエスケープした文字列として表示可能。抜粋は付けず、`source_excerpt_unavailable: outside_read_scope` 等とする。ファイルの実際の内容はログにもprovider要求にも現れない。

### A-03/A-04: Unixソケットを使う外部代理

ネットワーク無効時の試験では、試験用の小さなネイティブ送信プログラムを、検証用設定でだけ許可します。このプログラムは別のスクリプト言語を含まず、Unixソケットへ一定のダミー値を送るだけにします。

外側には、マーカーの受信だけを記録するUnix datagramの試験サーバを置きます。送信プログラムが `socket(AF_UNIX, SOCK_DGRAM, 0)` と宛先付きの `sendto` を使う場合、接続用の `connect` を呼ぶ必要はありません。現設計の拒否一覧だけなら、この系統が漏れる候補になります。実際のローカルサービスを操作する必要はありません。[S-K07]

ネットワーク有効時は、まず外部へのダミーHTTPS通信が許された構成を作り、同時に外部Unix stream/datagramが拒否されたままであることを検証します。承認画面で示したのがHttp.Connectであっても、外側のD-Bus等に接続できれば、外側で動くサービスの権限が関わります。外側のサービスは子のLandlock/seccompを継承しません。bubblewrapの文書も、D-Busソケットを見せる危険を明記しています。[S-K09]

**重要な条件**: このレビューでは、既定のBenitoiteだけから任意のUnix IPCを行うプログラムを実行していません。許可コマンドの選び方に依存する経路です。ただし、その条件があるからこそ「IPを許しても外部IPCは許さない」というOS層の独立した契約が必要です。

### A-06: あらかじめあるhardlink

試験担当者が、同じファイルシステムの外側のダミー `outside/keep.txt` と、内側の `project/alias.bnt` を同一ファイルのhardlinkにします。LLMに外側のリンクを作らせる必要はありません。その後、承認したFile.Writeを使うBenitoiteスクリプトから内側へ追記する試験をします。

親のwrite/editがatomic renameで置換した場合とは違い、通常の追記は同じファイルの実体を変更する操作です。Fileの公開APIには追記とwriterがあるため、道具のhardlink検査を通らない実行時の経路を別に扱う必要があります。[S-B04]

「外側へ新しいリンクを作れなかった」という試験だけでは、この初期状態を説明できません。Landlockの自己試験にはlink/renameの権利の試験がありますが、本製品のポリシーと初期状態に対する合格証拠は別途必要です。[S-K06] [S-K08]

**選べる仕様**: 既存の複数リンクを見つけたら制限モードを起動しない／作業領域を別実体へコピーする／保証をパス名だけに限定して説明し直す。最後の案は、利用者が期待する「外のファイルを変えない」より弱いので推奨しません。

### A-07/A-08: パスとソースの時間差

同時変更の試験では、外部の秘密を狙わず、ダミーの親ディレクトリをrenameして入れ替えます。最終要素だけのO_NOFOLLOWでは、その前に検査した途中のディレクトリが同じものかを固定できません。

ソースについては、checkが終わってから承認を待つ間に、入口またはimport先を変えます。実行側が単に同じ文字列のパスを開き直す場合、確認した対象と異なります。後で実行する版に対してエフェクトを抽出し直していても、そのさらに後の変更窓は残ります。

人間のエディタによる変更も含めて安全に扱える設計にすれば、LLMが残存子孫を利用する場合にも強くなります。ただし、同時変更主体が一切いない環境で、単一の逐次呼び出しだけから必ず競合を起こせると断定してはいません。

### A-21: 処理系の別サブコマンド

v0.0.5には、run/check/test以外にfmt・skill・packageがあります。道具から起動しないことと、Process.Runを承認した子が処理系へそれらを渡せないことは別です。[S-B05]

この区別を理由に、全てを新しい穴とは扱いません。例えば次のように評価します。

| 試行 | 期待する結果 | 理由 |
|---|---|---|
| `Process.shell`が/bin/shを起動 | 拒否 | shをexec許可しない |
| 子のBenitoiteが他の.bntをrun | 許可範囲で成功しうる | 既述のProcess.Runの例外 |
| 子のfmtがworkspaceを書き換える、File.Writeなし | 拒否 | 書込可能なのは子tmpのみ |
| 子のfmtがworkspaceを書き換える、File.Writeあり | 範囲内なら許容 | 非.bnt制限は道具層の規則 |
| `skill install --user`がホームの外部位置に書く | 拒否 | 子のOS書込範囲外 |
| `skill install --project`が.git等の保護対象へ影響 | 保護対象への操作は拒否 | 別サブコマンドも同じOSポリシー |
| packageが通信する | ネットワークの承認に従う | サブコマンド名でIP権限を得ない |
| `benitoiteh __sandbox`に別の方針を渡す | 親を代理にせず、既存制限を弱めない | 子の新しいexecで親の権限へ戻らない |

runのスクリプトパス以後の引数は処理系ではなくスクリプトへ渡す仕様です。ハーネスは常に固定したサブコマンドと検証済みの絶対パスを別々のargvとして組み立て、シェルに再解釈させないことを契約にしてください。[S-B05]

## 4. BH-043 — Landlock EXECUTEと動的ローダ

### 4.1 一次資料で言えること

Linux v6.12の公開ソースでは、次の経路を確認できます。

1. `fs/exec.c` の `do_open_execat` は実行用openとして対象を開きます。[S-K04]
2. `fs/binfmt_elf.c` はPT_INTERPのローダを `open_exec` で開きます。[S-K05]
3. `security/landlock/fs.c` は実行用のopenにLANDLOCK_ACCESS_FS_EXECUTEを要求します。[S-K03]

この組み合わせから、動的ELF本体だけにEXECUTEを与え、PT_INTERPのローダを与えない構成では、実行を完了できない理由が説明できます。これは最新版全ての実装を実機で試したという意味ではありませんが、設計の懸念を支える固定版のソース上の根拠です。

一方、Landlockの実行権利と、通常の読み込み後の実行可能mmapは同じではありません。[S-K01] ローダ自体の直接実行を許すと、ユーザ空間のローダが読み取り可能な別のELFを読み込む経路を考慮しなければなりません。したがって、**「動的ローダも許せばよい」は実行ファイルの許可一覧を守る解決ではありません**。

### 4.2 設計判断への意見

試作のLinux制限モードを、静的な処理系と検証済みの静的コマンドに限定する判断は妥当です。外部プロセス方式も、サイズと隔離境界の両方で維持する価値があります。

ただし、PT_INTERPがないことは「kernelが別ローダを自動起動しない」ことを確かめる検査です。それだけで、ファイルが実行時に別のコードを読み込まない、あるいは別言語を解釈しないことまでは保証できません。たとえば、ローダ自身のELF、内蔵VMを持つネイティブプログラム、設定によって処理を委譲するプログラムの意味までは別の問題です。

既知の処理系名・ローダ名の拒否は有用な誤設定防止ですが、一般的な意味の証明ではありません。別名へコピーした同じファイルを検査する試験も用意し、利用者が登録時に担う確認範囲を明示してください。最初の許可コマンドを少数に固定する方が、長い名前の拒否一覧を安全境界とみなすより説明しやすくなります。

### 4.3 P0の試験セット

| 試験 | 期待/確認点 |
|---|---|
| 静的な許可ELF | 実行成功 |
| 静的な未許可ELF | exec拒否 |
| 許可した動的ELF、ローダEXECなし | ローダ段階の失敗を確認 |
| 動的ELFとローダの両方を許可 | 成功条件を確認した上で、次行の危険を検証 |
| ローダを直接起動し、未許可ELFを渡す | 許可設計の破綻候補として試す。本番ではローダを許可しない |
| ローダの別名・hardlink | 名前だけの拒否に依存しないことを確認 |
| shebangの.bnt、shのwrapper | 許可プログラムとして登録を拒否 |
| 許可プログラムと同名のworkspaceファイル | 実体の許可一覧により拒否 |
| execveとexecveat、FD経由、memfd | 経路ごとに実測。匿名実体の実行拒否を未検証のまま断定しない |
| 許可ファイルのsymlink変更・実体の置換 | どの実体を起動したかを追跡し、権限が広がらない |
| 許可プログラムの環境・設定・plugin | 実行時の追加コードの読み込みを含めて評価 |

memfdや全てのexecveat変種について、このレビューだけで通る/通らないとは結論していません。BH-043の合格条件に含めるべき未検証項目です。

## 5. BH-049 — 読み取り禁止と保護ディレクトリ

### 5.1 Landlock単独で表せること／表せないこと

親ディレクトリへの許可はその下へ及びます。同じrulesetに子の「許可しない規則」を置く操作はありません。複数の規則層を掛ける場合も、各層が表現できる正の許可の範囲を理解する必要があり、「後からdenyを足す」の代わりにはなりません。[S-K01] [S-K08]

たとえば、既存の通常ファイルだけに書き込みを許し、プロジェクト根では新しいファイルを作らせない仕様なら、正の列挙だけで狭い構成を作る余地があります。しかし、任意の新しい.bntやデータを根に作らせながら、将来の `.git` だけは作らせないという現在の要求とは異なります。

書き込み許可を設定するときは、WRITE_FILEとTRUNCATE等の別々の権利を扱うことも必要です。文書上の「読み取り専用」が、実際のbitmaskでも切り詰めを禁止していることを確認してください。ABIに対応しない権利を黙って落としたポリシーを、同じ保証と表示してはいけません。[S-K01]

### 5.2 選択肢の比較

| 案 | 保つもの | 追加の負担／制約 | レビュー意見 |
|---|---|---|---|
| Landlock + seccompだけ、保証を狭める | 小さい実装、外部依存なし | 全体readからの除外と任意作成下の保護名を、そのまま保てない | 現在の保証を変える承認が必要 |
| 自前のnamespace/mount + Landlock + seccomp | 元の目標へ近づける | mount構成、権限、FD、子孫、非存在mountpoint、safe API、ABIの監査 | P0で成立条件を決める第一候補 |
| bubblewrap等 + Landlock等 | 名前空間構成を既存実装へ委ねる | 配布/導入/版の管理。ポリシー自体は自分で設計 | 不採用を絶対視せず、P0の比較対照にする |
| 対応するmacOSから開始し、Linux制限モードは拒否 | 嘘の安全保証を出さない | Linuxでの試作機能が遅れる | P0で他案が成立しなければ妥当な切り方 |
| 子の作業領域をコピー/overlayへ隔離し、安全に反映 | hardlink等も扱いやすくなる可能性 | 変更反映、root/import、性能、parent viewの設計が大きく変わる | 中期候補。簡単なbind案と同一視しない |

bubblewrapは、与えた引数から隔離環境を作る道具であり、自動で完全なセキュリティポリシーを作るものではありません。外部ツールを採れば本報告のIPCやread/writeの問題が消えるわけではないことにも注意が必要です。[S-K09]

### 5.3 自前のmount方式で先に解くべき細部

**秘密と保護対象の区別。** 秘密を読み取り専用にするだけでは読めます。秘密を隠すなら、子から見る位置を空の別のオブジェクトにするなど、読み取りそのものを失敗させる構成が必要です。保護したい.gitを読む必要がある場合は、秘密の隠し方とは異なる構成になります。

**まだない対象。** 存在しない `.git` に、そのままmountを置くことはできません。mountpointをどこに作るのか、ホストのプロジェクトへ勝手に空の.gitを作るのか、私有の上位ビューを作るのか、を決める必要があります。ホストの.gitの有無はGitの動作に影響するため、予約用ディレクトリを作る案は単なる内部実装とはみなせません。

**worktreeと別名。** `.git` がファイルの場合、実体がプロジェクト外にある場合、同じ木を別のbind経路でも見せる場合を扱います。一つの文字列パスだけを覆っても、別の見える名前まで覆えたとは限りません。

**rootの任意新規作成。** 既存の非保護の子を個別にbindする投影では、新しいルート直下のファイルがどこに保存されるかが問題になります。私有tmpfsやoverlayへ作った変更を親のworkspaceに反映するなら、その反映は新しい親の代理書き込みです。SafeFsの保護対象/リンク検査と、File.Writeの許可を適用しなければなりません。

**権限を戻せないこと。** mount構成の完成後、子がunmount、mount、別のnamespaceへ移動して隠した対象を再露出できないようにします。必要な初期化操作を終えてからseccomp等を固定し、失敗した場合はexecへ進みません。

以上は、自前mount案を否定するものではありません。**「readonly bindで覆う」と一行だけ決めても、BH-049は閉じない**という意味です。

## 6. Unix IPCとLandlockのABI

今回閲覧したカーネル文書には、ABI 6のabstract Unix socketのscope、ABI 9のpathname Unix socket用の権利が記載されています。03-02の「Unixソケットをパスの規則で隔てられない」は、対象ABIを明示して書き直す必要があります。[S-K01]

ただし、採用するcrateがそのABIの全機能を公開していること、実行先kernelで有効なこと、期待したpathname/datagram送信を実際に止められることは別です。kernel版の文字列だけでなく、実行時の対応ABIと実際の規則導入を調べます。新しい文書があることを、対象Linux全体の最低要件が満たされた証拠にしてはいけません。

推奨する能力の表は、単純な `sandbox_available: true` ではなく次のようなものです。これは新しい内部形式の提案です。

```json
{
  "platform": "linux",
  "landlock_abi": 9,
  "filesystem_read_exclusions": "verified",
  "protected_write_paths": "verified",
  "exec_allowlist": "verified",
  "external_unix_stream": "denied",
  "external_unix_datagram": "denied",
  "inherited_capabilities": "closed",
  "descendant_lifetime": "verified",
  "restricted_mode": "eligible"
}
```

数値9は例であり、ABI 9ならこの全項目が自動で成立するという意味ではありません。各値は選んだ実装と試験の結果から作ります。未知の項目が必要な保証に関わる場合はeligibleにしません。

## 7. macOS / Seatbeltへの意見

`/usr/bin/sandbox-exec`の固定パス、deny-default、パスを-Dの値で渡す方針、子孫のexec制限、書けるファイルからの実行可能mapの拒否という方向は、試作の合理的な出発点です。設計者がmacOS 27.0.1で確認したexecの拒否は、設計者の観測として扱いました。このレビューで追試したわけではありません。

一方、全Machサービスの安全な許可一覧、Wasmtime等の正常動作に必要な匿名の実行可能メモリとファイル由来のコードの区別、DYLD経由の追加読み込み、ファイル名の別名、外部IPC拒否は、その小さい試験だけでは証明されません。BH-044とBH-091で、必要なサービスを一つずつ増やし、増やすたびに外部代理実行の試験を戻す形を勧めます。

### 必須の確認

| 領域 | 確認すること |
|---|---|
| file操作 | 読ませない場所、書込範囲、既存/非存在の保護名、rename/link、仮想/別名経路 |
| process-exec | 処理系と許可ネイティブだけが起動でき、子孫でも同じ |
| コード読込 | workspace/tmp由来のdylibや実行可能file mapを拒否し、必要な処理系の実行は成功 |
| 環境 | DYLD等を変更してもコード読込制約を逃げず、親のキーを継承しない |
| Mach | 追加した各mach-lookupが、許可範囲外のプログラムの代理起動にならない |
| Unix IPC | ネットワーク有効時も外のローカル代理サービスは使えない |
| 子孫 | 完了/取消/親異常終了後の権限の残存を扱える |

sandbox-execの廃止・将来の削除時期・全対応macOSでの安定したprofile仕様について、このレビューではAppleの一次資料で十分な保証を確認できていません。AppleのApp Sandbox文書はありますが、それはsandbox-execのCLI/profileをそのまま置換する仕様ではありません。[S-M01] よって「すぐ消えるので使ってはいけない」とも「将来も保証される」とも結論しません。対応するOS版を実測で固定し、機能しなければ拒否する設計が現実的です。

## 8. 環境変数・tmp・spill・web_fetch

### 環境変数

設計にある、既知のproviderキーと設定で参照したキー変数を除く方針は維持してください。環境全体を秘密として完全に隔離する保証ではないことも明確にします。未登録の汎用トークンやユーザが自分で設定した値を全て見つけられる、とまではしません。

初期環境の安全な最小集合を作ることと、子のProcess.Commandから環境を追加できることは別です。BH-026は後者の危険なローダ系変数を処理系がどう扱うかを定める要望です。しかし環境変数の文字列だけを禁止すれば、任意の許可コマンドの全plugin/設定機能を安全にできるわけではありません。[S-B03]

### tmp

LLMのscratchと子のTMPDIRを同じセッション領域へ置く設計では、既にあるファイル名を信頼して上書きしてはいけません。親が付ける予測可能な番号であっても、排他作成と通常ファイル検査が必要です。利用者専用の親ディレクトリ、ルートの同一性、親の内部分類、終了後の安全な削除を一つの実装にまとめます。

古いtmpの掃除でPIDだけを見て所有者を判断しないでください。PIDの再利用やrootの差し替えを考慮し、ハーネスが作った識別子と保持した親の下だけを扱います。掃除のための再帰削除もSafeFsの対象です。

### spill

現設計ではspillを子のtmpではなく親のセッションデータへ置き、再開後も読めるようにしています。これは望ましい区別です。子にその領域の書き込み権限を渡さず、readの例外も提示した出力オブジェクトに限定してください。

出力が秘密を含んだ時点で、spillは秘密になりえます。0700/0600と保持期間に加え、総容量の上限、完全保存できたか、掃除中のセッションとの排他を持たせます。「出力が来たら自動でfileパスやURLを読みに行く」機能を追加しないことも重要です。

### web_fetch

web_fetchは親が明示的に行う、別の承認済みネットワーク操作です。子がネットワーク禁止でも、許可されたweb_fetchをLLMが呼ぶことは設計上の例外であり、新しいOS脱出とは数えません。HTTPS限定、domain承認、redirectごとの判定、禁止IP、DNS固定、proxy無効化を実装で維持します。

残る確認事項はTLSのホスト検証、URLの正規化、復号後のサイズ、時間/ヘッダの上限等です。外部ページ中のURLや画像を本文変換処理が自動で追加取得しないことも、単純なGET道具の範囲として固定してください。

## 9. 共通のセキュリティ試験ゲート

試験結果は、次の形式で保存するとBHの終了条件に使えます。

```text
case_id / harness_commit / interpreter_commit_or_hash
OS / architecture / kernel / Landlock ABI / sandbox implementation
mode / effective policy hash / fixture version
operation attempted / expected result / observed result
outside-marker before+after / surviving descendants / audit notes
```

### P0: 実現性を確定する

| ID | 試験 |
|---|---|
| SEC-P0-01 | 必要な権利とABIがないと、制限モードの子を起動しない |
| SEC-P0-02 | no_new_privs、Landlock、seccompの各失敗がexec前に止まる |
| SEC-P0-03 | 静的/動的ELF、ローダ直接実行、execveat/FDの行列 |
| SEC-P0-04 | 秘密の読み取り禁止と既存/非存在の.git保護 |
| SEC-P0-05 | IP無効/有効それぞれで外部Unix IPCを拒否 |
| SEC-P0-06 | 必要な内部socketpairと処理系の通常動作は成功 |
| SEC-P0-07 | FD・環境・端末・資格情報を最小化した起動 |
| SEC-P0-08 | helperをsafe APIだけで作れるか、規則との整合 |
| SEC-P0-09 | macOSで最小Mach許可とfile-map制限を両立 |

### P2: 子の実行と確認を完成させる

| ID | 試験 |
|---|---|
| SEC-P2-01 | effect増加の再確認、拒否後の実行なし、非対話allowの上限 |
| SEC-P2-02 | scratchの無確認範囲とread範囲、File.Writeなしのworkspace拒否 |
| SEC-P2-03 | 偽診断の位置で親が範囲外を読まない |
| SEC-P2-04 | 入口/import/設定を変更して、確認した集合と実行集合をずらせない |
| SEC-P2-05 | testの発見集合と承認集合が一致 |
| SEC-P2-06 | File.Writeの既存hardlinkと別名から外を変えない |
| SEC-P2-07 | 全サブコマンド・許可コマンドでもOS範囲を維持 |
| SEC-P2-08 | 正常終了/取消/異常終了後に子孫の権限が残らない |
| SEC-P2-09 | io_uring等の明示禁止と対象archでのsyscall表 |

### P4: 親の道具と再開を含む再評価

| ID | 試験 |
|---|---|
| SEC-P4-01 | 全ファイル操作入口のsymlink/parent race/通常ファイル検査 |
| SEC-P4-02 | create_projectのルート変更が旧権限を残さない |
| SEC-P4-03 | 未保存・除外・未走査のsnapshotを安全に戻す |
| SEC-P4-04 | spill/tmp/ログの境界、容量超過、掃除の競合 |
| SEC-P4-05 | terminalの制御列が確認欄へ干渉しない |
| SEC-P4-06 | web_fetchのDNS/TLS/redirect/圧縮本文の行列 |
| SEC-P4-07 | 再開/巻き戻しで承認を勝手に復活させない |
| SEC-P4-08 | 中断された実行が再開時に重複しない |

**合格の意味**: 成功するべき正常な処理と、拒否するべき不正な処理の両方を確認します。単に子が何もできず全て失敗する構成を、安全な実装が完成した証拠にしません。未試験は不合格と同じく公開判断を止める情報として扱い、試作の進行中であることとは分けて表示してください。
