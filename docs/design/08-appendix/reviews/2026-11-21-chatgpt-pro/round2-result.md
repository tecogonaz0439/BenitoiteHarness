R01. エフェクトを記憶する規則が、03-03 と ACP の対応表で一致していません

場所

- docs/design/03-safety/03-03-approval.md「制限モードの確認」
- 同章 「.agents への書き込み」
- docs/design/05-interface/05-03-acp.md「確認の種類ごとの選択肢と記憶の範囲の対応表」

問題点

ACP の表は、通常の Effects・TestEffects でも allow_once ではエフェクトを記憶せず、.agents 書き込みや unread_imports > 0 の確認では、その一回限りの選択肢だけを出すと定めています。この意味付けは適切です。

一方、03-03 の「.agents への書き込み」には、依然として次の記述があります。

> エフェクトの確認そのものは今までどおり覚える。



適用する入口の限定がないため、ACP の表と矛盾します。また、「制限モードの確認」の「前に確認した範囲に収まれば確認しない」という説明も、今回限りの確認と、セッションに記憶する確認を区別していません。

重さ：実装の前に直すべき。 局所的な文書の整合修正です。

修正案

03-03 で、従来の TUI の承認と ACP の選択肢による承認を明確に分けてください。

- TUI で従来どおりエフェクトを記憶する扱いを維持するなら、その適用範囲を明記する。
- ACP の allow_once は、エフェクト集合も含めて、その呼び出しだけに効くとする。
- 「確認済みなら次回の確認を省く」という説明は、セッションに記憶された承認の範囲についての規則とする。
- 既存のセッション許可がある場合、allow_once はそれを消すのでも広げるのでもなく、今回の承認によって更新しない、と整理する。

実装プランには「その一回の承認済み集合を渡す変更」も必要です

既存コードでは、承認後に remember_effects を呼び、その結果を使って execute_approved へ進みます。benitoite_run と benitoite_test は、再検査したエフェクトが Invocation.confirmed_effects に収まらなければ、承認済み状態でも EFFECTS_CHANGED を返します。したがって、remember_effects を呼ばなくするだけでは、初回の allow_once が実行できません。

根拠は、同じ改訂コミットの agent/execution.rs、tools/benitoite_run.rs、tools/benitoite_test.rsです。

この部分の重さは 実装の中で直せばよい です。設計には求める挙動が書かれているので、プランで次を具体化すれば足ります。

- セッションの confirmed_effects と、呼び出し単位の承認済みエフェクト集合を分ける。
- 後者を対象・呼び出しに結び付けて再実行へ渡す。
- 実行直前の再検査を維持し、承認した範囲を超えるエフェクトを通さない。
- benitoite_scratch の共通経路も対象に含める。

試験は「記憶されない」だけでなく、一回目は実際に実行でき、二回目は再確認になり、承認後にエフェクトが増えた場合は通らないことまで確認する必要があります。

R02. --allow を超える実行を尋ねるかどうか、準備方針の表内で食い違っています

場所

- docs/design/05-interface/05-03-acp.md「起動とセッションの準備の方針の分離」
- 関連して、docs/design/05-interface/05-01-cli.md「オプション」

問題点

準備方針の項目 2 は、ACP について次のように読めます。

- --approval never または --allow 指定時は、事前許可の範囲だけで判定する。

ところが、項目 3 は次の規則です。

- --allow を超える分は、--approval never でなければ AcpApprover で尋ねる。

同じ --allow 指定について、超過分を拒否するのか、追加の確認を受けられるのかが一致していません。

また、05-01 のオプション表には、--allow・--project-parent・--ephemeral などを非対話や exec に限定する説明が残っています。ACP でも受け付けるという 05-03 の規則との対応を明示した方が、CLI の実装時に迷いません。

重さ：実装の前に直すべき。

修正案

項目 3 を意図するなら、項目 2 の括弧を、例えば次の意味に揃えてください。

> --approval never の場合は事前許可の範囲だけで判定する。--allow はエフェクトの事前許可集合を指定し、その範囲を超えたときに追加確認できるかは、承認方針によって決まる。



あわせて 05-01 でも、対象入口を tui・exec・acp で明記してください。特に、ACP での --approval never の適用範囲は、通常モードだけなのか制限モードにも適用するのかを、05-03 と揃える必要があります。

R03. 終了手順には、出力キューの満杯と「stdout が開いたまま読まれない場合」を補うと確実です

場所

- docs/design/05-interface/05-03-acp.md「スレッドの構成と終了の手順」
- docs/design/07-quality/07-01-testing.md「安全の性質のテスト」

問題点

改訂された 5 段の手順は、前回問題になった、確認待ちの解除、AgentEvent の継続回収、最後の更新と完了応答の順序に対応しています。

残るのは、その手順を実装で成立させるための二つの条件です。

1. 出力専用スレッドがあっても、主スレッドが満杯の出力チャネルへの送信で止まると、取消処理とイベント回収も止まります。 「出力の滞留で確認の解除は止まらない」という要件を、チャネルの送り方まで落とす必要があります。
2. クライアントが stdout の読み取り口を開いたまま読まなくなると、書き込みは停止しても Broken pipe にはなりません。 その状態で stdin に EOF が来た場合、出力スレッドの join や未送信出力の排出を待つ実装では、終了できなくなります。

重さ：実装の中で直せばよい。 現在の終了方針に沿って具体化できる事項です。

修正案

設計または実装プランに、次を明記してください。

- 主スレッドから出力スレッドへの送信で、取消処理とイベント回収を無期限に止めない。
- 出力キューの容量と、満杯時の扱いを決める。例えば、有界キューへの非ブロッキング送信と、上限超過時の接続終了処理を組み合わせる。
- EOF・出力障害後は、子プロセス、エージェント、セッション記録の後始末を終えたら、未送信出力の完了を待たず終了する。
- stdin だけでなく、stdout の書き込みで停止した出力スレッドも無期限に join しない。

既存の Broken pipe 試験に加えて、stdout を読まずに開いたまま、stdin だけを閉じる模擬クライアントの試験があると、この条件を確認できます。

R04. AgentEvent::Error と、session/prompt の最終的な失敗応答を分ける必要があります

場所

- docs/design/05-interface/05-03-acp.md「イベントから session/update への変換」
- 同章「依頼の受け取りと終わりの理由」「スレッドの構成と終了の手順」

問題点

イベント表の最終行には、Error を session/prompt の JSON-RPC error 応答にする記述があります。

しかし、既存の Agent::run_controlled は、正常に完了した後でも take_storage_notice() があれば、AgentEvent::Error { kind: "storage_limit", ... } を出します。その後に、正常完了の SessionEnd と RunReport を返せます。agent/mod.rs の該当処理

そのため、Error イベントを見た時点で失敗応答を送る実装では、正常完了を失敗にする、後で二重に応答する、取消時の cancelled 優先を崩す、といった結果になりえます。

重さ：実装の中で直せばよい。 設計の一文も合わせて明確にするとよい箇所です。

修正案

応答の決定箇所を一つにしてください。

> Error イベントは診断として扱う。session/prompt の応答は、残イベントの回収後に、型付き RunReport と当該実行の取消状態から一度だけ決める。



これで、今回追加した終了理由の型付けと、5 段の終了手順が一貫します。
