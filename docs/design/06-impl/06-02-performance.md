# 性能

- 状態: 草稿
- 未決事項: BH-020, BH-060

## 目的と範囲

本章は、試作の実行ファイルの大きさ、起動と処理の速さ、メモリの使用量の目標と、測り方を定める。エージェントとしての性能（課題の達成率など）は[評価](../07-quality/07-02-evaluation.md)で定める。

## 前提

- 利用者の要件は、実行ファイルが小さく、実行が速いことである。
- 比べた三つのハーネスのうち、実行ファイルの大きさと起動の時間を公表しているものはない。Codex CLI のリリースの配布物は、aarch64 の macOS 向けが zstd の圧縮で 71 MB、tar.gz で 100 MB である（[先行事例](../08-appendix/08-01-prior-art.md)）。Pi と DeepSeek Harness は Node.js の上で動く。
- LLM の応答の時間は秒の単位であり、ハーネスの処理の時間は多くの場面でそれより十分に小さい。ハーネスの速さが効くのは、起動、道具の実行（ファイルの走査、検索、子プロセスの起動）、ストリーミングの描画、長いセッションでの文脈の組み立てである。

## 仕様

### 目標

【方針】次の目標を置く。測る環境は、設計者の手元の計算機（Apple M4 の Mac mini、macOS 27）とする。

| 項目 | 目標 |
|---|---|
| 実行ファイルの大きさ（`aarch64-apple-darwin` のリリースのビルド、記号を除いたもの） | 8 MiB 以下 |
| `benitoiteh --version` の時間 | 5 ms 以下 |
| 対話の画面を開いて入力を受けられるまでの時間（処理系の `--version` の起動を含む） | 150 ms 以下 |
| `exec` を起動してから最初の要求を送り始めるまでの時間（処理系の `--version` の起動を除く） | 30 ms 以下 |
| 待っている間のメモリ（常駐の大きさ） | 20 MiB 以下 |
| 200 番のセッションでのメモリ（子プロセスを除く） | 100 MiB 以下 |
| ストリーミングの文の差分を受けてから画面に示すまで | 16 ms 以下 |
| `grep` で 1 万のファイルを探す時間 | 1 秒以下 |

- 実行ファイルの大きさの目標の 8 MiB は、候補の依存（TLS、正規表現、ファイルの走査、JSON、TOML、端末）と、埋め込む Skill の文書（`v0.0.6` の時点で約 303 KB）を合わせた見込みに、余裕を加えた値である。2026-10-17 に、試作の P0-06 で測った（[実装プラン](../../plan/tasks/P0-06-size-probe.md)の「結果」）。P1 を終えた `benitoiteh`（`exec`、二つのアダプタ、TLS と証明書の検証、五つの道具、セッションの記録、埋め込んだ Skill を含む）は、`aarch64-apple-darwin` で 4,526,272 バイト（4.3 MiB）である。予定の依存のすべて（端末の `crossterm` を含む）の主な機能を呼ぶ構成は 4,129,184 バイト（3.9 MiB）で、`opt-level = "s"` では 3,386,624 バイトだった。Linux の補助のプロセス（Landlock と seccomp）は、P0-05 の報告で約 150〜180 KB を加える。この結果から、8 MiB の目標は P2〜P4 の部品を加える余裕を残しているので、変えない。P2〜P4 の実装を加えた大きさは、段階ごとに測る。空の実行ファイルの大きさは、目標を満たす見込みの根拠にしない。安全の機能（TLS の証明書の検証、サンドボックス）を外して目標を満たすことはしない。
- 処理系の実行ファイルの大きさは、この目標に含めず、別に記録する。
- 常駐の大きさ（待っている間）と、最大の常駐の大きさ（200 番のセッション）は、別の値として別の方法で測る（後述の「測り方」）。
- 処理系の起動の時間は、処理系の側の性能なので目標に含めない。ただし、`benitoite_check` の一回の時間を測り、LLM の応答の時間と比べて無視できるかを確かめる（BH-020）。

### 測り方

【方針】

- 実行ファイルの大きさは、依存のクレートを加えるたびと、各段階の完了のときに測り、`docs/` の下の測定の記録に、コミットとあわせて書く。どのクレートが大きさを占めるかは `cargo bloat` などで調べる。
- 時間は、同じ計測を 10 回以上繰り返して中央値と最大値を記録する。計測の道具は実装プランで決める。
- メモリは、`/usr/bin/time -l`（macOS）で最大の常駐の大きさを測る。待っている間の常駐の大きさは、起動して入力を待つ状態になった後の、その時点の常駐の大きさ（`ps` の `rss` など）で測る。
- 大きさの記録には、対象の環境、Rust の版、`Cargo.lock` のコミット、有効にした機能、ビルドの設定を添え、同じ条件で測り直せるようにする。`grep` の測定には、ファイルの数に加えて、合計の大きさ、除外したファイルの数、ファイルシステムのキャッシュの状態（初めてか二度目か）を添える。
- ストリーミングと長いセッションの測定は、模擬の提供者（[テスト](../07-quality/07-01-testing.md)の「模擬の提供者」）で、決まった応答を決まった速さで流して行う。理由: 本物の提供者の時間のゆらぎを除き、ハーネスの側の時間だけを測る。

### 速さのための作り

本書のほかの章で定めた作りのうち、速さに効くものを挙げる。

- 非同期の実行時を使わずにスレッドで組む（[クレートの構成](06-01-crate-structure.md)の「スレッドと非同期」）。起動の時に実行時を初期化する時間がない。
- 読み取りの道具を並べて実行し、ストリームの途中で始める（[エージェントのループ](../01-agent/01-01-agent-loop.md)の「道具の実行」）。
- プロンプトのキャッシュを壊さない（[文脈の管理](../01-agent/01-04-context.md)の「文脈の構成」）。キャッシュが効くと、提供者の側の応答の始まりが早くなる。
- 書いた後の検査で往復を減らす（[道具](../01-agent/01-03-tools.md)の「書いた後の検査（制限モード）」）。
- 巻き戻しの記録で、変わっていないファイルを読み直さない（[セッション](../01-agent/01-05-sessions.md)の「巻き戻し」）。

`opt-level` を大きさ優先にするかどうかは、大きさと上の時間の両方を測ってから決める（BH-060）。
