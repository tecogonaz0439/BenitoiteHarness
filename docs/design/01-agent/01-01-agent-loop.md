# エージェントのループ

- 状態: 草稿
- 未決事項: BH-011, BH-012

## 目的と範囲

本章は、`benitoiteh` のエージェントのループ（LLM への要求、応答の受け取り、道具の実行、結果の返却を繰り返す処理）を定める。対象は、番（turn）の構造、ストリーミングの受け取り、道具の実行の順序と並行、利用者の割り込みと取り消し、誤りのときのやり直し、上限、同じ呼び出しの繰り返しへの対処である。提供者との通信は[提供者の層](../02-providers/02-01-provider-layer.md)で、文脈の圧縮は[文脈の管理](01-04-context.md)で、スレッドの構成は[全体像](../00-overview/00-02-architecture.md)で定める。

## 前提

- 道具の定義と、並行の可否の印は[道具](01-03-tools.md)で定める。
- 参考にしたハーネスのループの作りは、[先行事例](../08-appendix/08-01-prior-art.md)にまとめた。Pi と DeepSeek Harness はどちらも、ストリームを受け取り、道具の呼び出しを実行し、結果を加えて次の要求を送る単純なループを持つ。

## 仕様

### 用語

- **依頼**: 利用者が入力欄から送る一つの文。
- **番**: LLM への一回の要求と、その応答（文と道具の呼び出し）と、応答の道具の呼び出しの実行までをいう。
- **一連の処理**: 一つの依頼を受けてから、LLM が道具を呼ばずに応答を終えるまでの番の並び。

### 番の流れ

【方針】一連の処理は次のように進む。

1. 依頼を会話に加える。
2. 文脈の大きさを見積もり、圧縮の条件に当たれば圧縮する（[文脈の管理](01-04-context.md)の「圧縮」）。
3. LLM に要求を送り、応答をストリーミングで受け取る。受け取った文は、届いた順に画面に示す。
4. 応答の終わりの理由によって分ける。終わりの理由は、提供者の終わりのイベントを受け取って確かめたものだけを使う。終わりのイベントの前にストリームが切れたとき、ストリームの中で誤りのイベントを受けたときは、誤りとして扱い、応答の中の道具の呼び出しを実行しない。
   - 道具の呼び出しがない: 一連の処理を終える。
   - 道具の呼び出しがある: 後述の「道具の実行」で実行し、結果を会話に加えて 2 に戻る。
   - 出力の上限で打ち切られた（終わりの理由が `length` に当たる）: 応答の中の道具の呼び出しを実行せず、各呼び出しに `Tool call was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.` を結果として返して 2 に戻る。理由: 打ち切られた応答の道具の引数は途中で切れている可能性があり、実行すると壊れた内容を書きうる。Pi が同じ扱いをする。
   - 誤り: 後述の「やり直し」に従う。

### 道具の実行

【方針】一つの応答の中の道具の呼び出しは、次のように実行する。

1. 応答の順に、各呼び出しを検証する。道具の名前を引き、引数を修復し、JSON Schema で検証する。知らない道具と検証の誤りは、その呼び出しの結果を誤りとし、実行しない。
2. 応答の順に、並行の可否の印が「可」の呼び出しが続く区間をまとめて並べて実行し、「不可」の呼び出しは、前の区間が終わってから一つずつ実行する。並べて実行する数は最大 8 とする。理由: 読み取りの道具を並べれば待ち時間が減る。書く道具と実行する道具は、順序に依存する効果を持つので並べない。DeepSeek Harness は、並べてよいと明示した道具だけを並べ、ほかを区切りとして扱う（安全な側に倒す作り）。
3. 結果は、実行が終わった順ではなく、応答の中の順に会話に加える。
4. 確認が要る呼び出し（[利用者の確認](../03-safety/03-03-approval.md)）は、実行の直前に確認を受ける。
5. 手元だけで動く読み取りの道具（`read`・`glob`・`grep`・`benitoite_check`・`benitoite_explain`・`benitoite_reference`。`web_fetch` は含めない）の呼び出しは、応答のストリームの途中でその呼び出しの引数を受け取り終え、検証を通った時点で、応答の終わりを待たずに実行を始めてよい。ただし、応答の先頭から続く読み取りの道具の呼び出しに限る。並行の可否が「不可」の呼び出し（`write` など）より後の呼び出しは、先に始めない。先に始めた呼び出しの結果と、`read` が記録する読んだ版は、応答が正常に終わったと確かめるまで仮のものとして持ち、確かめたときに確定する。応答が正常に終わらなかったとき（出力の上限、切断、誤り、取り消し）は、仮の結果と記録を捨てて、前述の「番の流れ」の 4 の扱いに従う。理由: 読み取りの道具の実行を、LLM が残りの応答を生成する時間に重ねられる。Codex CLI は、応答の項目を受け取り終えた時点で道具の実行を始める。`write` の後の `read` を先に始めると、書く前の内容を返してしまう。読んだ版は後の `write`・`edit` の前提になるので、捨てた応答の読み取りでは記録を変えない。

### 利用者の割り込み

【方針】一連の処理の途中に利用者が入力した文は、次の二種類として扱う。どちらも、実行中の道具を止めない。Pi の操縦（steering）と後続（follow-up）の作りに倣う。

- **操縦**（入力欄で Enter）: 今の応答の道具の呼び出しがすべて終わった後、次の要求の前に、利用者の発言として会話に加える。
- **後続**（入力欄で Alt+Enter）: 一連の処理が終わった後に、新しい依頼として扱う。

### 取り消し

【方針】利用者が ESC を押したら、そのときの処理を止める。

| 止める時点 | 止め方 |
|---|---|
| LLM の応答を待つ・受け取る途中 | 要求の受け取りを打ち切る。途中までの応答は、中断したものとして画面に示し、次の要求には含めない |
| 道具の実行の途中（子プロセス） | 子プロセスのグループに `SIGINT`（処理系）か `SIGTERM`（`bash`）を送り、10 秒で終わらなければ `SIGKILL` を送る |
| 確認の画面 | 拒否として扱う |

- 取り消した番の、まだ結果のない道具の呼び出しには、`Tool call was cancelled by the user.` を結果として加える。理由: 提供者の多くは、道具の呼び出しに結果が対応していない会話を誤りとして拒む。Pi と DeepSeek Harness も、結果のない呼び出しに作った結果を補う。
- 止める前に子プロセスが行った操作は戻らないことを、画面に示す。Benitoite の事前検討の見立て（Benitoite の docs/todo の TODO-139）を引き継ぐ。
- ESC を続けて二度押したら、一連の処理を止め、入力欄に戻る。
- 【方針】一度の ESC で止めた後の扱いは、止めた時点で分ける。道具の実行の途中なら、その応答のまだ終わっていない道具の呼び出しをすべて取り消した結果にして、一連の処理を続ける（LLM は取り消されたことを読んで次を決める）。LLM の応答を待つ・受け取る途中なら、続ける内容がないので、一連の処理を止めて入力欄に戻る（二度の ESC と同じ）。確認の画面では拒否として扱い、一連の処理を続ける。一連の処理の途中の Ctrl+C は、二度の ESC と同じに扱う。理由: 長いコマンドだけを止めて LLM に別の手を取らせたい場面と、作業そのものを止めたい場面を、押す回数で分ける。応答の途中で止めて同じ会話を送り直すと、同じ応答が返るだけである。

HTTP の受け取りは、ソケットを閉じて打ち切る（[提供者の層](../02-providers/02-01-provider-layer.md)の「HTTP の通信」）。接続の前の段階で打ち切れず、受け取りのスレッドを切り離すときは、取り消した要求の結果を後の番に混ぜない。切り離したまま終わっていないスレッドが 2 つあるときは、新しい要求を送らずに、そのスレッドが終わるのを待つ。

### やり直し

【方針】提供者への要求が失敗したときは、誤りを分類する。

| 分類 | 例 | 扱い |
|---|---|---|
| やり直せる | 429、500〜599、提供者の過負荷の誤り、接続の失敗、ストリームの途中の切断、応答が空 | 最大 4 回やり直す |
| 読めない応答 | 応答を受け取り切ったが、形が `benitoiteh` の読み方に合わない（[提供者の層](../02-providers/02-01-provider-layer.md)の「OpenAI の Chat Completions API」） | 【方針】一度だけやり直す。理由: 形の違いはやり直しても直らないことが多く、受け取り切って課金された応答を何度も捨てることになる（2026-10-18 の P1-12 の点検）。途中の切断と区別できないまれな壊れ方に備えて、一度は送り直す |
| 文脈の超過 | 提供者が文脈の長さの超過を示す誤り | 一度だけ、超過したときの圧縮（[文脈の管理](01-04-context.md)の「圧縮」）を行ってやり直す |
| やり直せない | 認証の誤り（401・403）、残高と利用の上限の誤り、要求の形の誤り（400） | 一連の処理を止めて、誤りを示す |

- やり直しの間隔は、1 秒から倍にし、30 秒を上限とし、±20% のゆらぎを加える。応答に `Retry-After` があれば、その値（60 秒を上限とする）を使う。
- ストリームを受け取る途中で切れたときは、受け取った分を捨てて、同じ要求を送り直す。
- 値は Pi（3 回、2 秒から、上限 60 秒）と DeepSeek Harness（5 回、0.5〜10 秒）の間に置いた。評価で見直す。

### 上限

【方針】次の上限を設ける。どれも設定ファイルの `[limits]` と起動のときのオプション（`--max-turns`・`--max-check-fix`・`--max-run-tokens`）で変えられる（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「オプション」）。

| 上限 | 既定 | 達したとき |
|---|---|---|
| 一連の処理の番の数 | 200 | 止めて、達したことを示す |
| 検査と修正の回数（制限モード） | 10 | 止めて、残る診断とともに利用者に報告する |
| 一連の処理のトークンの量 | なし | 止めて、達したことを示す |

- 検査と修正の回数は、同じスクリプトについて、検査（`benitoite_check` と、書いた後の検査）が誤りを返した回数を数え、誤りなく通ったら 0 に戻す。誤りを返したとするのは、`benitoite_check` では検査の誤り（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「終了状態と診断の受け渡し」の分類）、書いた後の検査では書いたファイルに `error` の診断があるか、位置が `null` の誤りがあるときである。警告だけのときは誤りなく通ったとする。使い方の誤り、処理系の不具合、時間切れ、取り消し、検査しなかったとき（[道具](01-03-tools.md)の「書いた後の検査（制限モード）」の `Not checked automatically`）は、回数を変えない。上限に達して止めたら、そのスクリプトの回数を 0 に戻す。回数はループのメモリに持ち、再開のときに記録から戻さないので、再開したセッションは 0 から数える。既定の 10 回は、Benitoite の事前検討の見立てと、Skill の評価の上限に揃えた（[ADR 0344](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/archive/2026-10-09-design-first-release/decisions/0344-agent-harness-operation-scope-and-tools.md) の帰結、Benitoite の docs/todo の TODO-134）。
- Pi と DeepSeek Harness は番の数の上限を持たない。試作が持つのは、LLM の誤りで利用料が上限なく増えることを防ぐためである（[セキュリティモデル](../03-safety/03-01-security-model.md)の「守るもの」）。

### 同じ呼び出しの繰り返し

【方針】同じ道具を同じ引数で、続けて 3 回呼んだときは、3 回目の結果の末尾に `[note: this is the 3rd identical call. Its result will not change unless something else changes. Try a different approach.]` を加える。5 回目と 8 回目にも加える。理由: LLM が同じ失敗を繰り返して番を浪費することがあり、DeepSeek Harness は同じ回数で注意を加えている。止めずに注意にとどめるのは、ファイルの変化を待って同じ読み取りを繰り返すような、正しい繰り返しもあるからである。

### 完了の前の確かめ

一連の処理を終える前に、ハーネスの側から LLM に検査やテストを促す仕組み（DeepSeek Harness は持たない）を加えるかは、評価で効果を確かめてから決める（BH-011）。制限モードでは、書いた後の検査（[道具](01-03-tools.md)の「書いた後の検査（制限モード）」）がこの役割の一部を担う。

### イベント

【方針】ループは、次のイベントを出す。画面（[対話の画面](../05-interface/05-02-tui.md)）と非対話の JSON の出力（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「exec の出力」）とセッションの記録（[セッション](01-05-sessions.md)）は、同じイベントを読む。

`session_start`、`turn_start`、`text_delta`、`reasoning_delta`、`tool_call`、`approval_request`、`approval_result`、`tool_result`、`turn_end`（使ったトークンの量を含む）、`compaction`、`retry`、`error`、`session_end`

イベントの欄の細部は、実装プランで定める。理由: 欄は提供者の層と画面の作りに依存し、試作の途中で変わる見込みが大きい。非対話の JSON の出力を利用者に約束する形にするかは BH-012 で決める。セッションの記録は、画面に示すイベントとは別に、再開に要る記録（道具の実行を始めたこと、など）も持つ（[セッション](01-05-sessions.md)の「セッションの記録」）。
