# 文脈の管理

- 状態: 草稿
- 未決事項: BH-014, BH-042, BH-096, BH-102

## 目的と範囲

本章は、`benitoiteh` が LLM に送る文脈（システムプロンプト、環境の情報、プロジェクトの指示のファイル、会話）の組み立て方と、文脈が長くなったときの圧縮を定める。プロンプトのキャッシュの提供者ごとの指定は[提供者の層](../02-providers/02-01-provider-layer.md)で定める。

## 前提

- Benitoite の事前検討は、初めの指示に `SKILL.md` に当たる内容を入れ、参照の文書は必要なときに読ませる形を見立てとし、圧縮と会話の保存・再開は初めは設けないとした（Benitoite の docs/todo の TODO-134。[検討メモ](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.7/docs/archive/2026-10-09-design-first-release/sources/post-first-release/post-first-release-agent-harness.md)の「文脈の管理」）。
- Pi のシステムプロンプトは、核の部分が約 400 トークンであり、日付と OS を含まない（作業ディレクトリと `AGENTS.md` の中身は含む）。DeepSeek Harness は、システムプロンプトを変えずに保ち、変わる情報を利用者の側の発言として後から加える（[先行事例](../08-appendix/08-01-prior-art.md)）。

## 仕様

### 文脈の構成

【方針】一つの要求の文脈は、先頭から次の順に並べる。

1. **システムプロンプト**（モードと、`benitoiteh` の版と、処理系から得た `SKILL.md` で決まる。セッションの間変えない）
2. **道具の定義**（モードと、処理系を使えるか（通常モードで処理系がなければ Benitoite の道具を外す）だけで決まる。セッションの間変えない）
3. **環境の情報**（セッションの初めの、利用者の側の最初の発言の先頭に置く）
4. **会話**（依頼、応答、道具の呼び出しと結果）

理由: 提供者のプロンプトのキャッシュは、要求の先頭から一致する部分に効く。セッションに依らない 1 と 2 を先頭に置けば、同じモードで同じ処理系を使う別のセッションの間でもキャッシュが効く。セッションごとに変わる 3 を会話の側に置けば、1 と 2 を変えずに済む。

【方針】送る会話は追記だけで伸ばす。前の要求で送った部分を、書き換え・並べ替え・途中の削除をしない。例外は、圧縮（古い側を要約に置き換える）と、巻き戻し（新しい側を切り捨てる。[セッション](01-05-sessions.md)の「巻き戻し」）の二つだけとする。注意の文（[エージェントのループ](01-01-agent-loop.md)の「同じ呼び出しの繰り返し」）や環境の変化も、加えた後に消さない。理由: 前の部分を書き換えると、プロンプトのキャッシュが効かなくなる。加えて、Anthropic の API は thinking のブロックを、それより前のシステムプロンプト、道具の一覧、会話に結び付けて検査し、途中を書き換えた会話を 400 の誤りで拒むことがある（後述の「圧縮」）。新しい側を切り捨てる巻き戻しは、残る部分の先頭を変えないので、この検査に当たらない。

### システムプロンプトの構成

【方針】システムプロンプトは次の節から成る。`<benitoite>` の節の Skill の本文と説明（後述の「Benitoite の Skill の置き方」）を除く文は、英語で書き、実行ファイルに埋め込む。

| 節 | 内容 | 制限モード | 通常モード |
|---|---|---|---|
| 前置き | `benitoiteh` の中で動くコーディングエージェントであることと、モードの目的を 2〜3 文で示す | ○ | ○ |
| `<tools>` | 有効な道具の一行の説明（[道具](01-03-tools.md)の「道具の定義の共通の規則」） | ○ | ○ |
| `<rules>` | 有効な道具の規則と、共通の規則（応答を簡潔にする、ファイルのパスを示す） | ○ | ○ |
| `<mode>` | モードの制約。制限モードでは、シェルがないこと、`.bnt` だけを書けること、実行の前に利用者の確認があること、`Process.Run` を使うスクリプトは止められうることを書く | ○ | ○ |
| `<benitoite>` | Benitoite の Skill（後述） | 全文 | 索引だけ（処理系がなければ節を置かない） |

- 前置きは、Pi の前置き（「You are an expert coding assistant operating inside pi, a coding agent harness.」）と同じ程度の短さにする。作業の進め方の一般論（テストを走らせよ、自分の変更を見直せ、など）は書かない。理由: Pi と DeepSeek Harness はどちらもそうした一般論を持たず、Pi の作者は、エージェントとして学習したモデルに長い一般論は要らないとしている。
- 日付、作業ディレクトリ、OS などの変わる情報は、システムプロンプトに入れない（後述の「環境の情報」）。
- システムプロンプトの全文と道具の定義の全文は、テストで固定する（[テスト](../07-quality/07-01-testing.md)の「LLM に見せる文の固定」）。システムプロンプトは処理系から得た `SKILL.md` を含むので、テストは決まった版（`v0.0.7`）の処理系で行う。理由: LLM に見せる文は性能と費用を左右するので、意図しない変更を差分として見えるようにする。DeepSeek Harness が同じことをしている。

### Benitoite の Skill の置き方

【方針】制限モードでは、起動した処理系から得た Skill の `SKILL.md` の本文（先頭の属性の部分と、本文の先頭の HTML の注釈を除く。[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「取り込む文書と版」）を `<benitoite>` の節にそのまま入れる。その前に、次の対応を書く。対応は `v0.0.7` の `SKILL.md` に合わせて書く。

- Skill の `benitoite check` は `benitoite_check`、`benitoite test --check` は `tests` を真にした `benitoite_check`、`benitoite run` は `benitoite_run`、`benitoite test` は `benitoite_test` の道具で行う。
- `references/<name>.md` は `benitoite_reference` の道具で `name` を指定して読む。
- 診断のコード（`E0405` など）の説明は、`benitoite_explain` の道具で引く。
- Skill の「Check the version first」の手順（`--version` と `--version=json`）と、`skill list`・`skill show` は、`benitoiteh` が起動のときに済ませているので行わない。
- Skill の、確認の直前の `check --report=json`・`test --check --report=json` と、実行の `--allow-effects` は、`benitoite_run`・`benitoite_test`・`benitoite_scratch` が行う。LLM は報告を読まず、許す集合を渡さない。
- Skill の「Before running」の確認は `benitoiteh` が画面で行うので、LLM は利用者に確認を求めなくてよい。ただし、エフェクトの意味を応答の文で説明するのはよい。

【決定】本文の先頭の HTML の注釈（`<!--` から最初の `-->` まで）は、LLM に見せるときにいつも除く。通常モードで `benitoite_reference` に `SKILL` を指定して読ませるときも同じである。2026-10-17 に設計者が決めた。理由: この注釈は、処理系の側のテストが文書の中の例をどう確かめるかの説明であり、LLM の作業に要らない。`v0.0.6` と `v0.0.7` の時点で 878 バイトある。

`SKILL.md` は `v0.0.7` の時点で約 26 KB（英語の文で約 6,700 トークンの見込み。`v0.0.6` の約 21 KB から、版と機能の問い合わせ、実行の前の検査、`--allow-effects` の手順が加わった）である。制限モードの作業はすべて Benitoite のスクリプトを書くことなので、毎回読ませる価値がある。キャッシュが効けば、2 回目以降の要求の費用は小さい。

【方針】通常モードでは、処理系が見つかり使えるとき（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系の見つけ方と版の確かめ」）は、起動のときに `SKILL.md` を処理系から得て、`<benitoite>` の節に、Skill の名前と説明（`SKILL.md` の先頭の `name` と `description`）と、`benitoite_reference` に `SKILL` を指定すれば全文を読めることだけを書く。処理系がないか使えないときは、`<benitoite>` の節を置かず、Benitoite の道具も外す。理由: 通常モードの作業は Benitoite に限らないので、Agent Skills の段階的な読み込みと同じく、要るときに読ませる。説明は処理系の版で変わりうるので、決まった文を埋め込まず、得た `SKILL.md` から取る。

### 環境の情報

【方針】セッションの最初の依頼の前に、次の情報を `<environment>` の塊として置く。

- プロジェクトのディレクトリの絶対パス、OS の種類、今日の日付（UTC の年月日だけ）
- モードと、OS のサンドボックスの方針の要約（書ける場所、ネットワークの可否）
- Benitoite の処理系の版（システムプロンプトの対応の説明を確かめた版と違うときは、その旨。[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系の見つけ方と版の確かめ」）
- 通常モードでは、プロジェクトの指示のファイル（後述）

セッションの途中で変わったとき（日付の変化、`create_project` によるプロジェクトのディレクトリの変更）は、変わった項目だけを次の依頼の前に同じ形で加える。

### プロジェクトの指示のファイル

【決定】通常モードでは、次のファイルを読み、`<project_instructions path="...">` の形で環境の情報に入れる。読む範囲と、下の箇条書きの読む条件（大きさの上限、パスの表示、実のパスと読まないファイルとハードリンクの数の確かめ、同じファイルを一度だけ読むこと、範囲の外へ出ない開き方）は、2026-10-17 に設計者が承認した。

1. 利用者の指示のファイル（`benitoiteh` の設定のディレクトリの `AGENTS.md`）
2. プロジェクトのディレクトリから上へ辿り、git のリポジトリの根（`.git` のあるディレクトリ）までの各ディレクトリの指示のファイル。根の側から順に並べる。git のリポジトリの外なら、プロジェクトのディレクトリだけを見る。見つかった根が利用者のホームディレクトリか、それより上のときも、リポジトリの外として扱う。理由: ホームディレクトリを設定のファイルの管理のためのリポジトリにしている利用者がいる。そのとき根まで辿ると、探す範囲がホームディレクトリの全体になり、そこに置かれた指示のファイルが、読まないファイルの一覧にない秘密（`~/.config` の下の認証の情報など）へのシンボリックリンクであっても、範囲の中として読んでしまう。

【決定】各ディレクトリでは `AGENTS.md` を読み、`AGENTS.md` がないときだけ `CLAUDE.md` を読む。一つのディレクトリからは一つのファイルだけを読む（2026-10-17 に設計者が決めた。BH-013 を閉じた）。理由: Benitoite の処理系のリポジトリは指示のファイルとして `AGENTS.md` だけを置いており、それに合わせて `AGENTS.md` を正とする。`AGENTS.md` がないときに限って `CLAUDE.md` を読めば、`CLAUDE.md` だけを置くリポジトリの指示も読め、両方を置くリポジトリ（`CLAUDE.md` を `AGENTS.md` へのシンボリックリンクにするものを含む）で同じ指示を二度入れずに済む。Codex CLI も、ディレクトリごとに候補の名前を順に見て、最初に見つかった一つだけを読む（[先行事例](../08-appendix/08-01-prior-art.md)の Codex CLI の「文脈と記録」）。利用者の指示のファイル（1）は `AGENTS.md` だけとする。

- 一つのファイルは 32 KiB、合計は 64 KiB までとし、超えた分は切り詰めたことを示して除く。
- 読んだファイルのパスを画面に示す。理由: 利用者が知らないうちに LLM の指示が増えることを避ける。Pi の作者が他のハーネスについて挙げた不満（利用者に見えないところで文脈に加える）に応える。
- 指示のファイルは信頼しない内容として扱う（[セキュリティモデル](../03-safety/03-01-security-model.md)の「プロジェクトの指示のファイル」）。
- プロジェクトの側の指示のファイル（2）は、通常のファイルで、実のパス（シンボリックリンクを辿った先）が git のリポジトリの根（リポジトリの外ならプロジェクトのディレクトリ）の中にあり、読まないファイル（[道具](01-03-tools.md)の「読まないファイル」）に当たらず、ハードリンクの数が 1 のときだけ読む。同じファイル（同じ装置と i ノード）は一度だけ読む。開くときは、探す範囲の根を開いた記述子から相対に、範囲の外へ出ない形で開く（[道具](01-03-tools.md)の「道具の定義の共通の規則」と同じ仕組み）。当たらないものは読まずに、読まなかったことと理由を画面に示す。開くときは待たない形（`O_NONBLOCK`）で開き、開いたものが通常のファイルであることを確かめてから読む。理由: プロジェクトは信頼しないので、指示のファイルを秘密へのシンボリックリンクにして、その中身を LLM の提供者へ送らせることを防ぐ。名前付きのパイプに置き換えられても、起動が止まらないようにする。

制限モードで指示のファイルを読むかは BH-042 で決める。

### 利用者の Agent Skill

【決定】`benitoiteh` は、Benitoite の Skill のほかに、利用者が定めた Agent Skill を、制限モードと通常モードの両方で読む（2026-10-19 に設計者が決めた）。読む場所は次の二つとする。

1. 利用者の Skill: `~/.agents/skills/<名前>/SKILL.md`
2. プロジェクトの Skill: プロジェクトの指示のファイルと同じ範囲（プロジェクトのディレクトリから git のリポジトリの根まで。リポジトリの外ならプロジェクトのディレクトリだけ）の各ディレクトリの `.agents/skills/<名前>/SKILL.md`

制限モードでも、プロジェクトの Skill を読み、読んだことを画面に示す（2026-10-19 に設計者が決めた）。理由: Benitoite で書いた道具（スクリプト）を Skill として配り、その使い方を LLM に伝えられるようにする。置き場所は、DeepSeek Harness（`<プロジェクトの根>/.agents/skills`。2026-10-18 の P5-04 の調べ）と Antigravity（作業ディレクトリから上の `.agents/`。同梱の文書の `json_configs.md`）と同じにし、一つの Skill を各ハーネスで共有できるようにする。制限モードでプロジェクトの Skill を読んでも、`sh` や Python の起動は、後述のとおり道具の作りと OS のサンドボックスで止まる。

【方針】Skill の読み方は、Agent Skills の段階的な読み込みに倣う（BH-102）。

- 起動のときに各 `SKILL.md` の先頭の `name` と `description` だけを読み、環境の情報に `<skills>` の塊として、名前、説明、`SKILL.md` の絶対パスを並べる。全文は、LLM が要るときに `read` で読む。一覧はセッションの間は変えない（キャッシュを保つ。途中で加えた Skill は次のセッションから読む）。
- 名前は、ディレクトリの名前と同じで、英小文字・数字・`-` の 64 文字までのものだけを受け付ける。説明は 1,024 文字まで、一覧は 100 個まで、一覧の合計は 16 KiB までとし、超えたものは除いて、除いたことと理由を画面に示す。【方針】上限は、利用者の Skill を先に名前の順で数え、残りの枠をプロジェクトの Skill に名前の順で配る（2026-10-19）。理由: 信頼しないリポジトリが名前の若い Skill を多く置いて、利用者の Skill を一覧から押し出すことを避ける。
- 同じ名前の Skill が二つ以上あるときは、利用者の Skill を、次にプロジェクトの根に近い側のものを採り、採らなかったものを画面に示す。名前 `benitoite` は Benitoite の Skill のために取っておき、利用者とプロジェクトの `benitoite` は読まない（処理系の版に合った Skill を使う。評価の道具が作業ディレクトリに置く Benitoite の Skill も、これで二重に読まない）。
- `SKILL.md` の先頭のほかの欄（`allowed-tools` など）は、道具や権限を与えるものとして扱わない。Skill は文書であり、使える道具と確認と OS のサンドボックスは、モードと利用者の設定だけで決まる。
- 開き方と読む条件は、プロジェクトの指示のファイルと同じとする（通常のファイル、読まないファイルに当たらない、ハードリンクの数が 1、待たない形で開く）。実のパスは、利用者の Skill ではホームディレクトリの中、プロジェクトの Skill では探す範囲の中になければならない（`.agents/skills/<名前>` を `.claude/skills/<名前>` へのシンボリックリンクにする置き方を、範囲の中なら受け付ける）。【方針】シンボリックリンクは、相対のパスのものだけを辿る。絶対のパスのリンクは、範囲の中を指していても読まない。Skill のディレクトリかプラグインのディレクトリの最後の要素が絶対のパスのリンクのときは、相対のリンクにするよう促す理由を示す。途中の要素（`.agents/skills` そのものなど）や `SKILL.md` が絶対のパスのリンクのときは、今は「範囲の外」の理由を示す（P5-24 の後の残り）。理由: 範囲を限って開く仕組み（Linux の `RESOLVE_BENEATH`、macOS の `O_RESOLVE_BENEATH`）は、絶対のパスのリンクを拒む（[道具](01-03-tools.md)の「道具の定義の共通の規則」）。2026-10-20 の P5-24 のレビューで、範囲の中を指す絶対のリンクが「範囲の外」という誤った理由で断られることを確かめた。加えて、`.agents/skills` の直下の項目の名前と、その実のパスの最後の要素の名前が、どちらも `name` と同じでなければならない。Skill のディレクトリの実のパスが、プロジェクトのディレクトリ、探す範囲の根、ホームディレクトリのどれかと同じか、その祖先であれば読まない。`SKILL.md` は、開いた Skill のディレクトリから相対に、範囲の外へ出ない形で開く。理由: `.agents/skills/x` をリポジトリの根やホームへのシンボリックリンクにすると、Skill のディレクトリとして読める範囲が、制限モードでもリポジトリの全体やホームに広がる（2026-10-19 の P5-09 の点検）。【方針】一つの `.agents/skills` の直下は、名前の順で最初の 1,000 項目だけを見る。理由: 信頼しないリポジトリが大量のディレクトリを置いて、起動を長く止めることを避ける。
- 読んだ Skill の名前とパスを画面に示し、セッションの記録のヘッダに、名前、パス、`SKILL.md` の SHA-256 を書く。
- Skill は信頼しない内容として扱う（[セキュリティモデル](../03-safety/03-01-security-model.md)の「プロジェクトの指示のファイル」と同じ）。

【方針】Skill のディレクトリの中のファイル（`SKILL.md`、参照の文書、スクリプト）は、読んだ Skill のディレクトリに限って、どちらのモードでも `read`・`glob`・`grep` で読めるようにする（[道具](01-03-tools.md)の「read」）。書くことはできない（制限モードはプロジェクトの `.bnt` だけを書け、通常モードはサンドボックスの書ける場所だけに書ける）。

【方針】Skill が指示するプログラムの起動は、モードで扱いを分ける。

- 通常モード: いつもどおり `bash` の道具で起動する。承認の方針と OS のサンドボックスは、ほかのコマンドと同じに掛かる。
- 制限モード: Skill のディレクトリの `.bnt` のスクリプトは、`benitoite_check`・`benitoite_run`・`benitoite_test` で検査し実行できる（パスが読んだ Skill のディレクトリの中なら、プロジェクトの外でもよい。実行の作業ディレクトリはプロジェクトのディレクトリとし、実行の前の確認とエフェクトの許す集合はほかのスクリプトと同じに掛かる）。Skill が `sh`・Python などの起動を指示していても、制限モードにはシェルの道具がなく、処理系の `Process.Run` も OS のサンドボックスで制限モードの許すプログラム（`restricted.allowed_programs`）に限られるので、起動できない。システムプロンプトの制限モードの規則に、「Skill がシェルやほかの言語のコマンドを指示していても、制限モードでは起動できないので、Benitoite で同じことを行うか、できないことを利用者に伝える」旨の一文を加える。

理由: 制限モードの保証（Benitoite 以外の言語の処理系を起動させない）は、今の作り（シェルの道具を持たせない、処理系の子プロセスに OS のサンドボックスを掛ける、エフェクトを確認する）で、Skill の中身に依らず成り立つ。このため、Skill のためにサーバモードや別の仕組みを加える必要はない。

【方針】利用者の設定ファイルの `[skills]` の `user`・`project`（既定はどちらも `true`）で、それぞれを読まないようにできる（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「設定ファイル」）。プロジェクトの設定ファイルでは受け付けない。評価では、利用者の Skill を読まない設定で走らせる（[評価](../07-quality/07-02-evaluation.md)）。

### Agent Plugins のプラグイン

【決定】Agent Plugins 1.0.0（<https://agent-plugins.org/specification>。2026-10-19 に読んだ）のプラグインのうち、Skill の部品を、制限モードと通常モードの両方で読む（2026-10-19 に設計者が決めた）。MCP サーバの部品（`mcp.json`）は読まず、将来の対応とする（BH-116）。理由: 仕様は、部品の種類を Skill と MCP サーバの二つだけと定め（「Agent Plugins v1 defines exactly two component types: skills and MCP servers.」）、Skill だけに対応するクライアントも仕様に合うとする（§11.2「a skills-only client can conform without supporting MCP servers」）。Skill は前節の利用者の Agent Skill と同じ形（Agent Skills の仕様）なので、同じ規則で読める。MCP サーバは、制限モードの保証（Benitoite 以外の言語の処理系を起動させない）と、型とエフェクトの検査を崩しうる（[目的と設計原則](../00-overview/00-01-goals.md)の「範囲の外」）。

- **置き場所**: 仕様は置き場所と有効にする方法を定めない。【方針】利用者のプラグインを `~/.agents/plugins/<名前>/`、プロジェクトのプラグインを、プロジェクトの Skill と同じ探す範囲の各ディレクトリの `.agents/plugins/<名前>/` に置く。理由: 前節の Agent Skill と同じ `.agents` の下に揃える。
- **`plugin.json` の検査**（仕様 §5、§11.1）: プラグインの根に `plugin.json` がなければプラグインとして扱わない。`$schema` が `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json` でなければ、プラグインを断り、対応しない版であることを画面に示す。`name` は 1〜64 文字の英小文字・数字・`-`・`.` で、先頭と末尾が英数字で、`--` と `..` を含まないもの（仕様の JSON Schema の規則）とし、【方針】置き場所の直下の項目の名前と、その実のパスの最後の要素の名前も `name` と同じでなければならない（前節の Skill と同じ規則）。仕様の欄（`$schema`、`name`、`version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords`、`extensions`）のほかの最上位の欄は、画面に示して無視する。ほかの形の誤りは、プラグインを断り、その部品を一つも読まない。`extensions` は使わない（対象でない形なら示して無視する）。仕様の拡張のディレクトリ（逆順のドメインの名前の最上位のディレクトリ）も読まない。
- **Skill の部品**（仕様 §7.1）: プラグインの `skills/` の直下の各ディレクトリの `SKILL.md` を、前節の規則（名前、大きさ、開き方、読む条件、Skill のディレクトリの読み取り、制限モードでの `.bnt` の扱い）で読む。規則に合わない Skill は、その Skill だけを飛ばし、理由を画面に示して、ほかを読み続ける。
- **パスの範囲**（仕様 §4.1）: プラグインの中のパスの実のパスは、プラグインの根の中になければならない（シンボリックリンクは、根の中を指すものだけを受け付ける）。外を指すものは読まない。
- **一覧と名前の重なり**: 仕様は、Skill の名前の付け方と、名前の重なりの扱いを定めない。【方針】利用者の段（利用者の Skill、次に利用者のプラグインの Skill をプラグインの名前の順）を先に、プロジェクトの段（プロジェクトの Skill、次にプロジェクトのプラグインの Skill）を後に数え、前節の一覧の上限（100 個、16 KiB）と名前の重なりの規則を当てる。名前 `benitoite` の Skill は、前節と同じく読まない。
- **MCP サーバの部品**: `mcp.json` があっても読まず、そのプラグインの MCP サーバを使わないことを画面に示す。`PLUGIN_ROOT` と `PLUGIN_DATA`（MCP サーバと子プロセスのための値）は設けない。
- **長さと数の上限**: 【方針】信頼しないリポジトリのプラグインで、記録と画面が膨らまないよう、仕様の型の範囲の外の上限を掛ける。`version` は `[0-9A-Za-z.+_-]` の 1〜64 文字に限り、合わなければ版を記録せず（`no version` と示す）、そのことを示す。読むプラグインの数は、利用者の段とプロジェクトの段のそれぞれで 100 個までとし、超えた分は数だけを示す。示す知らない欄の名前は、一つ 64 文字で切る。一覧の上限を越える Skill は、開かずに飛ばし、飛ばした数をまとめて示す。プラグインの Skill の候補（各プラグインの `skills/` の直下の項目）は、段ごとに、すべてのプラグインを合わせて 1,000 個までを開き、超えた分は開かずに数だけを示す。飛ばした Skill、断ったプラグイン、プラグインの通知は、利用者の Skill とプロジェクトの Skill の分も含めて、段ごとに 100 件までを一件ずつ画面に示して記録に書き、残りは数だけを示す。理由: 2026-10-20 のレビューで、長い `version` を持つ多数のプラグインで、セッションの記録のヘッダが 16 MiB を超えて分けて置かれ、そのセッションを一覧にも再開にも使えなくなることを確かめた。同じ日の再レビューで、規則に合わない候補（範囲の外へのリンクなど）と同名で負けた候補は一覧の上限に数えられないことを確かめた。このため、プラグイン 100 個に 1,000 個ずつ置くと、起動のたびに 10 万件を開いて一件ずつ示し、開始の記録が約 43 MB になる。【方針】件数に加えて、示す文の大きさも抑える。一つのプラグインの通知（知らない欄、`extensions`、`version`、`mcp.json`）は、一行にまとめる。段ごとに、通知の行と飛ばしたものの行は、合わせて 64 KiB（UTF-8 のバイト数）までを一件ずつ示して記録に書き、超えた分は数だけを示す。理由: 行に入るパスはリポジトリが選べ、OS の上限（Linux で約 4 KiB）まで延ばせる。件数だけを抑えると、長いパスの行が多数並んで、開始の記録が膨らむ。2026-10-20 の 2 回目の再レビューで、macOS で開始の記録が約 3.8 MB になることを確かめた。Linux では、分けて置く境（16 MiB）の約 9 割まで膨らむと見積もった。64 KiB の枠は、画面と記録で制御文字を逃がす前のバイト数で数える。読んだプラグインの行は枠の外とし、段ごとの 100 個の上限で抑える。2026-10-20 の P5-24 のレビューの見積もりでは、これらを合わせた開始の記録は、macOS で段ごとに約 1 MB、Linux で約 3 MB であり、16 MiB の境の内に収まる。【方針】段ごとの候補の上限や一覧の上限で開かなかった候補の名前も、利用者の段では、後の段との名前の重なりの判定に使う（開けば Skill にならない項目も含む）。理由: 開かずに飛ばしたことで、プロジェクトの Skill が、開いた場合には隠れるはずの利用者の名前を取れるようにしない。プロジェクトの段の後には段がないので、覚えない。
- **記録と表示**: 読んだプラグインの名前、版、パス、`plugin.json` の SHA-256 を、画面に示し、セッションの記録のヘッダに書く（前節の Skill の記録に、どのプラグインの Skill かを加える）。【方針】画面の一行では、出所、SHA-256、版を先に、パスを最後に置く。理由: パスにはリポジトリが選べる文字（`;`・`(`・`)`）が入りうる。パスの後ろにほかの欄を置くと、パスの中の文字でほかの欄を装える（2026-10-20 の再レビュー）。
- **設定**: 利用者の設定ファイルの `[plugins]` の `user`・`project`（既定はどちらも `true`）で、それぞれを読まないようにできる。プロジェクトの設定ファイルでは受け付けない。評価では、利用者のプラグインを読まない設定で走らせる。

### 送る内容の表示

【方針】セッションの初めに、使う提供者とモデル、要求を送るホストの名前を画面に示し、読んだファイルの中身、スクリプトとコマンドの出力、診断が提供者へ送られることを一行で示す。非対話では、同じ内容を `session_start` のイベントに含める。Benitoite の事前検討の見立て（Benitoite の docs/todo の TODO-132 の「利用者への表示」）を引き継ぐ。

### 文脈の大きさの見積もり

【方針】文脈の大きさは、最後の応答で提供者が報告した入力のトークンの量の全体に、その後に加えた内容の UTF-8 のバイトの数を 3 で割った値を足して見積もる。報告がないとき（セッションの初め）は、すべてをバイトの数で見積もる。入力の全体は、提供者ごとの報告の形の違いを、[提供者の層](../02-providers/02-01-provider-layer.md)の「共通の形」の規則で揃えた値とする（Anthropic では、キャッシュを使わない入力、キャッシュから読んだ量、キャッシュに書いた量の和）。理由: 提供者ごとのトークンの数え方（トークナイザ）を `benitoiteh` に持たせると実行ファイルが大きくなる。英語の文は 1 トークンがおよそ 4 文字なので、バイトの数を 3 で割ると多めに見積もる。日本語の文字は UTF-8 で 3 バイトであり、1 文字あたりのトークンが英語より多いので、文字の数を 4 で割る見積もりでは少なく見積もりすぎるおそれがある。少なく見積もると、圧縮が遅れて提供者に超過を返される。見積もりの誤差は、評価で実際の報告と比べて確かめる（BH-014）。

### 圧縮

Benitoite の事前検討は圧縮を初めは設けないとしたが、試作では設ける。理由: 長い作業を一つのセッションで続けられることは、エージェントとしての性能の目標（[目的と設計原則](../00-overview/00-01-goals.md)の「性能の目標」）に含まれる。比べた三つのハーネスのうち、圧縮を持たないのは DeepSeek Harness の評価用の最小の構成だけであり、それは文脈が 100 万トークンのモデルを前提にしている。

【方針】圧縮は次のように行う。

- **時機**: 番の前に、見積もった文脈の大きさが「モデルの文脈の上限 − 予備」を超えたら行う。予備は、出力の上限のトークンの量に 16,384 を足した値とし、文脈の上限の半分を超えない値に抑える。利用者が `/compact` で求めたときと、提供者が文脈の超過の誤りを返したとき（[エージェントのループ](01-01-agent-loop.md)の「やり直し」）も行う。
- **上限が分からないとき**: モデルの文脈の上限（提供者の設定の `context_window`）が設定されていなければ、番の前の判定では圧縮せず、`/compact` と文脈の超過のときだけ圧縮する。出力の上限（`max_output_tokens`）が設定されていなければ、予備の計算では 32,000 とみなす（Anthropic の要求に、指定がないときに送る値）。超過したときの圧縮で文脈の上限が分からなければ、このセッションで提供者が報告した入力の全体の最も大きい値（その要求は受け付けられたので、上限より小さい）を上限の代わりに使い、報告がなければ、今の会話の見積もりの半分を使う。理由: 提供者とモデルごとの上限を実行ファイルに持つと古くなる。超過の誤りは提供者が示すので、上限を知らなくても圧縮できる。
- **残す範囲**: 新しい側から、約 20,000 トークンと文脈の上限の 4 分の 1 の小さい方の量の会話を、そのまま残す。境界は、道具の呼び出しと結果の間に置かない。理由: 文脈の上限が小さいモデル（手元の推論サーバ）では、20,000 トークンを残すと、圧縮の後も上限に近いままになる。
- **要約の作り方**: 今の会話をそのまま送り、その末尾に、要約を求める発言を加えて要求する。道具を呼ばせない指定（`tool_choice` の `none` に当たるもの）を付ける。理由: 会話の先頭が前の要求と一致するので、キャッシュが効く。DeepSeek Harness が同じ作り方をしている。道具を呼ばせない指定を持たない提供者では、Pi の作り方（会話を文字にして `<conversation>` で囲み、別の要求で要約させる）を使う。ただし、Anthropic では `tool_choice` を変えず（`auto` のまま）、要約の依頼の末尾に道具を呼ばないことを求める文を置き、応答が道具を呼んだら呼び出しを捨てて文だけを使う。文が空なら Pi の作り方でやり直す。理由: Anthropic のプロンプトのキャッシュは、`tool_choice` を変えると会話の部分のキャッシュを失い、道具の定義とシステムプロンプトの部分だけが残る（[prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) の「What invalidates the cache」の表。2026-10-17 に確かめた）。圧縮は文脈が大きいときに行うので、会話の部分のキャッシュを保つ効果が大きい。
- **超過したときの圧縮**: 提供者が文脈の超過を返したときは、今の会話に要約の依頼を足して送らず、Pi の作り方で、要約する側の会話を文字にした別の要求を作る。その要求は、見積もりが文脈の上限の半分に収まるまで、大きい道具の結果を先頭と末尾だけに縮め、それでも収まらなければ古い側から除く。除いたことは要約の依頼に書く。それでも収まらないとき、またはこの圧縮の後の要求も超過したときは、一連の処理を止めて利用者に示す。理由: 超過した会話に依頼を足した要求は、さらに大きく、また超過する。
- **要約の形**: 次の見出しを持つ Markdown とする。Pi の型板と DeepSeek Harness の型板を合わせたものである。
  - `## Goal`（利用者の依頼と意図）
  - `## Constraints & Preferences`
  - `## Progress`（`### Done`・`### In Progress`・`### Blocked`）
  - `## Key Decisions`
  - `## Errors and Fixes`（診断のコードと、直し方）
  - `## Next Steps`
  - `## Critical Context`

  ファイルのパス、関数の名前、診断のコード、誤りの文を正確に残すよう指示する。前の要約があれば、一つにまとめるよう指示する。
- **ファイルの一覧**: 読んだファイルと変えたファイルの一覧は、LLM に作らせず、`benitoiteh` がセッションの記録から作って要約の後に加える。
- **圧縮の後の文脈**: システムプロンプト、道具の定義、環境の情報、要約（`<compacted_summary>` で囲んだ利用者の側の発言）、残した会話の順に並べる。
- **推論の内容の扱い**: 圧縮の後に残した会話の中の推論の内容を送るかは、アダプタと提供者ごとに決める（[提供者の層](../02-providers/02-01-provider-layer.md)の「提供者ごとの機能の表」の `reasoning_replay`）。一つの規則で全提供者を揃えない。理由: 提供者の求めが逆向きだからである。
  - Anthropic: 残した番の thinking のブロックを除き、文と道具の呼び出しと結果だけを送る。Anthropic の API は、thinking のブロックを、それより前のシステムプロンプト、道具の一覧、会話に結び付けて検査し、変わっていれば要求を 400 の誤りで拒む（Claude Fable 5.1、Opus 5.5、Sonnet 5.5、Haiku 5.5。2026-08-31 以降に作られたアカウントでは既定で働く）。古い側を要約に置き換えると、残した番の前の会話が変わる。Anthropic の文書は、自前の要約で新しい側を残す形では、残した番の thinking のブロックを除くよう求めている（[preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)、[圧縮](https://platform.claude.com/docs/en/build-with-claude/compaction)。2026-10-16 に確かめた）。圧縮は番の前に行うので、道具の呼び出しが続いている途中（最後の応答が道具を呼び、その結果を加えた直後）にも起こる。そのとき、最後の応答の thinking のブロックを除いた要求が受け付けられるかは確かめる（【要検証】BH-036）。受け付けられなければ、道具の呼び出しが続いている途中の圧縮では、残す範囲を設けない。確かめるまでは、Anthropic で道具の呼び出しが続いている途中に圧縮するときは、残す範囲を設けない。理由: 受け付けられない形を送ると、圧縮の直後の要求が 400 の誤りになり、一連の処理が止まる。
  - DeepSeek の推論のモード（Chat Completions の口）: 要求が道具の定義を含むときは、残した番の推論の文（`reasoning_content`）を送る。DeepSeek の文書は、要求が道具を含むとき、道具を呼ばなかった番も含めて、前のすべての番の推論の文を送り返すよう求め、欠けると 400 の誤りを返すとしている（[DeepSeek の文書の推論のモード](https://api-docs.deepseek.com/guides/thinking_mode/)。2026-10-16 に確かめた）。要約に置き換えた番は会話に残らないので、その推論の文は送らない。この形の要求が受け付けられるかは確かめる（【要検証】BH-031）。
  - ほかの提供者: 機能の表の既定は送らないとし、提供者の文書で確かめたものから表に加える。
- **圧縮しない時機**: 道具の呼び出しに結果がまだ対応していない時点（一つの応答の道具の実行の途中）では圧縮しない。番の前にだけ判定するので、この時点には当たらない。
- **文脈の外に持つ状態**: 確認したエフェクトの記録、読んだファイルの版、検査と修正の回数は、`benitoiteh` が会話の外に持つので、圧縮で失われない。

予備の値と残す量は、評価で見直す（BH-014）。圧縮の要約に使うモデルを、作業のモデルと分けるかは、事前検討が役割ごとにモデルを分けることを対象外とした（ADR 0343）のに従い、試作でも分けない。

#### 圧縮の値を比べる設定

【方針】評価のために、利用者の設定ファイルの `[compaction]` に次の二つの非負の整数を設ける。プロジェクトの設定ファイルでは受け付けない。理由: 今の固定値だけを一つずつ変え、圧縮の境界や提供者ごとの扱いを変えずに比較する。

| 鍵 | 既定 | 用途 |
|---|---:|---|
| `reserve_tokens` | 16,384 | 出力の上限に足す予備。予備全体は `min(max_output_tokens + reserve_tokens, context_window / 2)` とする。加算は飽和させる |
| `keep_tokens` | 20,000 | そのまま残す会話の目安。文脈の上限が分かるときは `min(keep_tokens, context_window / 4)` とする |

上限が分からないときの残す量は `keep_tokens` とし、`0` は残す範囲なしを表す。超過したときに上限の代わりの値を使う規則、道具の呼び出しと結果を分けない規則、Anthropic の道具の呼び出しが続く途中と送り先の変化による圧縮で残す範囲を設けない規則は、設定より優先する。設定を省けば、今の圧縮と同じになる。

【方針】残す量の記録 `kept_estimate` は、残すと選んだ範囲について、会話を再構築する前のバイト数の和を 3 で切り上げて割った値とする。範囲を選ぶときと同じ数え方を使い、残す範囲がなければ 0 とする。再構築で推論の内容を除く場合は、実際に送る残した会話の見積もりより多くなりうる。理由: `keep_tokens` に収まるかを判定した量を記録し、設定と選ばれた範囲を対応させる。

【方針】短い費用で圧縮を評価するには、既存の提供者の設定 `context_window` を小さくし、依頼を複数の段に分けて同じセッションで続ける。これは `benitoiteh` が圧縮を判定する上限であり、提供者の実際の上限を変える指定ではない。理由: 実際の上限まで会話を伸ばすより、送るトークンの量を少なくできる。

DeepSeek の Anthropic 互換の口では、道具の呼び出しが続く途中の圧縮は、上の Anthropic の規則で残す範囲がなくなる。残す量の比較では、前の依頼を正常に終え、次の依頼を加えた番の前にも圧縮を起こす。実際に残した項目の数と量を記録し、残す範囲が常に 0 の試行から、残す量の効果を結論しない。具体的な課題と条件は[評価](../07-quality/07-02-evaluation.md)の「M の段の圧縮」で定める。結果が出るまでは BH-014 を閉じない。

### 推論の内容の扱い

【方針】モデルが返した推論の内容（Anthropic の thinking のブロックと署名、OpenAI の Responses の暗号化した推論の項目など）は、作ったときと同じ送り先（提供者の設定の名前、ベースの URL、モデルの組）で、同じシステムプロンプトと道具の定義の要求では、提供者の定めに従ってそのまま送り返す。どれかが違うときは送らない。違うかは、セッションの記録に残したシステムプロンプトと道具の定義のハッシュで判定する（[セッション](01-05-sessions.md)の「再開」）。理由: 道具を呼ぶ番の推論を送り返すことを求める提供者がある。一方、Anthropic の thinking のブロックは、前のシステムプロンプトと道具の一覧に結び付けて検査され、`benitoiteh` を新しい版にしてから再開すると、同じモデルでもシステムプロンプトが変わりうる。別のモデルの推論を送ると、新しいモデルがそれを自分の応答の一部と読むおそれがあり、Pi は別のモデルの推論を送らないように改めている（[先行事例](../08-appendix/08-01-prior-art.md)）。提供者ごとの扱いは[提供者の層](../02-providers/02-01-provider-layer.md)で定める。

【方針】すべての番の推論の文の送り返しを求める提供者（DeepSeek の推論のモード）で、送り先かハッシュが記録と違うときは、最初の要求の前に圧縮し、残す範囲を設けずに、要約だけを置いた新しい文脈で続ける。要約は、Pi の作り方（会話を文字にした別の要求）で作る。理由: 送り返さなければ 400 の誤りになり、違う送り先の推論を送ることもできない。古い番を会話に残さなければ、送り返すべき推論の文がなくなる。

【決定】推論の内容は、画面には要約だけを示し、送り返しのための推論の内容は、示すかどうかに関わらず記録に残す（2026-10-17 に設計者が決めた。BH-015 を閉じた）。要約は、提供者が返す推論の要約（OpenAI の Responses の推論の要約など）とし、要約を返さない提供者で推論の文の全文が届くときは、先頭の数行だけを示す。【要検証】Anthropic の thinking の文が要約か全文か、要約を指定する方法（`display` の指定）は、一次資料で確かめる（BH-096）。理由: 推論の全文は長く、出力の流れを読みにくくする。示さないと、長い推論の間に何が起きているかが利用者に分からない。
