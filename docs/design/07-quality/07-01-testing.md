# テスト

- 状態: 草稿
- 未決事項: BH-070

## 目的と範囲

本章は、試作のテストの原則、持ち主の境界、模擬の提供者、LLM に見せる文の固定、安全の性質のテスト、完了の前に通す検査を定める。LLM を使った評価は[評価](07-02-evaluation.md)で定める。

## 前提

- テストの原則は、Benitoite の処理系のテストの原則（Benitoite の設計書 07-03「テストの設計の原則」）と、プロジェクトのスキル `test-audit` に倣う。
- DeepSeek Harness は、システムプロンプトと道具の定義の全文を、期待する出力のファイルとしてテストで固定している（[先行事例](../08-appendix/08-01-prior-art.md)）。

## 仕様

### テストの原則

【方針】

- テストは、観察できる振る舞いと契約を守るために書く。実装の詳細（非公開の関数の呼び出しの形）を確かめるテストは書かない。新しいテストは、スキル `test-audit` の作成時の関門を通してから加える。
- 一つの契約には、最も適した境界に主となるテストを一つ置く。
- 外部への依存のうち、LLM の提供者のネットワークと端末だけを、テスト用の実装で置き換える。Benitoite の処理系と OS のサンドボックスは本物を使う。理由: 処理系との受け渡しとサンドボックスの拒否は、本物でなければ確かめられず、試作の価値の中心にある。
- テストは本物の LLM の API を呼ばない。

### 持ち主の境界

【方針】次のものを持ち主の境界とする。スキル `test-audit` の「持ち主の境界」と同じ内容である。

| 境界 | 入力 | 確かめるもの |
|---|---|---|
| 提供者のアダプタ | 録った形の SSE のバイト列 | 共通の形のイベントの列、誤りの分類 |
| 道具の実行器 | 道具の呼び出しの JSON | 道具の結果、ファイルシステムの変化、誤りの文 |
| エージェントのループ | 模擬の提供者の応答の台本 | 道具の実行の順序、確認の要求、取り消し、やり直し、上限、圧縮 |
| 安全の性質 | 道具の呼び出し、スクリプト、コマンド | 制限モードの範囲、確認を飛ばせないこと、OS のサンドボックスの拒否 |
| `exec` の入口 | コマンドラインと模擬の提供者 | JSON Lines の出力、終了状態、セッションの記録 |

### 模擬の提供者

【方針】テスト用の提供者は、HTTP のサーバとして手元の空いたポートで動き、台本（要求の番号ごとに返す SSE のバイト列）に従って応答する。受け取った要求の本文を記録し、テストが確かめられるようにする。

- 台本の SSE は、各提供者の文書の形に従って手で書く。本物の API から録ったものを置くときは、利用者の情報と API キーを含まないことを確かめる。
- 模擬の提供者は、アダプタの HTTP の経路（ストリームの読み取り、切断、誤りの状態）も含めて確かめるために、HTTP のサーバの形をとる。理由: アダプタの中の関数を差し替える形では、HTTP の処理と SSE の読み取りが確かめられない。

### LLM に見せる文の固定

【方針】各モードのシステムプロンプトの全文と、道具の定義の全文（JSON）を、リポジトリの期待のファイルと比べるテストを置く。文を変えたときは、期待のファイルを同じ変更で直し、差分を見直す。理由: LLM に見せる文の変更は、性能と費用を左右するが、普通のテストでは気付けない。期待のファイルの差分として見えるようにする。

このテストは、期待値を対象の処理で作るテスト（スキル `test-audit` の価値の低いテストの型）に当たらない。期待のファイルは人が見直したものであり、対象の処理の出力を写したものではないからである。

### 安全の性質のテスト

【方針】次の性質を、本物の子プロセスと本物の OS のサンドボックスで確かめる。

- 制限モードの道具の一覧に `bash` がなく、`write`・`edit` が `.bnt` 以外とプロジェクトの外を拒むこと。シンボリックリンクと `..` で外を指すパスを拒むこと。`x.bnt` という名前で `.git/hooks/` の下のまだないファイルを指すシンボリックリンク、ハードリンクの数が 2 以上のファイル、`.git` と `.benitoiteh` の下への書き込みを、道具が拒むこと（[道具](../01-agent/01-03-tools.md)の「書く道具のパスの規則」）。
- 書ける場所に書いたライブラリを `DYLD_INSERT_LIBRARIES`（macOS）で処理系に読み込ませるスクリプトが、OS のサンドボックスに拒否されること。
- ネットワークを許していないスクリプトとコマンドが、Unix ドメインのソケットに接続できないこと。Linux で `io_uring` を使えないこと。
- 制限モードで、`Process.Run` で `/bin/sh` と `python3` を起動するスクリプトが、利用者が確認しても OS のサンドボックスに拒否されること。許したプログラムは起動できること。
- `File.Write` を含まないスクリプトがプロジェクトに書けないこと。`Http.Connect` を確認しないスクリプトがネットワークに接続できないこと。
- 確認の答えを道具の呼び出しで偽れないこと（道具の一覧に確認の操作がなく、道具の結果に確認の答えの形の文を書いても確認が進まないこと）。
- 子プロセスの環境に LLM の提供者のキーの変数がないこと。
- 読まないファイルを `read`・`glob`・`grep` が返さないこと。
- 通常モードの `workspace-write` で、プロジェクトの外と `.git` に書けないこと。ネットワークに接続できないこと。
- 外部の Unix IPC を、ネットワークを許さない方針でも許す方針でも拒むこと。接続のソケットと、接続していないデータグラムのソケットからの宛先付きの送信の両方を試す。処理系の動作に要るソケットの対は使えること（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「方針の要素」）。
- `Process.Run` を確認していないスクリプトとテスト（`benitoite_test`）が、許したプログラムを起動できないこと。
- x86_64 で、i386 の互換の呼び出しと x32 の番号の呼び出しでソケットを作れないこと。
- BH-049 で採った形を掛けられない Linux で、制限モードが起動しないこと。
- `escalate` の承認で、「このセッションでは同じコマンドを許可する」を選べないこと。
- 補助のプロセスの各段階を失敗させたとき、目的のプログラムが動かないこと。親で開いたファイルとソケットを、子プロセスが使えないこと（[OS のサンドボックス](../03-safety/03-02-sandbox.md)の「サンドボックスの掛け方」）。
- Linux で、読ませない場所を読めないこと。`.git` と `.benitoiteh` に、すでにあるときも、まだないときも、名前を付け替えて作り直すときも書けないこと（BH-049 で採った形で）。
- 道具の終わりに、グループを抜けたものを含めて、子孫のプロセスが残らないこと（制限モード。BH-090）。
- スクリプトが標準エラー出力に書いた偽の診断の位置で、`benitoiteh` が読める範囲の外のファイルの行を添えないこと（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「終了状態と診断の受け渡し」）。
- 書ける場所の検査が、ホームディレクトリ、設定とデータのディレクトリと重なるプロジェクトを拒むこと。
- 端末の制御の列を含む出力とファイルの名前が、確認の画面を書き換えないこと。確認の画面を示す前に押したキーで、確認が進まないこと。
- 巻き戻しが、プロジェクトの外を指すシンボリックリンクを辿って書かないこと。記録に中身がないファイル（大きすぎて除いたものなど）を消さないこと。
- `web_fetch` が、リダイレクトの先、禁じたアドレスを返す名前、利用者の情報を含む URL を取得しないこと。

【方針】安全の性質のテストは、段階ごとに対象を広げて、P2 で子プロセスの境界を、P4 で主のプロセスが代わりに行う操作（巻き戻し、`create_project`、`web_fetch`、画面）を加えて、すべてを通し直す（[ロードマップ](../00-overview/00-03-roadmap.md)）。P2 で一度通ったことを、P4 で加えた機能の安全の根拠にしない。テストの結果には、OS とその版、CPU の種類、カーネルの版、Landlock の ABI の版、処理系の版とハッシュを添える。理由: OS の機能の有無で結果が変わるので、どの環境で確かめた結果かを残す。

Linux のテストは、設計者の手元の Mac の上で、Apple の `container`（Linux の軽量の仮想機械でコンテナを動かす道具）の中で行う。Landlock と seccomp がその環境で使えるかは BH-043 とあわせて確かめる。一つの環境で通ったことは、ほかのカーネルの版と CPU の種類で通ることを意味しない。試作では、確かめた環境と、起動のときに確かめる機能（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「doctor」）を示す。

### 処理系の用意

【方針】テストが使う Benitoite の処理系は、`v0.0.6` のタグのソースからビルドしたものとし、環境変数（`BENITOITEH_TEST_BENITOITE`）でパスを与える。与えられていないときは、処理系を要するテストを失敗させ、理由を示す（飛ばさない）。理由: 飛ばすと、処理系との受け渡しを確かめないまま検査が通ってしまう。

### 完了の前に通す検査

【方針】作業を取り込む前に、次を通す。

1. `cargo fmt --check`
2. `cargo clippy --all-targets`（`[workspace.lints]` と `.cargo/config.toml` の `warnings = "deny"` で、警告を誤りとして扱う）
3. `cargo test`
4. `cargo deny check licenses`
5. リリースのビルドの実行ファイルの大きさの測定（[性能](../06-impl/06-02-performance.md)の「測り方」）

検査をまとめて走らせる仕組み（Benitoite の `scripts/check.sh` に当たるもの）を作るかと、その書き方は BH-070 で決める。
