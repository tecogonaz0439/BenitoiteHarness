# セキュリティモデル

- 状態: 草稿
- 未決事項: BH-040, BH-041, BH-042

## 目的と範囲

本章は、`benitoiteh` の脅威モデルと、モードごとに保証することと保証しないことを定める。保証を実現する仕組みは、[OS のサンドボックス](03-02-sandbox.md)と[利用者の確認](03-03-approval.md)で定める。モードの定義は[モード](../01-agent/01-02-modes.md)で、LLM に与える道具は[道具](../01-agent/01-03-tools.md)で定める。

## 前提

- Benitoite の処理系は、静的検査（型とエフェクトの規則への適合）だけを保証し、実行時の権限制御と OS のサンドボックスを持たない。隔離は処理系を起動する側に委ねる（[Benitoite のセキュリティモデル](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.6/docs/design/07-quality/07-01-security-model.md)）。`benitoiteh` は、この「起動する側」に当たる。
- 検査を通ったスクリプトは、`main` の `uses` にない組み込みの操作を行わない（同上の「各機構が保証すること」）。エフェクトは操作の種類を表し、どのファイル・どのコマンド・どのホストかは表さない。
- Benitoite の事前検討は、エージェントハーネスの脅威の前提を「エージェントハーネスのコードは信頼し、LLM の出力と、LLM が読んだファイル・ウェブのページ・実行結果に含まれる指示は信頼しない」と定めた（[ADR 0345](https://github.com/tecogonaz0439/Benitoite/blob/v0.0.6/docs/archive/2026-10-09-design-first-release/decisions/0345-agent-harness-confirmation-and-server-approval.md)）。本章はこれを引き継ぐ。

## 仕様

### 関係する者と信頼

| 者 | 信頼 | 理由 |
|---|---|---|
| 利用者 | 信頼する | `benitoiteh` を起動し、モードと許可を決める |
| `benitoiteh` のコード | 信頼する | 確認と OS のサンドボックスを掛ける主体である |
| Benitoite の処理系（`benitoite`） | 信頼する。ただし実行するスクリプトは信頼しない | 利用者が自分でビルドした処理系を使う |
| LLM の出力（文と道具の呼び出し） | 信頼しない | 依頼と違う意図を持ちうる。プロンプトインジェクションで誘導されうる |
| LLM が読む内容（ファイル、ウェブのページ、スクリプトと外部コマンドの出力） | 信頼しない | 第三者が指示を埋め込める |
| LLM が書いたスクリプトと、LLM が打つシェルのコマンド | 信頼しない | LLM の出力から作られる |
| プロジェクトの設定ファイルと、プロジェクトの指示のファイル（`AGENTS.md` など） | 信頼しない | 他人のリポジトリで `benitoiteh` を起動しうる |
| LLM の提供者 | 送った内容を、利用者が選んだ提供者の条件で扱うことを信頼する | 送る内容は利用者に示す（[文脈の管理](../01-agent/01-04-context.md)の「送る内容の表示」） |

### 守るもの

- プロジェクトの外のファイル（ホームディレクトリの設定、SSH の鍵、ほかのプロジェクト）。
- プロジェクトの中のファイル。誤った変更は巻き戻しで戻せるようにする（[セッション](../01-agent/01-05-sessions.md)の「巻き戻し」）。
- 秘密の情報。LLM の提供者の API キー、OAuth のトークン、秘密を含みやすいファイル（`.env`、秘密鍵）。
- 計算機の操作の範囲。制限モードでは、Benitoite 以外の言語の処理系を起動させない。
- 利用者の費用。LLM の利用料が上限なく増えないようにする（[エージェントのループ](../01-agent/01-01-agent-loop.md)の「上限」）。

### 信頼の境界

境界は三つある。

1. **LLM と `benitoiteh` の間**。LLM の道具の呼び出しは要求にすぎず、`benitoiteh` が引数を検証し、モードの道具の範囲と確認の規則に従って実行するかを決める。LLM に与える道具には、確認を承認する操作も、モードや許可を変える操作も含めない。
2. **`benitoiteh` と子プロセスの間**。`benitoiteh` が起動する子プロセス（Benitoite の処理系、通常モードのシェルのコマンド）には、OS のサンドボックスを掛ける。子プロセスの中で動くものは、この境界の外に出られない。子プロセスの出力（診断の JSON を含む）は信頼しない内容であり、`benitoiteh` はそれを読んで、子プロセスに許していない操作を代わりに行わない（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「終了状態と診断の受け渡し」）。
3. **利用者の設定とプロジェクトの設定の間**。プロジェクトの設定は、利用者の設定が許した範囲を広げられない（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「プロジェクトの設定ファイル」）。Benitoite の事前検討の方針（Benitoite の docs/todo の TODO-133 の対策 (a)）を引き継ぐ。

### 制限モードで保証すること

【方針】制限モードは、OS のサンドボックスが働く環境（[OS のサンドボックス](03-02-sandbox.md)の「対応する OS」）で、次のことを保証する。

- **R1 起動できるプログラム**: LLM の道具が起動するプログラムは Benitoite の処理系だけである。処理系の子プロセスが起動できるプログラムは、処理系自身と、利用者の設定で許したコマンド（`Process.Run` を確認したか、非対話で `--allow` に含めたときだけ）だけであり、OS のサンドボックスが強制する。利用者の設定で許したコマンドが別の言語の処理系であるときは、`benitoiteh` が設定を拒否する（[OS のサンドボックス](03-02-sandbox.md)の「制限モードで実行を許すプログラム」）。
- **R2 LLM が書けるファイル**: LLM の道具で書けるのは、プロジェクトのディレクトリの下の `.bnt` のファイルと、セッションごとの一時ディレクトリの `.bnt` のファイルだけである。
- **R3 実行の前の確認**: スクリプトを初めて実行するときと、`main`（テストでは対象のファイルのすべての `uses` の和）のエフェクトが前に確認したときより増えたときは、利用者の確認を受けてから実行する。非対話では、起動のときに許したエフェクトの範囲を超えるスクリプトを実行しない（[利用者の確認](03-03-approval.md)）。
- **R4 スクリプトの書き込みとネットワーク**: スクリプトが書き込めるのは、プロジェクトのディレクトリと一時ディレクトリだけであり、ネットワークに接続できるのは、エフェクトに `Http.Connect` か `Http.Listen` を含み、利用者が確認したときだけである。サンドボックスの外のプロセスとの Unix ドメインのソケットによる通信（外部の Unix IPC）は、ネットワークを確認したときもできない（macOS で、名前の解決などに要ると確かめて許した宛先を除く。BH-044）。どれも OS のサンドボックスが強制する。
- **R5 秘密**: 処理系の子プロセスの環境から LLM の提供者のキーの変数を除く（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系の起動」）。`read`・`glob`・`grep` は秘密を含みやすいファイルを既定で読まない（[道具](../01-agent/01-03-tools.md)の「読まないファイル」）。

### 通常モードで保証すること

【方針】通常モードは、次のことを保証する。

- **N1 サンドボックスの中での実行**: シェルのコマンドと処理系は、利用者が選んだサンドボックスの方針（既定はプロジェクトの中だけに書け、ネットワークを使えない方針）の中で動く。利用者がサンドボックスを外すことを選んだときは、この保証はない（[OS のサンドボックス](03-02-sandbox.md)の「通常モードの方針」）。
- **N2 範囲の外の操作の確認**: サンドボックスの範囲の外で動かす要求は、利用者の確認を受けてから行う。LLM は確認を承認できない（[利用者の確認](03-03-approval.md)の「通常モードの承認の方針」）。
- **N3 秘密**: 子プロセスの環境から LLM の提供者のキーの変数を除く。

通常モードは、シェルで別の言語の処理系を起動することを妨げない。これは利用者の要件（通常モードは一般的なハーネスと同じく振る舞う）による。

### 保証しないこと

どちらのモードでも、次のことは保証しない。

- **意図との一致**。プロンプトインジェクションや LLM の誤りで、利用者の意図と違うスクリプトやコマンドが作られることは防げない。確認とサンドボックスが防ぐのは、そのスクリプトやコマンドが、確認を受けていない種類の操作や、サンドボックスが許さない操作を行うことである。
- **`Process.Run` を確認したスクリプトの操作**。処理系は起動を許すプログラムに含まれるので、`Process.Run` を確認したスクリプトは、処理系で別のスクリプトを起動でき、その別のスクリプトは確認していないエフェクトのうち OS のサンドボックスが拒まないもの（`File.Read`・`Process.Environment` など）を使える。`Process.Run` の確認は、サンドボックスが許すすべての操作を許すのと同じである。確認の画面でそう示す（[利用者の確認](03-03-approval.md)の「制限モードの確認」）。
- **許したプログラムが内蔵する解釈系**。利用者が許したプログラムが解釈系を内蔵していれば（名前の一覧にないもの、名前を変えた写し）、そのプログラムを通じて Benitoite 以外のコードを動かせる（[OS のサンドボックス](03-02-sandbox.md)の「制限モードで実行を許すプログラム」）。R1 は、許したプログラムが解釈系を持たないことを前提とする。
- **許した操作の中の対象**。`File.Write` を確認したスクリプトは、サンドボックスが許す範囲のどのファイルにも書ける。`Http.Connect` を確認したスクリプトは、どのホストにも接続できる。このため、プロジェクトの中で読んだ内容を、確認したネットワークの操作で外へ送ることは防げない（【未決】ホストの範囲を限るか BH-040）。
- **LLM の提供者へ送る内容**。読んだファイル、スクリプトの出力、診断は LLM の提供者へ送られる。送る内容は利用者に示すが、送ること自体は道具の働きの一部である。
- **ウェブの取得による持ち出し**。`web_fetch` を使うときは、許したドメインへの URL に内容を載せて送ることを防げない（[道具](../01-agent/01-03-tools.md)の「web_fetch」）。
- **検査と実行の間の変更**。`benitoiteh` が検査してエフェクトを読み取ったスクリプトと、処理系がその後に読み込んで実行するスクリプトは、同じファイルを別々に読む。その間に LLM の道具の外（利用者のエディタ、ほかのプロセス）でファイルが変えられると、確認したエフェクトと、実行したスクリプトのエフェクトが食い違いうる。そのときも、OS のサンドボックスは確認したエフェクトから作った方針で掛かるので、R1 と R4 は成り立つ。処理系が、実行の前に `main` のエフェクトが指定した範囲に収まることを確かめる機能（BH-027）を持てば、この食い違いはなくなる。
- **前からあるハードリンク**。書ける場所の中の名前が、セッションの前から、書ける場所の外の名前と同じファイルを指しているとき（ハードリンク）、`File.Write` を確認したスクリプトがその名前に書くと、外の名前から見える内容も変わる。R4 は、書ける場所を名前（パス）で限る保証である。`benitoiteh` は、巻き戻しの記録のためにプロジェクトを辿るときに、ハードリンクの数が 2 以上の通常のファイルを見つけたら、その一覧を画面に示す（[セッション](../01-agent/01-05-sessions.md)の「巻き戻し」）。サンドボックスの中から、書ける場所の外のファイルへのハードリンクを新しく作れないことは、2026-10-17 に macOS と Linux で確かめた（BH-092）。
- **グループを抜けて残ったプロセス**。macOS と、サンドボックスを掛けない Linux（`danger-full-access`）では、子孫のプロセスが新しいセッションを作ってプロセスグループを抜けると、道具が終わった後も動き続けることがある（[OS のサンドボックス](03-02-sandbox.md)の「子プロセスの後始末」）。制限モードでは、利用者の設定で処理系のほかのプログラムを許したときの macOS に限られる。macOS では、`benitoiteh` が強制終了されたときも、子孫のプロセスは動き続けうる。残ったプロセスも、起動したときのサンドボックスの中にとどまる。
- **サンドボックスの外で動くコマンドからの秘密**。N3 は、子プロセスの環境に提供者のキーを渡さないことだけを保証する。サンドボックスを掛けずに動くコマンド（`danger-full-access`、`--no-sandbox`、承認を受けた `escalate`）は、`benitoiteh` と同じ利用者の権限で動くので、`benitoiteh` が読める認証の情報のファイルや、`benitoiteh` のプロセスの環境（Linux の `/proc/<pid>/environ` など）を読みうる。サンドボックスの中では、認証の情報のファイルは読ませない場所に入り、Linux では別の PID の名前空間で動き、macOS の方針は `sysctl` の読み取りを一つの名前に限る（[OS のサンドボックス](03-02-sandbox.md)）。
- **OS のサンドボックスの欠陥**。サンドボックスの仕組み（macOS の Seatbelt、Linux の bubblewrap と Landlock と seccomp）に欠陥があれば、R1・R4・N1 は成り立たない。
- **Benitoite の処理系の欠陥**。処理系が検査の規則を誤って実装していれば、R3 の確認は実際の操作と食い違いうる。R1 と R4 は OS のサンドボックスが強制するので、処理系の欠陥があっても成り立つ。

### Linux での保証の範囲

【決定】Linux では、bubblewrap、Landlock（ABI の版 3 以上）、seccomp を掛けられることを起動のときに確かめられたときだけ、制限モードを起動する（[OS のサンドボックス](03-02-sandbox.md)の「サンドボックスの掛け方」）。掛けられない環境では、Linux の制限モードは起動しない。理由: 保証を弱めた制限モードを同じ名前で動かすと、利用者は守られていない `.git` や秘密を守られていると思い込む。[目的と設計原則](../00-overview/00-01-goals.md)の設計原則 1（安全の性質を弱めず、範囲と時期で調整する）による。この方針は 2026-10-16 に設計者が承認した。

【決定】Linux で OS のサンドボックスが守る場所の範囲は、macOS より狭い。書ける場所の根の直下の `.git` と `.benitoiteh` は、あってもなくても守るが、それより深いところは、子プロセスを起動するときにすでにあるもの（既定で根から 3 段まで）だけを守る（[OS のサンドボックス](03-02-sandbox.md)の「Linux のファイルシステムの見え方」）。このため、子プロセスが新しく作った入れ子のリポジトリ（`sub/.git`）に書いた hooks は、利用者が後でそのディレクトリで git を使うと、サンドボックスの外で動きうる。この違いは、`doctor` と、制限モードを Linux で起動するときの表示で示す。2026-10-17 に設計者が決めた（BH-049）。理由: どの深さでも、まだなくても守る条件は、マウントでは前もって表せない。Landlock だけで表すと、書ける場所に新しいファイルを作れなくなり、サンドボックスとして使えない（[Linux のサンドボックスの検討の記録](../08-appendix/08-04-linux-sandbox.md)）。新しく作られた入れ子のリポジトリは、外側のリポジトリの `git status` に追跡していないディレクトリとして現れるので、利用者が気付く手がかりがある。Codex CLI も入れ子のリポジトリを守らない。この決定は、Linux の守る場所の性質を、範囲を明示して狭めるものである。

### モードを変える操作

【方針】モードは、利用者が `benitoiteh` を起動するときに選び、セッションの間は変えない。LLM の道具にも、`/` で始まる対話のコマンドにも、モードを変える操作を設けない。理由: 制限モードで読んだ内容（プロンプトインジェクションを含みうる）を文脈に持ったまま通常モードへ移ると、通常モードのシェルがその内容に従って動きうる。

保存したセッションを別のモードで再開することは、利用者の明示の操作として許す（[セッション](../01-agent/01-05-sessions.md)の「再開」）。制限モードのセッションを通常モードで再開するときは、前の文脈に信頼しない内容が含まれうることを示して、利用者の確認を受ける。非対話では、このモードの変更を行わない。再開した後は、再開した時点からそのモードの保証だけが成り立つ。

### OS のサンドボックスを使えない環境

【方針】制限モードは、OS のサンドボックスを掛けられないとき（対応しない OS、bubblewrap のない Linux、Landlock を持たない古い Linux のカーネル、サンドボックスの起動の失敗）は起動しない。理由: R1 と R4 は OS のサンドボックスなしには成り立たず、制限モードの名前が保証のない状態を指すことになる。通常モードは、サンドボックスを掛けられないことを利用者に示し、利用者が起動のときのオプションで明示したときだけ、サンドボックスなしで動く（[OS のサンドボックス](03-02-sandbox.md)）。コンテナの中など、外側で隔離している環境での扱いは BH-041 で決める。

### プロジェクトの指示のファイル

【決定】通常モードでは、プロジェクトの指示のファイル（`AGENTS.md`、ないときの `CLAUDE.md`）を文脈に入れる（[文脈の管理](../01-agent/01-04-context.md)の「プロジェクトの指示のファイル」）。このファイルは信頼しない内容として扱い、許可やモードを変える効果を持たせない。制限モードで指示のファイルを読むかは BH-042 で決める。
