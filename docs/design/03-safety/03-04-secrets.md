# 秘密の入力

- 状態: 草稿
- 未決事項: BH-103, BH-104, BH-105

## 目的と範囲

本章は、`benitoiteh` が起動するプログラムやスクリプトが、利用者の秘密（パスワード、SSH の鍵のパスフレーズ、ハードウェアの鍵（YubiKey など）の PIN、パスワードの管理の道具（KeePass など）の主のパスワード）を要するときの扱いを定める。手段は三つの段に分けて順に用意する。MCP とプラグインをこの用途に使わない理由も本章に書く。

本章の内容は 2026-10-19 に設計者が承認した方向であり、段 1〜3 の作りは未決事項として残る。実装の時期は別に決める。

## 前提

- 道具が起動する子プロセスは、新しいセッションで起動し、制御の端末を持たせない（[OS のサンドボックス](03-02-sandbox.md)の「端末からの切り離し」）。このため、`ssh` などが端末からパスフレーズを読もうとしても、今は利用者が答えられない。
- Linux のサンドボックスは、seccomp で Unix ドメインのソケットの作成を常に拒否する（同章の「方針の要素」）。このため、サンドボックスの中から `ssh-agent` などのソケットに接続できない。macOS の Seatbelt の方針で接続できるかは確かめていない。
- LLM の文脈に入った内容は、提供者へ送られ、セッションの記録に残る（[文脈の管理](../01-agent/01-04-context.md)の「送る内容の表示」）。

## 仕様

### 秘密を LLM に通さない

【決定】秘密は、利用者から、それを要するプログラムへ直接渡す。LLM の文脈、道具の結果、セッションの記録、画面の履歴、提供者への要求のどれにも入れない（2026-10-19 に設計者が承認した）。理由: LLM の文脈に入った秘密は提供者へ送られ、記録に残り、後の要求でも送られ続ける。LLM の出力は信頼しない（[セキュリティモデル](03-01-security-model.md)の「関係する者と信頼」）ので、LLM に秘密を扱わせる作りは、秘密を信頼しない者に渡すことになる。

### 段 1: すでにある秘密の仲介役を使う

【方針】まず、利用者がすでに使う秘密の仲介役（エージェントと GUI の入力の窓）を、子プロセスから使えるようにする。秘密はハーネスの外の窓や仲介役の中だけで扱われ、`benitoiteh` を通らない。

- SSH: `ssh-agent` に、利用者が前もって鍵を読み込ませる（macOS のキーチェーンとの連携や、KeePassXC の SSH エージェントの機能を含む）。
- ハードウェアの鍵: `gpg-agent` と GUI の PIN の入力の窓（macOS の `pinentry-mac` など）。FIDO の鍵（`ed25519-sk` の形の SSH の鍵）のタッチと PIN も、同じく仲介役か GUI の窓で受ける。
- パスワードの管理の道具: KeePassXC の SSH エージェントの機能など、管理の道具が持つ仲介の仕組み。

【決定】段 1 は、サンドボックスに穴を開けず、通常モードの「範囲の外の実行の要求」（`bash` の `escalate`。利用者がその一回を承認し、サンドボックスの外で起動する。[OS のサンドボックス](03-02-sandbox.md)の「通常モードの方針」、[利用者の確認](03-03-approval.md)の「通常モードの承認の方針」）で、仲介役を使う（2026-10-19 に設計者が決めた）。サンドボックスの中から仲介役の窓口へ接続することは、今までどおりどの OS でも許さない（03-02 の「方針の要素」の、外部の Unix の IPC を拒む規則）。制限モードは、今までどおり `ssh` などのほかの仕組みにプロセスを起動させるプログラムを許さない（03-02 の「制限モードで実行を許すプログラム」）。理由: 仲介役の窓口をサンドボックスの中に開くと、LLM が打ったコマンドが、利用者の承認なしに利用者の鍵で署名できるようになる。範囲の外の実行の要求なら、鍵を使う一回ごとに利用者が承認する。

- 2026-10-19 に、macOS で、`benitoiteh` の端末から切り離す補助（`benitoiteh __session`。新しいセッションで、制御の端末を持たず、標準入力は空）を通して起動した `ssh-add -l` が、利用者の `ssh-agent` に接続できることを確かめた（終了状態 0。範囲の外の実行の要求は、サンドボックスを掛けずにこの補助だけを通して起動する）。
- 【要検証】Linux で同じく接続できるか、GUI の入力の窓（`pinentry-mac`、`ssh-askpass`、FIDO の鍵のタッチ）が、制御の端末を持たない範囲の外の実行から出せるかは、確かめていない（BH-103）。

### 段 2: `benitoiteh` が秘密の入力を仲介する

【未決】`benitoiteh` が、秘密を求める子プロセスと利用者の間を仲介する（BH-104）。案は次のとおりである。

- `benitoiteh` が小さな補助（`SSH_ASKPASS` と同じ働きのもの）を用意し、子プロセスの環境にその補助を指す。子プロセスが秘密を求めると、補助は主のプロセスに問い合わせ、主のプロセスが対話の画面に伏せ字の入力の欄を出す。入力された値は、補助を通じてその子プロセスにだけ渡す。
- 入力の欄には、誰が求めているか（プログラムのパスと引数、そのセッションのモード、許したエフェクトとネットワークの可否）を示す。求めの文（「〜のパスワードを入力してください」）は、子プロセスが決めるものであり、信頼しない内容として、`benitoiteh` の文と区別して示す。理由: 秘密を受け取るのは、LLM が書いたスクリプトや LLM が打ったコマンドでありうる。偽りの求めの文で秘密を聞き出し、外へ送ることを、利用者が見分けられるようにする。
- 非対話の実行では仲介せず、求めを失敗として子プロセスに返す。
- 入力された値は、主のプロセスのメモリに必要な間だけ置き、記録、画面の履歴、道具の結果に書かない。

決めることは、補助と主のプロセスの間の通り道（サンドボックスの中から届く形）、`SSH_ASKPASS` 以外の求めの形（`sudo -A`、`git` の `GIT_ASKPASS`、`pinentry` の取り決め）、一回の入力をどの子プロセスに何回使わせるか、制限モードで許すかである。

### 段 3: Benitoite のスクリプトで秘密を受け取る

【未決】Benitoite の処理系に、秘密を伏せ字で読む標準の関数と、それを表すエフェクト（例えば `Console.ReadSecret`）を求め、その入力を段 2 の仲介で渡す（BH-105）。エフェクトとして宣言されるので、実行の前の確認で、そのスクリプトが秘密の入力を求めることを利用者に示せる（[利用者の確認](03-03-approval.md)の「制限モードの確認」）。処理系の変更が要るので、段 2 を作った後に、処理系への要望として出す（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系への要望」の 9）。

### MCP とプラグインを秘密の入力に使わない理由

【方針】秘密の入力のために MCP やプラグインを使わない。理由: MCP の道具の結果は LLM の文脈に入るので、例えばパスワードの管理の道具の MCP サーバでパスワードを取り出すと、そのまま提供者へ送られ、「秘密を LLM に通さない」に反する。MCP とプラグインは、試作の範囲の外のままとする（[目的と設計原則](../00-overview/00-01-goals.md)の「範囲」）。試作の後に、通常モードに限って加えるかを考える。外部の道具は Benitoite の型とエフェクトの検査を通らないので、制限モードには加えない。
