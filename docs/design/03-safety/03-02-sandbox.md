# OS のサンドボックス

- 状態: 草稿
- 未決事項: BH-041, BH-044, BH-045, BH-046, BH-090, BH-091, BH-094, BH-095

## 目的と範囲

本章は、`benitoiteh` が子プロセス（Benitoite の処理系と、通常モードのシェルのコマンド）に掛ける OS のサンドボックスを定める。対象は、対応する OS、サンドボックスの掛け方、モードごとの方針（読み書きの範囲、ネットワーク、起動できるプログラム）、制限モードで実行を許すプログラムの規則である。サンドボックスが支える保証は[セキュリティモデル](03-01-security-model.md)で、範囲の外に出る要求の承認は[利用者の確認](03-03-approval.md)で定める。

## 前提

- Codex CLI は、macOS で `/usr/bin/sandbox-exec`（Seatbelt）を、Linux で bubblewrap と seccomp を使う。Landlock は古い経路として残しているが、ファイルシステムを制限する方針では使わない（[先行事例](../08-appendix/08-01-prior-art.md)）。DeepSeek Harness は、macOS で Seatbelt、Linux で bubblewrap か Landlock を使い、掛けられないときは実行を拒む。Pi はサンドボックスを持たず、コンテナや仮想機械の中で動かすことを勧める。Claude Code の sandbox-runtime と Gemini CLI も、Linux で bubblewrap を使う（[Linux のサンドボックスの検討の記録](../08-appendix/08-04-linux-sandbox.md)）。
- 2026-10-16 に、手元の macOS 27.0.1（arm64）で次のことを確かめた。`/usr/bin/sandbox-exec` があり、`(deny process-exec)` の後に `(allow process-exec (literal "/bin/bash"))` を置いた方針で `/bin/bash` を起動すると、その `bash` が起動しようとした `/bin/ls` と `/usr/bin/python3` は `Operation not permitted` で拒否された。つまり、実行の許可は、サンドボックスの中のプロセスの子孫にも及ぶ。
- Benitoite の処理系は、Linux 向けには musl の静的リンクのビルドを対象の一つにしている（Benitoite の `deny.toml` の対象の一覧に `x86_64-unknown-linux-musl` と `aarch64-unknown-linux-musl` がある）。

## 仕様

### 対応する OS

【方針】試作が対応する OS は、macOS（arm64）と Linux（x86_64 と aarch64）とする。Windows は対象外とする。理由: 設計者の作業の環境は macOS であり、Benitoite の処理系が対象とする OS も macOS と Linux である。Windows のサンドボックス（制限付きトークンなど）は作りが大きく異なり、試作の範囲を超える。

### サンドボックスの掛け方

【方針】子プロセスは、`benitoiteh` 自身を補助のプロセスとして起動し、補助のプロセスがサンドボックスを自分に掛けてから目的のプログラムを `exec` する形で起動する。

```text
benitoiteh __sandbox <方針の JSON> -- <プログラム> <引数...>
```

- macOS では、補助のプロセスを使わず、`/usr/bin/sandbox-exec -p <方針> -D<名前>=<値>... -- <プログラム> <引数...>` で起動する。`sandbox-exec` のパスは固定し、`PATH` から探さない。理由: Codex CLI と同じく、`PATH` に置かれた偽の `sandbox-exec` を起動しないためである。パスの値（書ける場所など）は `-D` の引数で渡し、方針の文に埋め込まない。理由: パスに方針の文法の文字が含まれても、方針の意味が変わらないようにする（Codex CLI と同じ作り）。
- Linux では、`benitoiteh` が bubblewrap（`bwrap`）を起動し、bubblewrap が名前空間とファイルシステムの見え方を作った中で、`benitoiteh` 自身を補助のプロセスとして起動する。補助のプロセスは、自分に制限を掛けてから目的のプログラムを `exec` する。理由: 子プロセスを作った直後（`fork` の後、`exec` の前）に Rust の処理を走らせると、多くのスレッドを持つプロセスでは確保の待ちで止まるおそれがある。いったん自分を起動し直せば、普通の単一のスレッドのプロセスとして規則を掛けられ、`unsafe` の `pre_exec` も要らない。Codex CLI も、bubblewrap の中で自分を補助として起動し直し、seccomp を掛ける。

```text
/usr/bin/bwrap <見え方の引数...> -- <benitoiteh> __sandbox <方針の JSON> -- <プログラム> <引数...>
```

【決定】Linux では、bubblewrap、Landlock、seccomp の三つを重ねて使い、役割を次のとおり分ける。2026-10-17 に設計者が決めた（BH-049 を閉じた）。

| 仕組み | 役割 |
|---|---|
| bubblewrap | 名前空間を作り、読ませない場所を覆い、書ける場所の中の守る場所を読み取りだけにする（後述の「Linux のファイルシステムの見え方」） |
| Landlock | 起動できるプログラムを限る（実行の権利）。書ける場所の外への書き込みを拒む。読める範囲を限る方針では、読み取りの権利も限る |
| seccomp | ソケットと、ほかの危険な呼び出しを拒む（後述の「方針の要素」） |

理由: 書ける場所の下の一部を除く規則は、Landlock では表せず（後述の Landlock の限界）、マウントの名前空間が要る。Codex CLI、Claude Code の sandbox-runtime、Gemini CLI も、Linux で書ける場所の中の守る場所を bubblewrap のマウントで表している。マウントの名前空間を `benitoiteh` が自分で作ると、`unsafe` の関数（`rustix` の `unshare_unsafe`）が要り、bubblewrap の一部を作り直すことになる。bubblewrap が名前空間を作れば、`benitoiteh` は `unsafe` なしに書ける。検討した形と、ほかのハーネスの作りは[Linux のサンドボックスの検討の記録](../08-appendix/08-04-linux-sandbox.md)に書く。

【決定】bubblewrap は、利用者が配布物から導入したものを使い、試作には同梱しない。`/usr/bin/bwrap` を固定のパスで起動し、`PATH` から探さない。理由（同梱しないこと）: 試作の間は配布物を作らない（[クレートの構成](../06-impl/06-01-crate-structure.md)の「対象の環境」）。Codex CLI は bubblewrap を同梱するが、同梱すると配るものと版の管理が増える。理由（固定のパス）: `sandbox-exec` と同じく、`PATH` に置かれた偽の `bwrap` を起動しないためである。`/usr/bin` の外に bubblewrap を置く配布物での指定の仕方、要る最も古い版、setuid で導入された bubblewrap の扱い、特権を持たない利用者の名前空間の作成を AppArmor などで限る配布物での扱いは確かめる（【要検証】BH-094）。2026-10-17 の時点で、試験に使う x86_64 の機械（Omarchy）には、配布物の bubblewrap 0.12.0 が `/usr/bin/bwrap` にある。

【方針】Linux の補助のプロセスは、次の順に処理する。

1. 引数の `__sandbox` を、設定ファイルの読み込みなどの通常の起動の処理より前に見分け、方針の JSON を検証する。
2. 標準入力・標準出力・標準エラー出力のほかに開いたファイル記述子がないことを確かめる（`/proc/self/fd` の一覧で）。あれば失敗とする。
3. `no_new_privs` を設定する。
4. Landlock の規則を掛ける。
5. seccomp のフィルタを掛ける。
6. 目的のプログラムを `exec` する。

- どの段階で失敗しても `exec` せず、決まった終了状態と、標準エラー出力の一行で失敗を示して終わる。親は、この終了状態を、その道具の呼び出しの誤りとして LLM と利用者に示し、セッションは止めない。サンドボックスを掛けられるかは、起動のときに補助のプロセスを一度試して判定する（後述の「サンドボックスを掛けられないとき」）。理由: スクリプトは `Process.Exit` で任意の終了状態で終われるので、同じ終了状態を偽れる。偽った終了状態でセッションを止めると、LLM の出力だけで利用者の作業を止められる。呼び出しの誤りとして扱えば、偽っても、その呼び出しが失敗に見えるだけである。
- `no_new_privs` を先に設定するのは、特権を持たないプロセスが Landlock の規則を掛けるには `no_new_privs` が要るからである（[Landlock の文書](https://docs.kernel.org/userspace-api/landlock.html)。seccomp のフィルタも同じ）。規則を掛けた後に `no_new_privs` を設定する新しい指定は、2026-10-16 の時点でリリースされたカーネルの文書になく、使わない。
- 余分なファイル記述子を許さないのは、親から引き継いだ開いたファイルやソケットが残ると、パスの規則を掛けても、それを通して範囲の外を操作できるからである。閉じる代わりに確かめるのは、番号で記述子を閉じる `rustix` の関数が `unsafe` だからである（[rustix の文書](https://docs.rs/rustix/latest/rustix/io/fn.close.html)）。親は、子に渡す記述子に、Rust の標準のライブラリと同じく close-on-exec の印を付けて開き、標準入出力のほかを渡さない。
- 補助のプロセスは名前空間を作らない。名前空間とマウントは、補助のプロセスを起動する前に bubblewrap が作る。bubblewrap には、記述子で内容を渡す引数（`--ro-bind-data` など）を使わない（後述の「Linux のファイルシステムの見え方」）。
- 補助のプロセスは、利用者もサンドボックスの中のプロセスも起動できる。しかし、掛けた規則（`no_new_privs`、Landlock、seccomp）は外せず、後から重ねて狭めることしかできないので、補助のプロセスを起動し直しても制限は弱まらない。
- Landlock の規則を掛けたスレッドは、`mount` と `pivot_root` でファイルシステムの見え方を変えられない（[Landlock の文書](https://docs.kernel.org/userspace-api/landlock.html#filesystem-topology-modification)）。bubblewrap にも、入れ子のユーザの名前空間を作らせない指定（`--disable-userns`）を渡す（[bubblewrap の説明](https://github.com/containers/bubblewrap/blob/main/bwrap.xml)は、この指定で見え方を組み替えられなくなるとする）。理由: サンドボックスの中のプロセスが、bubblewrap が作った読み取りだけのマウントの上に、書けるマウントを重ねることを防ぐ。マウントを外せないことは、テストで確かめる（[テスト](../07-quality/07-01-testing.md)の「安全の性質のテスト」）。

【方針】起動できるプログラムは Landlock の実行の権利で限る。理由: Landlock は、実行できるファイルを限る規則を持ち、制限モードの「起動できるプログラム」の規則を直接書ける。Landlock の実行の権利は、動的リンクのローダの扱いを含めて期待どおりに働く。2026-10-17 に、試作の P0-05 で、x86_64 の Linux 7.2.9（Landlock の ABI の版 10）の rootless の podman の中で、次のことを確かめた（BH-043 を閉じた）。

- 実行の権利を与えたプログラムだけを起動でき、その制限は子孫のプロセスにも及ぶ。書ける場所に置いたプログラムは起動できない。
- 動的リンクのプログラム（`alpine:3.22` の `/bin/sh`）は、そのプログラムに実行の権利を与えても、ローダ（`/lib/ld-musl-x86_64.so.1`）に権利がなければ起動できない。カーネルが ELF のインタプリタを実行のために開くときに、Landlock が実行の権利を調べるからである。
- ローダに実行の権利を与えると、実行の権利のないプログラムも、ローダの引数に渡して動かせる。ローダは対象を読み取りとして開き、メモリに写すからである（後述の「制限モードで実行を許すプログラム」の懸念のとおり）。

読み取りの規則の権利には、実行の権利を含めない。理由: Landlock は、同じ層でパスに掛かる規則のどれかが権利を与えれば許すので、読み取りの規則に実行の権利が混ざると、実行を許すプログラムの一覧を迂回できる（[Landlock の文書](https://docs.kernel.org/userspace-api/landlock.html#layers-of-file-path-access-rights)）。`landlock` クレートの `AccessFs::from_read` は実行の権利（`Execute`）も含むので、読み取りの規則には使わない（`landlock-0.4.7/src/fs.rs`）。

Apple の `container` の既定のカーネル（6.18.15）は Landlock を有効にしてビルドされておらず（`CONFIG_SECURITY_LANDLOCK` が無効）、その中では Landlock を使えなかった。seccomp は使えた。

Landlock には、次の限界がある。

- Landlock の規則は許可だけを並べる形であり、一つの規則はディレクトリの下全体に及ぶ。このため、「全体を読めるが `~/.ssh` は読ませない」と「プロジェクトに書けるが `.git` には書かせない（まだなくても作らせない）」を、そのままでは表せない。そこで、この二つは bubblewrap のマウントで表す（後述の「Linux のファイルシステムの見え方」）。
- ファイルを実行の権利なしにメモリに写して実行する操作（`mmap` の `PROT_EXEC`）を限らない。
- Unix ドメインのソケットを限る規則は、新しい ABI にしかない。名前のない（abstract）ソケットを限る指定は ABI 6（Linux 6.12）から、パスを持つソケットへの接続と宛先付きの送信を限る権利（`LANDLOCK_ACCESS_FS_RESOLVE_UNIX`）は ABI 9（Linux 7.1）からである（[Landlock の文書](https://docs.kernel.org/userspace-api/landlock.html)。カーネルの版は、[Linux 6.11](https://www.kernel.org/doc/html/v6.11/userspace-api/landlock.html)・[6.12](https://www.kernel.org/doc/html/v6.12/userspace-api/landlock.html)・[7.0](https://www.kernel.org/doc/html/v7.0/userspace-api/landlock.html)・[7.1](https://www.kernel.org/doc/html/v7.1/userspace-api/landlock.html) の文書を比べて 2026-10-16 に確かめた）。Codex CLI が Landlock から bubblewrap に移した理由も、Unix ソケットを隔てられないことである（[先行事例](../08-appendix/08-01-prior-art.md)）。

ソケットは、どのカーネルでも使える seccomp で拒み、Landlock の Unix のソケットの規則は、使えるときに重ねて掛ける（後述の「方針の要素」）。

### Linux のファイルシステムの見え方

【決定】bubblewrap に渡す見え方は、Codex CLI の作りに倣い、次のとおりとする（[Linux のサンドボックスの検討の記録](../08-appendix/08-04-linux-sandbox.md)）。2026-10-17 に設計者が決めた。

- **全体**: ファイルシステムの全体を読み取りだけで見せ（`--ro-bind / /`）、`/dev` と `/proc` は新しく作る（`--dev /dev`・`--proc /proc`）。ユーザ、プロセスの番号、IPC の名前空間を新しく作る（`--unshare-user`・`--unshare-pid`・`--unshare-ipc`）。IP の通信を許さないときは、ネットワークの名前空間も新しく作る（`--unshare-net`）。端末のセッションを分け（`--new-session`）、親が終われば中のプロセスも終わらせる（`--die-with-parent`）。理由（`/proc`）: 外のプロセスの番号の名前空間の `/proc` を見せると、`/proc` の下の特別なリンクを通してマウントを回り込みうる（DeepSeek Harness の説明）。理由（`--new-session`）: 端末に入力を差し込む操作で、サンドボックスの外のシェルにコマンドを打たせることを防ぐ（[bubblewrap の説明](https://github.com/containers/bubblewrap/blob/main/bwrap.xml)）。
- **書ける場所**: 書ける場所ごとに、書ける形で重ねる（`--bind <場所> <場所>`）。Landlock の規則では、書ける場所に、作成・削除・名前の付け替えを含む書き込みの権利をすべて与える。守る場所は、後述のとおり読み取りだけのマウントで守るので、Landlock の規則からは除かない。
- **書ける場所の根の直下の守る場所**: 書ける場所の根の直下の `.git` と `.benitoiteh` は、あってもなくても守る。あるときは、読み取りだけで重ねる（`--ro-bind`）。`.git` が別の場所を指すファイル（`gitdir:` の行）であれば、指す先が書ける場所の中にあるときは、指す先も読み取りだけで重ねる。まだないときは、権限 555 の空の tmpfs を、読み取りだけでその名前にマウントする（`--perms 555 --tmpfs <場所> --remount-ro <場所>`）。サンドボックスの中からは、その名前のディレクトリがすでにあるように見え、中に書けない。マウントの場所なので、名前の付け替えと削除もできない（[rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) の `EBUSY`）。
- **入れ子の守る場所**: 根の直下より深い守る場所は、子プロセスを起動するときにすでにあるものだけを、読み取りだけで重ねる。探す深さは、既定で根から 3 段（`a/b/.git` まで）とし、シンボリックリンクを辿らない。名前は ASCII の大文字と小文字を区別せずに比べる。理由（すでにあるものだけ）: まだない入れ子の守る場所は、どの深さに作られるか分からず、前もって塞げない。すでにある入れ子のリポジトリの hooks は、利用者が後で git を使うと動くので守る。理由（深さ）: 子プロセスを起動するたびに書ける場所の木を辿る時間を限る。3 段は Claude Code の sandbox-runtime の既定と同じである。辿る時間と、深さの既定は確かめる（【要検証】BH-095）。
- **読ませない場所**: すでにあるディレクトリは、権限 000 の空の tmpfs で覆う（`--perms 000 --tmpfs <場所> --remount-ro <場所>`）。すでにあるファイルは、書ける場所の外に排他に作った権限 000 の空のファイルを、読み取りだけで重ねて覆う（`--ro-bind <そのファイル> <場所>`）。記述子で内容を渡す引数（`--ro-bind-data`）は使わない。理由: 標準入出力のほかの記述子を子に渡さない規則に反し、ほかのスレッドが同時に起動した子にも記述子が漏れうる。どちらも、読み取りそのものが失敗する。読み取りだけで覆うと、空の内容が読めてしまうからである。まだない読ませない場所は覆わない。このため、子プロセスが動いている間にサンドボックスの外で新しく作られた秘密は読めてしまう。
- **書ける場所の中のシンボリックリンク**: 守る場所と読ませない場所に至るパスに、書ける場所の中のシンボリックリンクがあるときは、サンドボックスを掛けずに失敗とする。理由: リンクの今の指す先を覆っても、サンドボックスの中のプロセスがリンクを差し替えれば、覆っていない先を指せる（Codex CLI も同じ理由で失敗とする）。

2026-10-17 に、試作の P0-07 で、この見え方を x86_64 の Linux 7.2.9 と bubblewrap 0.12.0（rootless の podman の中の、root でない利用者）で確かめた。根の直下の守る場所は、すでにあるとき、`gitdir:` のファイルのとき、まだないとき、付け替えて作り直すときのどれも書けず、すでにある入れ子の守る場所も書けなかった。読ませない場所は内容も一覧も読めなかった。サンドボックスの中から、これらのマウントを外すことも上に重ねることもできなかった。書ける場所には新しいファイルを作れ、消せ、名前を付け替えて書けた。塞ぐために作らせた空のディレクトリは、子の終了の後に消えた。

根の直下のまだない守る場所は、`.git` と `.benitoiteh` の綴りでだけ塞ぐ。理由: Linux の多くのファイルシステムは大文字と小文字を区別し、そこでは `.GIT` は `.git` と別の名前であり、git は `.git` を探す。

bubblewrap は、まだない場所にマウントするとき、マウントの場所として空のディレクトリを書ける場所に作るので、そのディレクトリはサンドボックスの外からも見える（Claude Code の sandbox-runtime の説明と、Codex CLI の後始末の処理による）。【方針】`benitoiteh` は、子プロセスが終わった後に、塞ぐために作らせたディレクトリが空のまま残っていれば消す。`benitoiteh` が強制終了されたときに残ったものの扱いと、同じ書ける場所で並んで動く子プロセスとの競合（一方が消すと、他方の塞ぎがなくなる）の扱いは、BH-095 で決める。

Linux の守る場所の保証は macOS より狭い。子プロセスが新しく作った入れ子の守る場所（`sub/.git`）と、根から 3 段より深いところにすでにある守る場所は、Linux では OS のサンドボックスで守らない（[セキュリティモデル](03-01-security-model.md)の「Linux での保証の範囲」）。LLM の道具（`write`・`edit`）は、どの OS でも、どの深さの守る場所にも書かない（[道具](../01-agent/01-03-tools.md)の「書く道具のパスの規則」）。

### 方針の要素

サンドボックスの方針は、次の要素の組み合わせで表す。

| 要素 | 内容 |
|---|---|
| 読める範囲 | 既定はファイルシステムの全体から、読ませない場所を除いたもの |
| 読ませない場所 | `~/.ssh`・`~/.gnupg`・`~/.aws`・`benitoiteh` の設定のディレクトリとデータのディレクトリ。利用者の設定で足せる |
| 書ける場所 | プロジェクトのディレクトリと、セッションの一時ディレクトリ。通常モードでは利用者の設定で足せる |
| 書ける場所の中の守る場所 | `.git` と `.benitoiteh`（プロジェクトの設定のディレクトリ）。macOS では、書ける場所の下のどの深さにあるものも守り（入れ子のリポジトリの `sub/.git` を含む）、名前は ASCII の大文字と小文字を区別せずに比べ、まだなくても作らせない。Linux では、書ける場所の根の直下のものを、あってもなくても守り、それより深いものは、すでにあるものだけを守る（前述の「Linux のファイルシステムの見え方」） |
| ネットワーク（IP の通信） | 使えない／使える |
| 外部の Unix IPC | 使えない（`danger-full-access` を除くどの方針でも）。macOS で IP の通信を許すときの、名前の解決などに要る宛先（BH-044）を除く |
| 起動できるプログラム | 制限しない／列挙したファイルだけ |

- 読ませない場所を設けるのは、LLM が書いたスクリプトやコマンドが、秘密の情報を読んで出力に含め、LLM の提供者へ送ることを減らすためである。Codex CLI は全体の読み取りを許すが、試作は Benitoite の事前検討の勧め（`File.Read` を許すときは読める場所を限る。ADR 0345 の決定 3）に近づける。
- `.git` を守るのは、hooks を書き込まれると、利用者が後で git を使ったときにサンドボックスの外でプログラムが動くからである。Benitoite の事前検討が git の操作で hooks を起動しないと定めた理由（ADR 0348 の決定 4）と同じ危険である。Codex CLI も `.git` を書ける場所の中で守っている。
- 【決定】ネットワークは、IP の通信と、サンドボックスの外のプロセスとの Unix ドメインのソケットによる通信（外部の Unix IPC）に分けて扱う。外部の Unix IPC は、IP の通信を許すときも許さない。理由: 外部の Unix IPC を許すと、D-Bus（`systemd-run --user` など）、コンテナのデーモンのソケット、端末の多重化のサーバに依頼して、サンドボックスの外でプロセスを起動させられる。外のサーバは、子プロセスのサンドボックスを引き継がない。`Http.Connect` の確認で利用者が許すのは IP の通信であり、この依頼までは含まない。
- Linux では、seccomp で、Unix ドメインを含めて IP 以外のソケットの作成（`socket`）を常に拒否する。IP の通信を許さないときは、IP のソケットの作成と、接続・待ち受け・受け付け（`connect`・`bind`・`listen`・`accept`）も拒否する。Unix ドメインのソケットの対（`socketpair`）は、領域が `AF_UNIX` で、種類が `SOCK_STREAM` か `SOCK_SEQPACKET` のものだけを許す。種類の引数は、一緒に指定される印（`SOCK_CLOEXEC`・`SOCK_NONBLOCK`）を除いてから比べる。フィルタは、補助のプロセスの CPU の種類の呼び出しの番号の表だけを許し、ほかの種類の呼び出し（x86_64 の上の i386 の互換の呼び出しと、x32 の番号）を拒む。理由（種類の比べ方と CPU の種類）: Rust の標準のライブラリは、ソケットの対を `SOCK_CLOEXEC` の印を付けて作るので、値の完全な一致で比べると拒んでしまう。x86_64 では、i386 の互換の呼び出し（`socketcall` など）は別の番号の表を使うので、それを拒まなければ `socket` の拒否を回り込める。理由（作れる種類を限ること）: seccomp は、`connect`・`sendto`・`sendmsg` の宛先（ポインタの先の構造体）を調べられないので、宛先では区別できない。接続していない Unix ドメインのデータグラムのソケットは、`connect` を呼ばずに `sendto` で宛先へ送れる（[unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)、[send(2)](https://man7.org/linux/man-pages/man2/send.2.html)）ので、`connect` を拒むだけでは足りない。そこで、作れるソケットを、外へ宛先を指定して送れない種類に限る。ソケットの対は、サンドボックスの中のプロセスの間の通知に使われることがあり、作った時点で互いに接続している。対のストリームのソケットが宛先付きの送信で別のソケットへ送れないこと、処理系がこの規則の下で動くことは確かめる（【要検証】BH-091）。Codex CLI の規則は Unix ドメインのソケットの接続を許すので、試作はそれより狭い。
- macOS では、ネットワークを使えないときは方針にネットワークの許可を書かない（Unix ドメインのソケットへの接続も拒まれる）。IP の通信を許すときも、Unix ドメインのソケットへの接続は、名前の解決などに要ると確かめたものだけを許す。許すものの一覧は BH-044 で決める。
- 【決定】Linux では、`socket` で Unix ドメインのソケットを作れないので、サンドボックスの中のプロセスどうしが名前を付けた Unix ドメインのソケットで通信すること（テストのために立てるサーバ、言語の道具の IPC など）もできない。外部の Unix IPC を要するコマンド（コンテナの道具、SSH のエージェントを使う git など）とあわせて、通常モードでは `escalate` の承認を受けて、サンドボックスの外で動かす。Landlock の ABI 9 の Unix のソケットの規則が使えるカーネルでは、サンドボックスの外のソケットだけを拒み、中どうしの通信を許せる見込みがある。そうするかは BH-091 で決める。この制限で通常モードの課題が失敗した数は、評価で分けて数える（[評価](../07-quality/07-02-evaluation.md)）。
- どの方針でも、seccomp で `ptrace`・`process_vm_readv`・`process_vm_writev`・`io_uring_setup`・`io_uring_enter`・`io_uring_register` を拒否する。理由: `io_uring` はソケットの呼び出しを経ずに通信でき、seccomp のネットワークの規則を回り込める。Codex CLI も同じ呼び出しを拒否する。
- macOS では、方針を `(deny default)` から始め、Mach のサービスの参照（`mach-lookup`）は、処理系とコマンドが動くのに要ると確かめたサービスだけを許す。理由: LaunchServices などのサービスに依頼すれば、サンドボックスの外でプログラムを起動させられる。許すサービスの一覧は BH-044 で決める。`sysctl-read` も、要ると確かめた名前だけを許す。2026-10-17 に、試作の P0-04 で、Rust の標準のライブラリで書いたプログラムは、起動のときに `hw.pagesize_compat` を読めないと初期化で止まり、この名前だけを許せば起動できることを確かめた。処理系とコマンドに要る名前は P2 で BH-044 とあわせて確かめる。
- macOS で守る名前を大文字と小文字を区別せずに比べるのは、macOS の既定のファイルシステムが区別しないので、`.GIT` を作れば git がそれを `.git` として使いうるからである。
- 2026-10-17 に、試作の P0-04 で、macOS 27.0.1 の Seatbelt が次のように働くことを、サンドボックスの外で本物の子プロセスで確かめた。読ませない場所を読めない。書ける場所の外と、守る場所（まだないとき、付け替えて作るとき、`.GIT` の綴りを含む）に書けない。起動できるプログラムの一覧が子孫にも及び、書ける場所の下の実行ファイルは一覧にあっても起動できない。書ける場所の動的ライブラリを `DYLD_INSERT_LIBRARIES` で読み込ませられない。外部の Unix ドメインのソケットに、IP の通信を許す方針でも許さない方針でも、接続も宛先付きの送信もできない。IP の通信は方針のとおり。Seatbelt は記述子を閉じないので、close-on-exec の印のない記述子は子に残る（親は標準入出力のほかを渡さない）。

### 書ける場所の検査

【方針】起動のときと `create_project` のときに、書ける場所（プロジェクトのディレクトリ、セッションの一時ディレクトリ、通常モードで設定で足した場所）を実のパスで調べ、次のどれかに当たれば誤りとして止める（`create_project` では作らない）。

- 書ける場所が、ファイルシステムの根か、利用者のホームディレクトリか、それらを含むディレクトリである。
- 書ける場所が、ホームディレクトリの直下の名前が `.` で始まるディレクトリ（`~/.config`・`~/.local` など）か、macOS の `~/Library` の中にある。理由: これらの下には、利用者のログインのとき、端末を開いたとき、ほかのプログラムが起動するときに読まれる設定と実行ファイルの置き場所（`~/Library/LaunchAgents`・`~/.config/autostart`・`~/.local/bin` など）が多い。
- 書ける場所が、`benitoiteh` の設定のディレクトリかデータのディレクトリ（[CLI と設定ファイル](../05-interface/05-01-cli.md)の「データの置き場所」）と重なる（どちらかが他方を含むか、同じである）。
- プロジェクトのディレクトリと一時ディレクトリが重なる。
- 書ける場所が、`benitoiteh` の実行ファイル（実のパス）を含む。理由: 子プロセスが実行ファイルを書き換えると、利用者が次に起動したときに、書き換えたプログラムがサンドボックスの外で動く。Linux では、補助のプロセスとして起動した書き換えたプログラムが、Landlock と seccomp を掛けずに目的のプログラムを動かせる（2026-10-17 の P0-07 の点検で見つかった）。

理由: ホームディレクトリを書ける場所にすると、`File.Write` を確認したスクリプトが、シェルの起動のファイル（`~/.zshrc` など）や `benitoiteh` の設定（許すプログラムの一覧）を書き換えられる。利用者が後で端末を開いたときや次に起動したときに、そのプログラムはサンドボックスの外で動く。`.git` を守るのと同じ危険である。設定とデータのディレクトリが書ける場所に入ると、子プロセスが、セッションの記録、巻き戻しの記録、切り詰めた出力の置き場所を書き換えられる。一時ディレクトリがプロジェクトの中にあると、`File.Write` を確認していないスクリプトが、一時ディレクトリを通してプロジェクトに書ける。

### 制限モードの方針

【方針】制限モードで処理系を起動するときの方針は次のとおりとする。

| 要素 | 値 |
|---|---|
| 読める範囲 | 既定 |
| 書ける場所 | `main` のエフェクトに `File.Write` を含むときは、プロジェクトのディレクトリと一時ディレクトリ。含まないときは一時ディレクトリだけ |
| ネットワーク（IP の通信） | `main` のエフェクトに `Http.Connect` か `Http.Listen` を含み、利用者が確認したときだけ使える |
| 起動できるプログラム | `main` のエフェクトに `Process.Run` を含むときは、処理系の実のパスと、制限モードで実行を許すプログラム（後述）。含まないときは、処理系の実のパスだけ |
| 書ける場所のファイルの実行 | 拒否する。macOS では、書ける場所の下のファイルを実行できる形でメモリに写すこと（`file-map-executable`）も拒否する |

- 書ける場所のファイルの実行を拒むのは、スクリプトが `File.Write` で書いたライブラリを、`Process.Run` の環境変数（`DYLD_INSERT_LIBRARIES`・`LD_PRELOAD`）で処理系や許したプログラムに読み込ませ、Benitoite の外のコードを動かす道を塞ぐためである。Benitoite の `Process` のモジュールは、起動するコマンドに環境変数を渡せる。Linux では、処理系と許したプログラムを静的リンクに限る（後述）ので、`LD_PRELOAD` は効かない。
- `benitoite_check` に当たる処理系の起動は、書ける場所を一時ディレクトリだけ、ネットワークを使えない方針で行う。
- エフェクトに応じて方針を狭めるのは、Benitoite の静的検査（エフェクトにない組み込みの操作を行わない）と OS のサンドボックスを重ねるためである。静的検査が正しければ、狭めた方針はスクリプトの動作を妨げない。処理系に欠陥があっても、確認していない種類の操作は OS のサンドボックスが拒否する。検査と実行の間にスクリプトが変えられ、確認していないエフェクトを持つスクリプトが動いたときも、書き込み・ネットワーク・プログラムの起動は、確認したエフェクトから作った方針の範囲にとどまる（[セキュリティモデル](03-01-security-model.md)の「保証しないこと」）。

### 制限モードで実行を許すプログラム

【方針】制限モードの子プロセスが起動できるのは、処理系の実のパスと、利用者の設定ファイルの `restricted.allowed_programs` に絶対パスで書いたプログラムだけである。

- 許すプログラムは、OS の実行ファイルの形式（Mach-O か ELF）のファイルであり、`#!` で始まるスクリプトでなく、書ける場所（プロジェクトのディレクトリと一時ディレクトリ）の外にあるものに限る。Linux では、さらに静的リンク（後述）に限る。処理系自身にも同じ規則を当てる（[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系の見つけ方と版の確かめ」）。理由: 書ける場所の中のプログラムを許すと、スクリプトがその中身を解釈系の写しで上書きできる。
- 設定に、別の言語の処理系か、別のプログラムを起動するための道具を書いたら、`benitoiteh` は起動のときに誤りとして止まる。判定は、シンボリックリンクを解いた実のパスのファイルの名前で行う。名前の一覧は、`sh`・`bash`・`zsh`・`dash`・`ksh`・`csh`・`tcsh`・`fish`・`busybox`・`toybox`・`python*`・`perl*`・`ruby*`・`node`・`deno`・`bun`・`lua*`・`luajit`・`php*`・`Rscript`・`julia`・`osascript`・`awk`・`gawk`・`mawk`・`nawk`・`tclsh`・`wish`・`expect`・`vi`・`vim`・`nvim`・`emacs`・`gdb`・`lldb`・`env`・`xargs`・`nohup`・`sudo`・`doas`・`open`・`launchctl`・`systemd-run`・`docker`・`podman`・`tmux`・`screen`・`ssh` と、Linux の動的リンクのローダ（`ld-linux*`・`ld-musl*`）である。一覧は、Codex CLI が永続化を拒む解釈系と起動の道具の一覧（`BANNED_PREFIX_SUGGESTIONS`）を元に、シェルを内蔵するもの（`busybox`）、解釈系を内蔵するもの（`vim`・`gdb`）、ほかの仕組みにプロセスを起動させるもの（`open`・`systemd-run`・`docker`・`tmux`・`ssh`）を加えた（[先行事例](../08-appendix/08-01-prior-art.md)）。
- 一覧は名前による判定であり、名前を変えた解釈系の写しと、一覧にない、解釈系を内蔵したプログラムは防げない（[セキュリティモデル](03-01-security-model.md)の「保証しないこと」）。利用者が許すプログラムを選ぶときは、そのプログラムが解釈系を持たないことと、プロセスグループを抜けて常駐するプロセスを作らないことを、利用者が確かめる。設定の説明の文書にそう書く。
- 許したプログラムが内部で別のプログラムを起動しようとしても、その別のプログラムが一覧になければ OS のサンドボックスが拒否する（前提に挙げた macOS での確かめのとおり、許可は子孫に及ぶ）。hooks などで `sh` を起動するプログラムを許しても、`sh` は起動できない。

【方針】Linux で処理系か許したプログラムが動的にリンクされているときは、制限モードを起動しない。理由: 動的リンクの実行ファイルを起動するには、ローダ（`ld-linux` など）の実行を許す必要がある。ローダは引数に渡した任意の実行ファイルを読み込んで動かせるので、ローダを許すと、Python などの解釈系を、その実行ファイルの実行の権利なしに動かせてしまう。静的リンクのプログラムならローダを許す必要がない。静的にリンクされているかは、ELF のヘッダの並びに `PT_INTERP` がないことで判定する。この判断は、Landlock の実際の振る舞いと合う（BH-043。前述の「サンドボックスの掛け方」）。多くの Linux の配布物のコマンド（`sort` など）は動的にリンクされているので、Linux の制限モードで許せるプログラムは実際には限られる。

### 通常モードの方針

【方針】通常モードの方針は、利用者が次の三つから選ぶ。名前と意味は Codex CLI の方針に揃える。

| 方針 | 読める範囲 | 書ける場所 | ネットワーク | 起動できるプログラム |
|---|---|---|---|---|
| `read-only` | 既定 | 一時ディレクトリだけ | 使えない | 制限しない |
| `workspace-write`（既定） | 既定 | プロジェクトのディレクトリと一時ディレクトリ（と設定で足した場所） | 使えない（設定で使えるようにできる） | 制限しない |
| `danger-full-access` | 制限しない | 制限しない | 使える | 制限しない（サンドボックスを掛けない） |

- `danger-full-access` は、起動のときのオプションか利用者の設定でだけ選べる。プロジェクトの設定では選べない。
- 承認を受けてサンドボックスの外で動かすコマンド（`bash` の `escalate`）は、その一回だけ `danger-full-access` で動かす。

### サンドボックスを掛けられないとき

【方針】サンドボックスを掛けられないとき（`sandbox-exec` がない、bubblewrap がない、特権を持たない利用者の名前空間を作れない、Landlock を持たないカーネル、seccomp を使えない）は、[セキュリティモデル](03-01-security-model.md)の「OS のサンドボックスを使えない環境」に従う。Landlock は、試作が要る規則（実行の権利と、ファイルの読み書きの権利）を持つ ABI の版が使えなければ、使えないものとして扱う。部分的にだけ掛けられるときは、掛けられた範囲を利用者に示したうえで、掛けられないときと同じに扱う（制限モードは止め、通常モードは `--no-sandbox` を指定したときだけ、サンドボックスなしで動く）。理由: 部分的なサンドボックスで続けると、利用者が掛かっているつもりの制限が掛かっていない状態になる。コンテナの中など、外側で隔離されている環境で、利用者がサンドボックスなしの起動を選べるようにするかは BH-041 で決める。

### 拒否の検出

【方針】`bash` の結果をサンドボックスに拒否されたものと見なす条件は、Codex CLI の判定に倣う。終了状態が 0 でなく、2・126・127 でなく、出力に `operation not permitted`・`permission denied`・`read-only file system`・`sandbox` のいずれかを含むか、Linux で `SIGSYS` で終わったときとする（[先行事例](../08-appendix/08-01-prior-art.md)）。見なしたときに結果に加える文は、[道具](../01-agent/01-03-tools.md)の「bash（通常モード）」で定める。誤って見なしても、加えるのは案内の文だけであり、操作を許す方向には働かない。

### 子プロセスの環境

【方針】サンドボックスの中の子プロセスには、次の環境変数を設定する。

- `TMPDIR` をセッションの一時ディレクトリにする。
- `BENITOITEH_SANDBOX` に方針の名前を、`BENITOITEH_SANDBOX_NETWORK_DISABLED=1`（ネットワークを使えないとき）を設定する。Codex CLI の同じ働きの変数に倣う。理由: テストなどがサンドボックスの中で動いていることを知り、ネットワークを要するテストを飛ばせる。
- 通常モードの `bash` では、`NO_COLOR=1`・`TERM=dumb`・`PAGER=cat`・`GIT_PAGER=cat` を設定する。理由: 色の制御の文字とページャの待ちは、LLM に返す出力を読みにくくし、コマンドを止める。Codex CLI も同じ値を設定する。

### 子プロセスの後始末

【方針】道具が起動した子プロセスは、新しいプロセスグループで起動し、次の手順で止めて片付ける。

- 時間の上限と取り消しで止めるときは、止める合図（処理系には `SIGINT`、`bash` には `SIGTERM`）をグループに送り、10 秒で終わらなければ `SIGKILL` を送る（[道具](../01-agent/01-03-tools.md)の「bash（通常モード）」、[Benitoite の処理系との連携](../04-benitoite/04-01-benitoite-integration.md)の「処理系の起動」）。
- 子プロセスが終わった後（止めて終わったときを含む）は、グループに残ったプロセスに、すぐに `SIGKILL` を送る。理由: 子プロセスが終わった後に残るのは、道具の終わりより後まで動かすことを確認していない背景のプロセスである。合図を送ってから 10 秒待つ形にすると、背景のプロセスを残すたびに道具の応答が 10 秒遅れる。
- グループへは、子プロセスがまだ回収されていない間（終わったが終了の状態を受け取っていない間を含む）にだけ送る。終わりは、回収せずに知る形（`waitid` の `WNOWAIT`）で受け取り、グループに送ってから回収する。理由: 回収した後は、子プロセスの番号と同じ値のグループの番号が、別のプロセスに使い回されうる。

新しいセッションを作ってグループを抜けたプロセスには、グループへの合図が届かない。そこで、グループを抜けたプロセスを、OS ごとに次のように扱う。

【方針】Linux のサンドボックスの中では、bubblewrap の PID の名前空間で、グループを抜けたものを含めて子孫を残さない。

- 名前空間の pid 1 を、bubblewrap の回収の役のプロセスではなく、`benitoiteh` の補助のプロセス自身にする（bubblewrap の `--as-pid-1`）。補助のプロセスは、Landlock と seccomp を自分に掛けた後、目的のプログラムを新しいプロセスグループの子として起動する。名前空間の中で親を失ったプロセスを回収し続け、目的のプログラムが終わったら、同じ終了状態（合図で終わったときは 128 に合図の番号を足した値）で終わる。
- pid 1 が終わると、カーネルは名前空間の残りのプロセスに `SIGKILL` を送る（`pid_namespaces(7)`）。`--as-pid-1` のとき、外側の bubblewrap は pid 1 の終わりを受け取ってから終わる（bubblewrap の `bubblewrap.c` の `monitor_child`。v0.11.0 で確かめた）。【要検証】カーネルが pid 1 の終わりを親に知らせるのは、名前空間の残りのプロセスがすべて終わった後であり、`benitoiteh` が bubblewrap の終わりを受け取った時点で、名前空間の中のプロセスが一つも残っていないこと（BH-090）。
- 止める合図は、`benitoiteh` から補助のプロセスへの制御のパイプで伝え、補助のプロセスが目的のプログラムのグループに送る。制御のパイプが閉じたとき（`benitoiteh` が強制終了されたときを含む）は、補助のプロセスがすぐに終わり、名前空間ごと終わる。理由: bubblewrap は `--new-session` で端末から切り離した新しいセッションを作るので、名前空間の中のグループの番号は外から分からない。外側の bubblewrap に合図を送ると、bubblewrap だけが終わり、`--die-with-parent` で名前空間が `SIGKILL` で終わるので、止める合図を中のプログラムへ渡せない。
- 制御のパイプの読み口は、補助のプロセスへ受け継がせるために、起動のときだけ `FD_CLOEXEC` を外す。ほかの子プロセスへ受け継がれないように、`benitoiteh` の子プロセスの起動は、一つの関数を通して、一度に一つずつ行う。

【方針】macOS と、サンドボックスを掛けない Linux（通常モードの `danger-full-access`）では、グループを抜けたプロセスを止める方法を持たない。macOS では、親を失ったプロセスの親は pid 1（`launchd`）になり（macOS 27.0.1 の `man 2 _exit`）、`benitoiteh` から子孫として辿れない。macOS 27.0.1 の SDK のヘッダには、子孫を引き取る仕組み（Linux の `PR_SET_CHILD_SUBREAPER`、FreeBSD の `PROC_REAP_ACQUIRE`）もない。

- 制限モードで起動を許すプログラムが処理系だけのときは、グループを抜けるプロセスは生じない。処理系（`v0.0.6`）は、自分の子プロセスを新しいセッションやグループで起動する操作（`setsid`・`setpgid`・`process_group`）を持たず、OS のサンドボックスは処理系のほかのプログラムの起動を拒むからである。処理系の版を取り込み直すときに、この点を確かめ直す。
- 利用者の設定で処理系のほかのプログラムを許したときは、macOS では、そのプログラムがグループを抜けて起動したプロセスを止められない。`Process.Run` の確認の画面でそう示す（[利用者の確認](03-03-approval.md)の「制限モードの確認」）。
- グループに `SIGKILL` を送った後、子プロセスの標準出力と標準エラー出力のパイプが 2 秒のうちに閉じなければ、パイプを持つプロセスが残っていると見なす。このときは、道具の結果と画面に、子孫のプロセスが残っている可能性を示す。制限モードでは、あわせてエージェントの一連の処理を止める。理由: 確認していない背景のプロセスが動き続けるまま、次の実行の確認へ進まないためである。パイプを閉じたプロセスは、この方法では見つけられない。

通常モードで残りうるプロセスと、`benitoiteh` が強制終了されたときに macOS で残りうるプロセスは、[セキュリティモデル](03-01-security-model.md)の「保証しないこと」に書く。

Seatbelt の方針の文の細部（Codex CLI の基本の方針から何を写すか）は、実装プランで定める（BH-044）。`sandbox-exec` は、macOS 27.0.1 の `man sandbox-exec` で非推奨（DEPRECATED）とされており、将来の macOS で使えなくなる危険がある（BH-045）。ネットワークをドメインで限る仕組み（Codex CLI の手元のプロキシ）は試作では作らず、要るかを評価の後に決める（BH-046）。
