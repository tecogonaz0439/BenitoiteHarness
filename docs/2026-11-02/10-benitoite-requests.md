# Benitoite の処理系への要望（benitoiteh から）

本書は、Benitoite の試作のエージェントハーネス `benitoiteh`（リポジトリ `tecogonaz0439/BenitoiteHarness`）から、Benitoite の処理系 `benitoite` への要望をまとめる。Benitoite の作業をするエージェント（Claude Code）が、本書だけを読んで要望の背景、欲しい振る舞い、受け入れの条件を判断できるように書く。設計者は、次の次の版での実現を検討している（2026-11-03）。どの要望を採るか、形をどうするかは、Benitoite の設計者と処理系の側で決める。

## 本書の読み方

- 処理系の事実は、Benitoite `v0.0.12`（コミット `d0678ddb`）のソースと実行ファイルで確かめた。確かめた日と方法を各項に書く。
- `benitoiteh` の側の文書は、BenitoiteHarness のリポジトリの根からの相対パスで示す（例: `docs/design/04-benitoite/04-01-benitoite-integration.md`）。リンクにしないのは、本書を単独のファイルとして読んでも、どこを指すかが分かるようにするためである。
- `BH-nnn` は BenitoiteHarness の未決事項の番号である（`docs/design/open-issues.md`）。Benitoite の `TODO-nnn` や ADR の番号とは別である。
- 要望の番号は、本書で付け直した（R1〜R5）。`benitoiteh` の設計書（04-01「処理系への要望」）の番号との対応は、末尾の「番号の対応」に示す。

## 前提: benitoiteh が処理系をどう使うか

`benitoiteh` は、処理系をライブラリとして組み込まず、実行ファイルを子プロセスとして起動する。起動した処理系には、`benitoiteh` が OS のサンドボックス（Linux の bubblewrap・Landlock・seccomp、macOS の Seatbelt）を掛ける。処理系の静的な検査とエフェクトの上限の照合（`check --report=json`、`--allow-effects`）は、宣言した契約を比べるだけであり、隔離は起動する側が持つ。これは Benitoite の SECURITY.md と同梱の Skill の「Inspecting before execution」の立場と同じである。

`benitoiteh` には二つのモードがある。

- **制限モード**: LLM に許す操作を、Benitoite のスクリプトの作成・検査・実行と、プロジェクトの中のファイルの読み取りに限る。シェルを道具として持たせず、Benitoite 以外の言語の処理系を起動させない。スクリプトを実行する前に、`check --report=json` の宣言したエフェクトを利用者に示して確認を受け、`run --allow-effects=<確認したエフェクト>` で実行する。
- **通常モード**: シェルとファイルの編集の道具を持つ一般的なハーネスとして振る舞う。

`v0.0.7` は、`benitoiteh` の前の依頼（Benitoite の docs/todo の TODO-254）に応えて、`check --report=json`、`test --check`、`--allow-effects`、`--version=json`、`Command.environment` のローダの変数の拒否、`skill list`・`skill show` を加えた。本書の要望は、その続きである。

## 要望の一覧

| 番号 | 要望 | 種類 | benitoiteh の側の未決事項 | 優先の案 |
|---|---|---|---|---|
| R1 | `Http.Connect` の通信を、起動する側が示す HTTP のプロキシに通す | 機能 | BH-040 | 高 |
| R2 | 下のディレクトリの入口が取り込んだモジュールの表示のパスを、実在するパスにする | 不具合 | BH-029 | 高 |
| R3 | 一つのファイルを検査するときの取り込みの根の指定、または入口の間の検査の共有 | 機能・性能 | BH-028 | 中 |
| R4 | 秘密を伏せ字で読む標準の関数と、それを表すエフェクト | 機能（検討の依頼） | BH-105 | 低 |
| R5 | スクリプトから、起動したハーネスの読む道具を呼ぶエフェクト | 機能（形の相談） | BH-002 | 低 |

優先の案は、`benitoiteh` のオーケストレータの見立てである。R1 は安全の性質（制限モードの通信を許したドメインに限る）に、R2 は LLM が直す先を誤る不具合に関わるので高くした。R4 と R5 は、`benitoiteh` の側でも採るかを決めていないので、形の相談として出す。

各要望には、次の機能の有無を `--version=json` で知らせる印を付けてほしい（たとえば `formats` に並べる版、または新しい `features` の一覧）。理由: `benitoiteh` は起動のときに処理系の機能を確かめ、ない版では今の回避を使い続ける。

## R1: `Http.Connect` の通信をプロキシに通す

### 背景

`benitoiteh` の通常モードは、サンドボックスの中のコマンドの通信を、`benitoiteh` の中の HTTP のプロキシ（中継）にだけ通し、利用者が許したドメインにだけ届ける（`docs/design/03-safety/03-02-sandbox.md` の「通信の中継」。2026-11-02 に作った）。中継は、`CONNECT` のトンネル（HTTPS など。中身は覗かない）と、平文の HTTP の絶対形の要求（`GET http://host/path`）を受け付ける。許したドメインでも、名前を解決したアドレスが私的なもの（ループバック、リンクローカル、私的なアドレスなど）なら断る。断ったときは、理由を本文にした 403 を返し、断った宛先と理由を道具の結果に事実として載せる。

制限モードの `Http.Connect` も、同じ中継で限る方針である（BH-040）。今は、`Http.Connect` を確認したスクリプトの実行では、サンドボックスで IP の通信をすべて許している。つまり、利用者が `Http.Connect` を一度許すと、スクリプトはどのホストにもつながる。

### v0.0.12 の振る舞い（確かめた事実）

`crates/benitoite/src/builtins/funcs/http_client.rs` の 63 行目で、HTTP のクライアント（ureq）を `.proxy(None)` で作っており、環境変数のプロキシの指定にも従わない（2026-11-02 に v0.0.12 のソースで確かめた）。このため、`benitoiteh` がプロキシを示しても、制限モードの通信を中継に通せない。

### 欲しい振る舞い

1. 起動する側が、`Http.Connect` の接続に使う HTTP のプロキシの URL を指定できる。形の案は次のどちらかである。
   - 実行のオプション（例: `run --http-proxy=<URL>`、`test` にも同じもの）。
   - 標準の環境変数（`HTTPS_PROXY`・`HTTP_PROXY`・`ALL_PROXY` と小文字の名前）に従う。
   
   `benitoiteh` はオプションの形を推す。理由: 利用者の環境に前から設定されたプロキシの変数を、スクリプトの通信に黙って使わせない。オプションなら、起動する側が指定したときだけ効く。
2. 指定したときは、HTTPS の宛先へは `CONNECT host:port` のトンネルで、平文の HTTP の宛先へは絶対形の要求で、必ずプロキシを通す。プロキシにつながらない、またはプロキシが断ったときは、直接の接続に切り替えず、誤りとして返す。理由: 直接の接続に戻ると、中継で限る意味がなくなる。（サンドボックスが直接の接続を塞ぐので、戻っても外には出ないが、失敗の理由が分かりにくくなる。）
3. プロキシの URL の利用者の情報（`http://user:password@127.0.0.1:port`）を、`Proxy-Authorization: Basic` で送る。理由: macOS では中継をループバックのポートで待ち受け、手元のほかのプロセスからの利用を、セッションごとの乱数の合言葉で断る。
4. 宛先を除く指定（`NO_PROXY`）で、プロキシを迂回しない。少なくとも、オプションの形で指定したときは、`NO_PROXY` を見ない。
5. プロキシが返した 403 などの状態と本文を、スクリプトから見える誤り（または応答）として返す。誤りの文、診断、内部の誤りの報告に、プロキシの URL の合言葉を含めない。
6. `Http.Listen`（待ち受け）は対象の外である。中継で扱えないので、今のままでよい。
7. `--version=json` で、この指定を受け付けることを知らせる。

### 受け入れの条件（benitoiteh が確かめること）

- 指定したプロキシを通して、許したドメインの HTTPS と平文の HTTP にだけ届く。
- プロキシが断った宛先への接続は、スクリプトに誤りとして返り、直接の接続を試みない（ネットワークの名前空間の中で、プロキシのほかに出口がない状態で確かめる）。
- 合言葉付きの URL で、`Proxy-Authorization` が送られる。誤りの出力に合言葉が現れない。
- 指定しないときは、今の振る舞い（プロキシを使わない）のまま変わらない。

### benitoiteh の側の今の扱いと、入った後に変えること

今は、制限モードで `Http.Connect` を確認すると IP の通信をすべて許す。R1 が入った版では、`Http.Connect` を確認したスクリプトの実行に中継を通し、許すドメインと確認の答えを通常モードと同じ門で扱う。評価の課題のうち、手元の模擬の宛先（`127.0.0.1`）につなぐもの（`http_client`）は、中継が私的なアドレスを断るので、`benitoiteh` の側で扱いを決める。処理系の側の変更は要らない。

## R2: 下のディレクトリの入口が取り込んだモジュールの表示のパス

### v0.0.12 の振る舞い（確かめた事実）

2026-11-03 に、Linux の x86_64 で v0.0.12 のリリースのビルドを使い、次の手順で再現した。

`proj/Lib/M.bnt`（型の誤りを含む）:

```text
public function value() -> Integer
  return "text"
end function
```

`proj/A/X.bnt`:

```text
import Lib.M
public function value() -> Integer
  return M.value()
end function
```

```bash
cd proj && benitoite test --check --diagnostics=json .
```

同じ型の誤り（E0401）が二度出る。一つは `primary.file` が `./Lib/M.bnt`、もう一つは `./A/Lib/M.bnt` である。`./A/Lib/M.bnt` は存在しない。`A/X.bnt` の入口が取り込んだ `Lib.M` を、`<入口のディレクトリ>/<モジュールのパス>` の形で表示している。`v0.0.7` で見つけ、`v0.0.12` でも同じであることを確かめた。

`benitoiteh` の記録では、同じ形の誤りが次の欄にも現れる（`v0.0.7` で確かめた）。

- 診断の `primary.file`、`secondary[].file`、`helps[].edits[].file`
- `check --report=json` と `test --check --report=json` の `sources[].displayPath`
- `test` の結果の表明の `primary.file`

### 困ること

- 実在しないファイルを指すので、LLM が直す先を誤る。誤ったパスに新しいファイルを書くこともある。
- `benitoiteh` は、利用者が読ませないと決めたファイル（`read.exclude` など）の診断を LLM に見せない。表示のパスが実のパスと違うと、この判定を表示のパスで行えない。今は、存在しないファイルの診断を重なりとして除き、件数だけを示す回避を置いている（`docs/design/04-benitoite/04-01-benitoite-integration.md` の「終了状態と診断の受け渡し」）。誤った表示のパスと同じ名前の囮のファイルを置かれると、除いたモジュールの診断の文が、囮のパスの診断として LLM に渡りうる。報告の `sources` は内容のハッシュで照合して塞いだが、診断にはハッシュがないので塞げない（BH-029）。

### 欲しい振る舞い

- どの欄でも、モジュールの表示のパスを、そのモジュールの本当のファイルのパス（起動のディレクトリからの相対の形。今の `./Lib/M.bnt` と同じ規則）にする。
- 同じモジュールを、複数の入口から取り込んでも、同じ表示のパスで示す。同じ診断を一度だけ示せれば、なおよい（診断の重複を除く規則は、処理系の側で決めてよい）。
- 取り込みの解き方（どのディレクトリを根にするか）が、起動の仕方で変わるなら、それを文書に書く。今の版では、`check A/X.bnt` は `Lib.M` を見つけられず（E0318）、`test --check .` は見つける。これは R3 と関わる。

### 受け入れの条件

- 上の再現の手順で、表示のパスに存在しないファイルが現れない。
- 報告の `sources[].displayPath` と、診断の各欄のパスが、同じモジュールで一致する。

### benitoiteh の側の今の扱いと、入った後に変えること

直った版を `--version=json` で見分けられれば、存在しないファイルの診断を重なりとして除く回避を外し、読ませないファイルの判定を表示のパスで行う。

## R3: 取り込みの根の指定、または入口の間の検査の共有

### 背景

`benitoiteh` の制限モードは、LLM が `.bnt` のファイルを書くたびに、プロジェクトのディレクトリへ `test --check` を走らせ、その結果を書いた結果に添える（`docs/design/01-agent/01-03-tools.md` の「書いた後の検査（制限モード）」）。書いたファイルだけを検査しないのは、一つのファイルを検査すると、プロジェクトの根からの取り込みを解けないからである（R2 の `check A/X.bnt` の E0318）。

### 測った結果（確かめた事実）

`test --check .` の時間は、入口の数に比例する。

| 版と機械 | 1 | 150 | 300 | 600 | 1,000 |
|---|---:|---:|---:|---:|---:|
| `v0.0.7`、macOS 27.0.1、Apple M4（2026-10-18） | — | — | 1.80 秒 | — | 6.30〜6.45 秒 |
| `v0.0.12`、Linux x86_64 のクラウドの仮想機械、4 コア（2026-11-03） | 0.05 秒 | 7.6 秒 | 15.5 秒 | 29.7 秒 | — |

`v0.0.12` の測定は、`import Benitoite.Unofficial.IO.Console` を取り込んで一行を書くだけの `main` を持つファイルを並べ、3 回の最小を取った。入口一つにつき約 50 ms で、`v0.0.7` の約 6.4 ms より大きい。機械が違うので、版の違いによるものかは分からない。`benitoiteh` は、書く道具の応答の目安を 1 秒、検査の時間の上限を 30 秒としており、この機械では約 20 の入口で目安を、約 600 の入口で上限を超える。

### 欲しい振る舞い（どちらか一方でよい）

1. 一つのファイルを検査するときに、取り込みを解く根を指定できる（例: `check --root=<ディレクトリ> <ファイル>`、`test --check --root=<ディレクトリ> <ファイル>`）。根の下のモジュールを、ディレクトリを検査するときと同じ規則で解く。`--report=json` の形は今と同じとする。
2. ディレクトリを検査するときに、入口の間でモジュールの検査の結果を共有し、同じモジュール（前置きの標準のモジュールを含む）を入口ごとに検査し直さない。共有する形なら、入口ごとに繰り返される診断も減ると見込む（R2 の重複とも関わる）。

1 なら、`benitoiteh` は書いたファイル（と、それを取り込む入口）だけを検査できる。2 なら、全体の検査が速くなる。

### 受け入れの条件

- 1 の場合: 上の R2 の `proj` で、`check --root=. A/X.bnt` が `Lib.M` を解き、型の誤りを `./Lib/M.bnt` に示す。
- 2 の場合: 同じ内容の入口を 300 並べたときの `test --check .` の時間が、入口の数に比例して増えない（前置きの検査を共有する分だけでも減る）。

## R4: 秘密を伏せ字で読む標準の関数とエフェクト（検討の依頼）

### 背景

`benitoiteh` は、サンドボックスの外のコマンドが求めるパスワードなどの秘密の入力を、LLM を通さずに利用者から受け取って渡す仲介を持つ（`docs/design/03-safety/03-04-secrets.md` の「段 2」。`SSH_ASKPASS` などを補助に向ける）。Benitoite のスクリプトが秘密を受け取る標準の方法はまだない。

### 欲しいもの

- 秘密を伏せ字で読む標準の関数（例: `Console.readSecret`）と、それを表す専用のエフェクト（例: `Console.ReadSecret`）。専用のエフェクトなら、`check --report=json` に現れ、実行の前の確認で「このスクリプトは秘密の入力を求める」と利用者に示せる。
- 入力の出どころを、起動する側が指定できる形（例: 受け継いだファイル記述子、または起動する側が示す補助のプログラム）。端末から読むときは、文字を表示しない。
- 読んだ値を、診断、内部の誤りの報告、`--wasm-stats` などの出力に含めない。

### 相談したい点

形は処理系の側の判断に任せる。`benitoiteh` の側でも、採るかは試作の後に決める（BH-105）。制限モードで SSH の接続などの秘密を要する作業を、処理系の中のライブラリで行う方向（BH-107）と組み合わせて考える。

## R5: スクリプトから、起動したハーネスの読む道具を呼ぶエフェクト（形の相談）

### 背景

ほかのエージェントハーネス（DeepSeek Harness の PTC、Pi の code mode、Hermes の `execute_code`）は、LLM が書いたスクリプトの中から、ハーネスの道具（ファイルの読み取り、検索）を呼ばせる。多くのファイルを扱う課題で、LLM との往復の数を大きく減らしうる。`benitoiteh` の制限モードは、Benitoite 以外の言語の処理系を起動させないので、同じことをするなら Benitoite のスクリプトから呼ぶ形になる（BH-002。`benitoiteh` の側でも採るかを決めていない）。

### 考えている形（案）

- 道具の呼び出しを、専用のエフェクト（例: `Harness.Read`・`Harness.Glob`・`Harness.Grep`）として宣言させる。`check --report=json` に現れるので、実行の前の確認と `--allow-effects` の照合の対象にできる。
- 呼び出しは、起動する側が用意した通り道（例: 受け継いだファイル記述子の上の、一行一件の JSON の要求と応答）で、ハーネスに渡す。ハーネスは、自分の道具の規則（読ませないファイル、範囲、大きさの上限）で処理して結果を返す。処理系は、ファイルシステムに直接触れない。
- 最初は読む道具だけとし、書く道具と実行する道具は対象にしない。

### 相談したい点

- 処理系の側で、外部とのこのような通り道を持つエフェクトを作れるか。作れるなら、標準のモジュールの形と、通り道の取り決め（誰が版を管理するか）。
- 今は実装の依頼ではない。`benitoiteh` の側で効果を見込めるかを評価の前に詰めるための相談である。
